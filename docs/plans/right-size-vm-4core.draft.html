เอา config กลับไปตามสเปก แล้วค่อยวัด

architecture.md §8.1 ระบุ VM 4 core / 6 GB ไว้อยู่แล้ว พร้อมสเปกของแต่ละ service แต่ docker-compose.yml ปัจจุบันหลุดไปจากนั้นมาก แผนนี้คือการดึงกลับ — ไม่ใช่การออกแบบใหม่ — โดยแบ่งเป็น 4 ระยะที่ความเสี่ยงไล่จากศูนย์ขึ้นไป

ข้อสรุปก่อนอ่านต่อ

config หลุดจากสเปกของตัวเอง — §8.1 เขียนว่า app-N: mem_limit 512m, cpus 0.75 และ 6 instance แต่ของจริงคือ cpus 1.5 และ 8 instance ทำให้ mem_limit รวมเป็น 7,424 MB ซึ่ง เกิน RAM ทั้งเครื่อง (6,144 MB) — นี่คือข้อเดียวที่พิสูจน์ได้ด้วยเลขล้วนว่าต้องแก้

แต่การแก้ config จะไม่ทำให้ p95 ที่เห็นในผล k6 ดีขึ้นเท่าไหร่ เพราะสาเหตุจริงคือยิงเกินเพดานเครื่อง ตัวที่น่าจะให้ผลมากที่สุดและเสี่ยงศูนย์คือแก้ pacing ของ k6 ก่อน (ระยะ 0) — จึงต้องทำก่อนแตะ docker-compose.yml เลย

02

งบ RAM — ตัวเดียวที่พิสูจน์ได้ด้วยเลขล้วน

Memory ต้องแก้

ตอนนี้ — mem_limit รวม7,424 MB · 121%
เส้นดำ = 6,144 MB · เกินไป 1,280 MB
ที่เสนอ (ชั่วคราว)5,056 MB · 82%
เหลือ 1,088 MB ให้ OS + page cache

CPU เพดาน ไม่ใช่การจอง

ตอนนี้ — cpus รวม18.0 / 4 core
เพดานรวม 450% ของเครื่อง
ที่เสนอ8.5 / 4 core
app tier เหลือ 4.5 — กันไม่ให้กลืน datastore
สิ่งที่เพดาน CPU ทำได้จริง — cpus: เป็นโควตาต่อ cgroup ไม่ใช่การจอง คอนเทนเนอร์หนึ่งไม่ถูก throttle เพราะโควตาของอีกตัว ตัวเลขรวม 8.5 บน 4 core จึงไม่ได้ทำอะไรโดยตรง ประโยชน์จริงคือ เพดาน app tier ที่ 4.5 กันไม่ให้ 6 Node process กลืน CPU จนไม่เหลือให้ redis-data ซึ่ง §8.2 ระบุว่าเป็นคอขวดอันดับ 2 · ⚠️ docker compose ตั้ง ลำดับความสำคัญ ระหว่างคอนเทนเนอร์ไม่ได้ (ไม่มี cpu_shares) เวลาแย่ง CPU จริง scheduler มอง app instance กับ redis-data เท่ากัน — ถ้ายังไม่พอ ค่อยพิจารณา cpuset แยก core ให้ datastore

เสี่ยงศูนย์ · ไม่ต้องขอ §8

ทำก่อนแตะ config เลย เพราะอาจอธิบาย collapse ได้เกือบหมด แล้วทำให้ทั้งแผนนี้ไม่จำเป็น

06

Impact — อะไรที่อาจพัง

เสี่ยงสุด

  • app-1 ทำ migration + seed คนเดียว (RUN_MIGRATIONS: "true" มีแค่ที่ docker-compose.yml:186-213) — ลบได้แค่ท้ายแถวเท่านั้น
  • postgres OOM ตอน burst ถ้าตั้ง mem_limit ต่ำเกินพื้นจริง — บน primary คือโดนกลางทรานแซกชัน กระทบ §4 ข้อ 7

ต้องเช็ค

  • throughput อาจลดจาก 8 → 6 — แต่ §8.2 ข้อ 1 บอกว่าบน 4 core การเพิ่ม instance ให้ context switch ไม่ใช่ throughput · ต้อง A/B
  • cpus 0.75 ทำให้ Node โดน CFS throttle กลางคำขอได้ ตอนโหลดเต็ม — เป็นราคาที่จ่ายเพื่อกัน app tier ไม่ให้กลืน redis-data · ดู p95 หลังแก้ว่าคุ้มไหม

ไม่กระทบ

  • API contract §3 — ไม่แตะ path / field / status code
  • invariant §4 ทั้ง 11 ข้อ — ไม่แตะ Lua / transaction / jobId / compensation
  • app-entrypoint.sh:71-83 — instance รอ schema + stock key ตรงๆ ไม่ได้ผูกกับ depends_on: app-1 ลบท้ายแถวจึงไม่กระทบ
  • loadtest/run-all.js:24 อ้างแค่ fs-app-1
07

สิ่งที่แก้จากฉบับแรก (หลัง review 2 รอบ)

ฉบับแรกเขียนว่าทำไมถึงผิดแก้เป็น
“6 instance บน 4 core โอเคเพราะงานเป็น I/O-bound” ตัวเลขที่วัดได้บอกตรงข้าม — ตอน 400 VUs แอปกิน 60–77% ของ core ขณะที่ redis-cache 15% / redis-data 11% · และ /health/live ทำได้ 10,213 rps เทียบกับ /products 4,190 rps ที่ VUs เท่ากัน = ต้นทุนอยู่ที่ handler CPU ไม่ใช่การรอ I/O อ้าง §8.1 (สเปกกำหนด 6 อยู่แล้ว) แทน และยอมรับว่า 4 vs 6 ต้อง A/B
redis-data ลด cpus 1.0 → 0.75 §8.2 ข้อ 2 ระบุว่าเป็น คอขวดอันดับ 2 — thread เดียวรับ gatekeeper.lua + BullMQ + MGET ทุก read + AOF fsync · 11% ที่วัดได้เป็นค่าเฉลี่ย ไม่ใช่ burst คง 1.0
heap 384 → 256, mem_limit 512m → 384m อ้าง RSS ซึ่งรวม native + code ไม่ได้บอก heap pressure · ถ้า V8 heap OOM ตอน worker ทำ job → stalled job → สต็อกหาย 1 ชิ้น (§0.1) → ตก §9.3 คง heap 384 · mem_limit 448m เป็นค่าชั่วคราวรอวัด heapUsedMb
postgres primary 768m / replica 512m เพราะ “CPU 1.7% / 0.03%” CPU ไม่เกี่ยวกับ RAM ของ postgres ซึ่งเป็น process-per-connection · พื้นจริง = shared_buffers 256MB + 48 conn × 5–10MB + overhead ≈ 530–770 MB → 512m เสี่ยง OOM replica 640m · ทั้งคู่รอยืนยันจากระยะ 1
แก้ k6 อยู่ท้ายตาราง “ยังไม่แก้” เสี่ยงศูนย์ ไม่ต้องขอ §8 และอาจอธิบาย collapse ได้เกือบหมด — ทำทีหลังคือเรียงผิด ย้ายขึ้นเป็น ระยะ 0
