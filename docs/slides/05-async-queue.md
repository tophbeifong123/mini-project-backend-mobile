# Backend 05 — Async Communication

> บทนี้ตอบคำถามเดียว: **งานที่ช้าและงานที่ล้มเหลวได้ ควรถูกย้ายออกจากเส้นทางของ request ยังไง โดยไม่ทำงานหาย และไม่ทำงานซ้ำ**

### 📌 หัวข้อหลักในบทนี้:
- **Sync vs Async (รอผลลัพธ์ตรงนั้น vs โยนงานทิ้งไว้แล้วตอบกลับเลย)**
- **Pub/Sub (ประกาศออกไป ใครฟังอยู่ก็ได้รับ ไม่ฟังก็ตกหล่น)**
- **Queue / BullMQ (ที่พักงานรอ worker มาหยิบไปทำ / ไลบรารีคิวบน Redis)**
- **At-least-once (รับประกันว่างานถึงแน่ ๆ แต่อาจถึงซ้ำ)**
- **Idempotency (ทำซ้ำกี่รอบผลก็เท่าเดิม ไม่เกิดของซ้ำ)**
- **Retry + Backoff + Jitter (ลองใหม่ + เว้นห่างขึ้นเรื่อย ๆ + สุ่มเวลากันมาพร้อมกัน)**
- **DLQ (ถังพักงานที่ retry จนครบแล้วยังพัง ไว้ตามแก้ทีหลัง)**
- **Concurrency / Rate limit (ทำพร้อมกันได้กี่งาน / ยิงได้ไม่เกินกี่ครั้งต่อวินาที)**

## 0. จุดที่เรื่องเดินมาถึง

Flash Sale ตัดสต็อกถูกแล้ว (บท 03) DB ไม่ตายแล้ว (บท 04) แต่ผู้ใช้ยังต้อง**รอ 8 วินาที** หลังกดปุ่ม "ยืนยันคำสั่งซื้อ"

```typescript
async createOrder(dto) {
  const order = await this.repo.save(dto);        //  50ms
  await this.mailer.sendConfirmation(order);      // 3000ms ← รอ SendGrid
  await this.sms.send(order.phone);               // 2000ms ← รอ Twilio
  await this.invoice.generatePdf(order);          // 3000ms ← สร้าง PDF
  return order;                                   // รวมประมาณ 8 วินาที
}
```

และมันแย่กว่าแค่ "ช้า" ตรงที่ **ถ้า SendGrid ล่ม ผู้ใช้จะได้ error ทั้งที่ order สร้างสำเร็จไปแล้ว** เขาก็จะกดซ้ำ แล้วเราก็ได้ order ซ้ำ

> 📊 **แผนภาพ: งานเท่าเดิม ใช้เวลารวมเท่าเดิม — เปลี่ยนแค่ว่า "ใครเป็นคนรอ"**
>
> *ข้อความ/ลำดับในแผนภาพ:*
> - แบบเดิม (sync) — ผู้ใช้รอทุกอย่าง
> - DB
> - ส่งอีเมล 3s
> - SMS 2s
> - สร้าง PDF 3s
> - ผู้ใช้จ้องหน้าจอรออยู่ตรงนี้ ~8 วินาที
> - ผู้ใช้
> - แบบใหม่ (async) — ผู้ใช้รอแค่ของที่จำเป็น
> - คิว
> - ~70ms แล้วตอบกลับเลย
> - worker
> - ส่งอีเมล
> - SMS
> - สร้าง PDF
> - ทำงานอยู่เบื้องหลัง ผู้ใช้ไม่เกี่ยวแล้ว

> 🎯 **ความคิดตั้งต้นของทั้งบท**
> งานสองแบบนี้ต่างกันโดยสิ้นเชิง:
>
> - **สิ่งที่ผู้ใช้ต้องรู้ผลเดี๋ยวนี้** เช่น "order เลขที่ 123 สร้างแล้ว" → ทำ*ตอนนี้* แล้วตอบกลับ
> - **สิ่งที่ผู้ใช้ไม่จำเป็นต้องรอ** เช่น อีเมล, SMS, PDF → **ฝากไว้ให้คนอื่นทำทีหลัง**  *((โยนแล้วไม่ต้องรอผล = fire-and-forget))*
>
> **กฎตัดสิน:** ถ้างานใช้เวลาเกิน 1 วินาที **หรือ** ผลลัพธ์ไม่จำเป็นต้องใช้ทันที → ทำแบบ async  *((โยนงานไปทำเบื้องหลังแล้วตอบกลับเลย ไม่ block รอเหมือน sync))*

## 1. Pub/Sub  *((publisher ประกาศเข้า channel ใครที่ subscribe ฟังอยู่ก็ได้ยินหมด))* กับ Queue — ต่างกันคนละโลก

นี่คือจุดที่คนสับสนมากที่สุดในบทนี้ เพราะทั้งคู่รันอยู่บน Redis เหมือนกัน แต่**รับประกันคนละเรื่อง**

> 📊 **แผนภาพ: ความต่างอยู่ที่ลูกศรล่าง — Pub/Sub แจกให้ทุกคน ส่วน Queue ให้คนเดียว**
>
> *ข้อความ/ลำดับในแผนภาพ:*
> - Pub/Sub — กระจายเสียง
> - Queue — ส่งถึงตัว
> - Publisher
> - channel: user.created
> - instance 1
> - instance 2
> - instance 3
> - ทุกตัวได้ข้อความ → ถ้าข้างในส่งอีเมล = ผู้ใช้ได้ 3 ฉบับ
> - ไม่เก็บข้อความ · ไม่มี ack · ไม่ retry · ไม่เรียงลำดับ
> - Producer
> - คิวใน Redis
> - worker 1
> - worker 2
> - worker 3
> - งาน 1 ชิ้น มีคนหยิบไปทำแค่คนเดียว → เพิ่ม worker ได้ไม่ซ้ำ
> - เก็บใน Redis · มี ack · retry อัตโนมัติ · FIFO ตอนหยิบ

|  | Pub/Sub | Queue (BullMQ)  *((BullMQ = ไลบรารีทำคิวที่ใช้ Redis เป็น broker เก็บงาน))* |
| --- | --- | --- |
| รูปแบบ | one-to-many (broadcast)  *((กระจายให้ทุกตัวที่ฟังอยู่ = fan-out))* | point-to-point (ใครหยิบได้ก่อนได้ไป) |
| เก็บข้อความไว้ไหม | **ไม่** — ถ้าไม่มีใครฟังอยู่ตอนนั้น **ข้อความหายเลย** | **เก็บใน Redis** รอจนมีคนมาทำ |
| ack  *((สัญญาณบอกคิวว่างานนี้ทำเสร็จแล้ว คิวถึงจะลบทิ้ง))* | ไม่มี | มี |
| retry  *((ล้มเหลวแล้วคิวเอากลับมาลองใหม่ให้เอง))* | ไม่มี | มี auto-retry |
| ลำดับ | ไม่รับประกัน | FIFO (ตอนหยิบ)  *((เข้าคิวก่อนได้ทำก่อน))* |
| ใช้กับ | cache invalidation  *((สั่งล้างของเก่าใน cache ทิ้ง))*, notification แบบ real-time, metrics, sync ระหว่าง instance  *((ตัวสำเนาของแอปที่รันอยู่จริง 1 ตัว))* | อีเมล, payment, ประมวลผลวิดีโอ, งาน batch, งานตั้งเวลา |

> 🧠 **ประโยคเดียวที่ตัดสินได้ทุกกรณี**
> **ถ้างานนี้ "ต้องเกิดขึ้นให้ได้" → ใช้ Queue**
>
> **ถ้างานนี้ "เกิดก็ดี ไม่เกิดก็ไม่เป็นไร" → ใช้ Pub/Sub**
>
> Pub/Sub ไม่มี persistence  *((เก็บลงที่ที่ข้อมูลไม่หายตอนระบบดับ))* ไม่มี ack ไม่มี retry — ห้ามใช้กับ payment หรือการสร้าง user เด็ดขาด

### 1.1 กับดัก Pub/Sub ที่โยงกับบท 06

> ⚠️ **Pub/Sub + หลาย instance = ทำงานซ้ำ N ครั้ง**
> ตามรูปด้านบน Pub/Sub เป็น broadcast คือ **ทุก subscriber ที่ฟังอยู่ได้ข้อความหมด** ถ้าเรา scale เป็น 3 instance (บท 06) แล้ว subscriber ข้างในนั้นส่งอีเมล → **ผู้ใช้จะได้อีเมล 3 ฉบับ**
>
> เพราะฉะนั้น: **logic ที่มี side effect ต้องอยู่ใน queue ไม่ใช่ใน subscriber**  *((side effect = ผลที่ไปเปลี่ยนของจริง เช่นส่งอีเมล ตัดเงิน))* — subscriber  *((ฝั่งที่สมัครฟัง channel นั้น))* ควรทำได้แค่งานที่ "ทำซ้ำกี่ครั้งก็ได้ผลเหมือนเดิม" เช่น ลบ cache key ซึ่งพอดีเป๊ะกับที่บท 04 ต้องการ คือบอกทุก instance ให้ล้าง cache พร้อมกัน

**ข้อจำกัดทางเทคนิค:** Redis client ที่อยู่ใน subscribe mode **รันคำสั่งอื่นไม่ได้เลย** ต้องแยก client สำหรับ publish กับ subscribe คนละตัว

**ตั้งชื่อ channel:**  *((ชื่อช่องที่ประกาศเข้าไป บางเจ้าเรียก topic))* ใช้รูปแบบ `resource.action` เช่น `user.created`, `order.placed`

## 2. Queue ทำงานยังไง

โครงสร้างมี 3 ส่วน: **producer**  *((ฝั่งผลิตงาน คู่กับ consumer คือฝั่งที่หยิบไปทำ))* คือคนโยนงานเข้าคิว (ปกติคือ service ใน API), **queue** คือที่พักงานซึ่งอยู่ใน Redis, และ **worker** คือ process แยกที่คอยหยิบงานไปทำ

```typescript
// Producer — อยู่ใน service (บท 02)
await this.emailQueue.add('order-confirmation', { orderId: order.id }, {
  attempts: 3,
  backoff: { type: 'exponential', delay: 1000 },
  removeOnComplete: { age: 3600 },
  removeOnFail: false,
});

// Worker — เป็น process แยกต่างหาก
@Processor('email')
export class EmailProcessor extends WorkerHost {
  async process(job: Job) {
    const order = await this.orderRepo.findOne({ where: { id: job.data.orderId } });
    await this.mailer.send(order);
  }
}
```

> 🧠 **payload (ข้อมูลที่แนบไปกับ job)**
> ต้องเป็น "ตั๋ว" ไม่ใช่ "ของ"
>
> ส่ง **reference** (id, url) ไม่ใช่ตัวข้อมูลจริง — ส่ง `{ orderId: 123 }` ไม่ใช่ order object ทั้งก้อน และห้ามส่ง binary หรือ buffer เด็ดขาด เพราะ **job ทั้งหมดอยู่ใน RAM ของ Redis**  *((job = งาน 1 ชิ้นในคิว))* ส่ง PDF 5MB เข้าคิว 1,000 งาน Redis ก็ระเบิด
>
> ผลพลอยได้คือ worker จะอ่านข้อมูลสด ณ เวลาที่ทำงานจริง ไม่ใช่ข้อมูล ณ เวลาที่โยนเข้าคิวซึ่งอาจเก่าไปแล้ว

## 3. At-Least-Once & Idempotency — ใจกลางของบทนี้

### 3.1 ทำไมงานถึงถูกทำซ้ำได้

> 📊 **แผนภาพ: ช่องว่างระหว่างขั้น ② กับการ ack คือสิ่งที่ทำให้ exactly-once  *((ทำครั้งเดียวเป๊ะ — อีกแบบคือ at-most-once ที่ไม่ซ้ำแต่ยอมให้งานหาย))* เป็นไปไม่ได้ในทางทฤษฎี**
>
> *ข้อความ/ลำดับในแผนภาพ:*
> - ทำไมระบบคิวถึงรับประกันได้แค่ at-least-once
> - Worker 1
> - ① หยิบ job
> - "ส่งอีเมล"
> - ② ส่งอีเมลสำเร็จ
> - ผู้ใช้ได้รับแล้ว ✓
> - ③ 💥 ตายก่อน ack
> - (deploy / OOM / ไฟดับ)
> - Queue
> - ④ ไม่เห็น ack
> - คืน job กลับเข้าคิว
> - Worker 2
> - ⑤ หยิบไปทำใหม่
> - ผู้ใช้ได้อีเมลฉบับที่ 2
> - เวลา →
> - "ทำงานเสร็จ" กับ "บอกว่าเสร็จแล้ว" เป็นคนละเหตุการณ์ และรวมเป็นหนึ่งเดียวไม่ได้

> ⚠️ **ความจริงที่ต้องยอมรับ**
> ระบบคิวทุกตัวรับประกันแบบ **at-least-once** (อย่างน้อยหนึ่งครั้ง) ไม่ใช่ exactly-once
>
> เพราะจังหวะระหว่าง "ทำงานเสร็จ" กับ "บอกว่าทำเสร็จแล้ว" **ไม่มีทางเป็น atomic ได้**  *((atomic = เกิดครบทั้งคู่หรือไม่เกิดเลย ไม่มีสภาพครึ่ง ๆ))* นี่เป็นข้อจำกัดเชิงทฤษฎีของระบบกระจาย ไม่ใช่ข้อบกพร่องของ BullMQ
>
> **⚠ สไลด์เขียนขัดกันเอง** — สไลด์หนึ่งบอก "At-least-once delivery" แต่อีกสไลด์ถัดมาบอก "Exactly-once: each job processed once" ข้อหลัง**ผิด** ถ้าข้อสอบถามให้ตอบว่า at-least-once

### 3.2 ทางออกเดียวคือ Idempotency

**Idempotent** แปลว่า ทำกี่ครั้งก็ได้ผลเหมือนทำครั้งเดียว (เหมือนกดปุ่มลิฟต์ซ้ำ ๆ ลิฟต์ก็มาคันเดียว)

```typescript
async process(job: Job) {
  const key = `email:${job.data.orderId}`;

  // เช็คก่อนว่าเคยทำไปแล้วหรือยัง
  const already = await this.sentRepo.findOne({ where: { key } });
  if (already) return;                      // ทำไปแล้ว → จบเลย ไม่ถือเป็น error

  await this.mailer.send(...);
  await this.sentRepo.insert({ key });      // unique constraint กันซ้ำอีกชั้น
}
```

> 🧠 **โยงกับบท 03 และ 04**
> **ตัวรับประกันสุดท้ายคือ unique constraint ที่ database**  *((unique constraint = กฎที่ DB บังคับว่าค่านี้ห้ามซ้ำ ซ้ำแล้ว insert ไม่ผ่าน))* ไม่ใช่ `if` ในโค้ด เพราะการเช็คแล้วค่อยเขียนก็คือ read-check-write  *((อ่านมาเช็คแล้วค่อยเขียน มีช่องให้อีก request แทรกจนผลเพี้ยน))* ที่มีช่องว่างอีกแล้ว (บท 03) และเป็นเหตุผลเดียวกับที่บท 04 บอกว่า distributed lock  *((กุญแจกลางกันหลาย instance แย่งทำของชิ้นเดียวกัน))* เป็นแค่ best-effort
>
> สรุปเป็นหลักที่ใช้ได้ทั้งวิชา: **lock กับ cache ช่วยลดการทำซ้ำ แต่ความถูกต้องมาจาก idempotency + constraint ที่ DB**

## 4. Retry — ทำให้ถูกวิธี

### 4.1 Exponential backoff  *((ล้มแล้วรอนานขึ้นเรื่อย ๆ ค่อยลองใหม่ ไม่ถล่มซ้ำทันที))* + jitter

```typescript
attempts: 3,
backoff: { type: 'exponential', delay: 1000 },   // 1s → 2s → 4s
```

ทำไมต้อง exponential: ถ้า SendGrid  *((บริการส่งอีเมลของเจ้าอื่น เรียกผ่าน API))* ล่มแล้วเรา retry ทันทีทุก 100ms เราแค่กำลัง**ซัดระบบที่กำลังป่วยให้หนักขึ้น** การถอยห่างขึ้นเรื่อย ๆ คือการให้เวลามันฟื้น

> 🛑 **⚠ สไลด์ไม่ได้พูดถึง jitter**
> ถ้า job 1,000 ตัวล้มเหลวพร้อมกัน (เพราะ SendGrid ล่ม) แล้วทุกตัวใช้ backoff เท่ากันเป๊ะ ๆ มันจะ **กลับมาพร้อมกันอีกครั้งเป็นระลอก** ที่วินาทีที่ 1, 2, 4 พอดี
>
> ต้องบวก **jitter**  *((สุ่มบวกลบเวลานิดหน่อย กันทุกตัวกลับมาพร้อมกันเป๊ะ))* แบบสุ่มเพื่อกระจายออก — หลักการเดียวกับ TTL jitter (บท 04) และ deadlock retry (บท 03)

### 4.2 แยกความล้มเหลว 2 ประเภท (ข้อนี้ออกสอบแน่)

|  | Transient (ชั่วคราว) | Permanent (ถาวร) |
| --- | --- | --- |
| ตัวอย่าง SMTP  *((โปรโตคอลส่งอีเมล))* | **4xx** — 421, 450, 451, 452 (server ยุ่ง, mailbox เต็มชั่วคราว) | **5xx** — 550, 551, 552, 553 (อีเมลไม่มีอยู่จริง) |
| ควรทำ | **retry** เดี๋ยวมันก็หาย | **ห้าม retry** ส่งอีกกี่ครั้งก็ล้มเหลวเหมือนเดิม |
| ถ้าทำผิด | — | เปลือง attempt ฟรี ๆ และ**ทำลาย sender reputation**  *((คะแนนความน่าเชื่อถือของผู้ส่ง ตกแล้วเมลเราจะไปลง spam))* เพราะ provider มองว่าเราสแปม |

```typescript
async process(job: Job) {
  try {
    await this.mailer.send(...);
  } catch (e) {
    if (e.responseCode >= 550 && e.responseCode <= 559) {
      await this.markPermanentFailure(job);
      return;             // ← return ไม่ใช่ throw : บอกคิวว่า "จบแล้ว อย่า retry"
    }
    throw e;              // ← transient : ให้ BullMQ retry ตาม backoff
  }
}
```

### 4.3 Dead Letter Queue (DLQ)  *((ที่พักงานที่ retry ครบแล้วยังพัง กัน poison message วนกวนคิวไม่จบ))*

พอ retry ครบแล้วยังไม่สำเร็จ ต้องมีที่ให้มันไปอยู่ **และต้องมี alert** ไม่งั้นความล้มเหลวจะเงียบ ซึ่งเท่ากับข้อมูลหายโดยไม่มีใครรู้

> 🛑 **⚠ ตัวอย่าง DLQ ในสไลด์มีบั๊ก**
> สไลด์ push เข้า DLQ เมื่อถึง attempt สุดท้าย **แล้วยัง `throw error` ต่อ** → BullMQ เห็น throw ก็ retry อีกครั้ง → เข้า DLQ ซ้ำเป็นรายการที่สอง
>
> ทางที่ถูกคือที่ attempt สุดท้ายให้ `return` หลังจาก push DLQ แล้ว ไม่ใช่ throw

### 4.4 การตั้งค่าที่ต้องมี

| Option | ทำไม |
| --- | --- |
| `attempts: 3–5` | มากไปคือทรมานระบบปลายทาง น้อยไปคือยอมแพ้เร็วเกิน |
| `removeOnFail: false` | **เก็บหลักฐานไว้ debug** ถ้าลบทิ้ง เราจะไม่มีทางรู้ว่ามันพังเพราะอะไร |
| `removeOnComplete: { age: 3600 }` | ถ้าไม่ตั้ง job ที่สำเร็จจะกองสะสมจน **Redis memory เต็ม** |
| job timeout | **BullMQ ไม่มี option `timeout`** (มีแต่ใน Bull v4) ต้องทำเองด้วย `Promise.race`  *((ใครถึงก่อนเอาอันนั้น ใช้ตัดงานที่เกินเวลา))* ไม่งั้น job ที่ค้างจะกิน worker slot ตลอดกาล |
| graceful shutdown  *((ปิด worker แบบรอ job ที่ทำค้างอยู่ให้จบก่อน ไม่ตัดกลางคัน))* | ถ้าไม่มี ทุกครั้งที่ deploy จะทิ้ง job ค้างสถานะ stalled  *((หยิบไปแล้วเงียบเกินเวลาที่คิวยอมรอ เจ้าอื่นเรียก visibility timeout))* ไว้ |

**หมายเหตุ:** พอ job ที่ stalled ถูกกู้คืน มันจะ**รันใหม่ทั้งงาน**ตั้งแต่ต้น ไม่ใช่ทำต่อจากจุดที่ค้าง — ย้ำเรื่อง idempotency อีกครั้ง

## 5. Throughput  *((จำนวนงานที่ทำได้ต่อวินาที))*: Concurrency, Rate Limit, Priority

### 5.1 Concurrency  *((worker 1 ตัวรับ job พร้อมกันได้กี่ชิ้น))*

| ประเภทงาน | Concurrency | เหตุผล |
| --- | --- | --- |
| CPU-bound (สร้าง PDF, resize รูป) | **1–2** | Node เป็น single-threaded — งาน CPU หนักหลายตัวพร้อมกันจะ**ยึด event loop**  *((เส้นทางรันงานเส้นเดียวของ Node ถ้าโดนยึด งานอื่นรอหมด))* ทำให้ทุกอย่างช้าลงหมด |
| I/O-bound (ส่งอีเมล, เรียก API) | 5–20 | ส่วนใหญ่คือการนั่งรอ ไม่ได้กิน CPU ทำพร้อมกันได้เยอะ |
| งานเบามาก | 20–50 |  |

ถ้าอยากได้ throughput มากขึ้นสำหรับงาน CPU-bound ให้ **เพิ่มจำนวน process ไม่ใช่เพิ่ม concurrency** เช่น `pm2 -i 4`  *((สั่งรัน Node เป็น 4 process พร้อมกัน))* เพราะแต่ละ process มี event loop ของตัวเอง

### 5.2 Rate Limiter  *((คุมไม่ให้ยิงงานเกินโควตาต่อวินาทีของปลายทาง))*

ต้องตั้งให้ตรงกับโควตาของ provider เช่น SendGrid 100 ต่อวินาที, Mailgun 1000 ต่อชั่วโมง, Stripe 100 ต่อวินาที

> ⚠️ **ทำไมสำคัญกว่าที่คิด**
> ถ้าส่งเกินโควตา provider จะตอบ **429**  *((รหัส HTTP ที่แปลว่า "ยิงถี่เกินไป"))* หรือ**ตีตราว่าเราสแปม** และเนื่องจาก job ที่ได้ 429 จะถูก retry ตามระบบ มันจะ**ยิ่งส่งเยอะขึ้น** กลายเป็นวงจรที่ทำให้แย่ลงเรื่อย ๆ
>
> **⚠ สไลด์วาง `limiter` ไว้ที่ `registerQueue` ซึ่งผิด** — ใน BullMQ `limiter` เป็น option ของ **Worker**

### 5.3 Priority  *((งานด่วนได้หยิบก่อน ไม่ต้องต่อท้ายแถว))*

| Priority | งาน |
| --- | --- |
| 1 | reset password / security alert |
| 2–3 | ผู้ใช้ premium |
| 4–6 | งานปกติ (order confirmation) |
| 7–9 | อีเมลการตลาด / bulk |
| 10 | งานเบื้องหลัง |

**แยกคิวตามประเภทงานด้วย** — งานประมวลผลวิดีโอที่ใช้เวลา 10 นาทีต้องไม่ไปติดขวางคิวอีเมล ลำพัง priority อย่างเดียวไม่พอถ้ายังใช้คิวเดียวกัน

### 5.4 Delayed jobs

`delay: 86400000` แปลว่าทำอีก 24 ชั่วโมง ใช้กับการเตือนก่อนหมดช่วงทดลองใช้หรือ reminder และยกเลิกได้ด้วยการเก็บ `jobId` ไว้แล้วเรียก `job.remove()`

## 6. Operations

| เรื่อง | ทำไม |
| --- | --- |
| **แยก Redis ของ queue ออกจาก cache** | eviction policy `allkeys-lru`  *((memory เต็มเมื่อไหร่ เขี่ยคีย์ที่ไม่ได้ใช้นานสุดทิ้ง))* ของ cache จะ**ลบ job ในคิวทิ้ง** (ย้ำจากบท 04) |
| เปิด **AOF**  *((โหมดจดทุกคำสั่งลงไฟล์ ข้อมูลไม่หายตอน Redis ดับ))* บน Redis ของคิว | คิวคือข้อมูลที่หายไม่ได้ ต้องมี persistence จริง ไม่ใช่แค่ snapshot เป็นช่วง ๆ |
| **Bull Board ต้องมี auth**  *((Bull Board = หน้าเว็บ dashboard ไว้ดูและสั่งงานในคิว))* | มันเปิดเผย payload ของทุก job ซึ่งอาจมีข้อมูลส่วนบุคคล และ**สั่ง retry หรือ remove ได้** — สไลด์ mount ไว้ที่ `/admin/queues` โดยไม่มี middleware ป้องกันเลย |
| เปลี่ยนรูปร่างของ payload | job ที่อยู่ในคิวแล้วยังใช้รูปแบบเก่า → ต้อง**รองรับทั้งสองแบบไว้หนึ่ง release** (แนวคิดเดียวกับ expand-and-contract ในบท 03)  *((เพิ่มของใหม่ให้อยู่ร่วมกับของเก่าก่อน แล้วค่อยถอดของเก่าทิ้ง))* |

**Metric ที่ต้อง monitor:**  *((ตัวเลขที่ต้องมีจอเฝ้า ไม่งั้นคิวตันแล้วไม่มีใครรู้))* waiting  *((จำนวน job ที่กองรออยู่ = ความลึกของคิว))*, active, failed ต่อชั่วโมง, processing rate, avg duration, p95/p99  *((ช้ากว่านี้แค่ 5% / 1% ของงานทั้งหมด ดูความช้าของคนซวย ไม่ใช่ค่าเฉลี่ย))*, **queue lag** คืออายุของ job ที่รอนานที่สุด (ตัวนี้บอกได้ดีที่สุดว่าคิวตามงานทันหรือไม่), stalled count

> ⚠️ **FIFO ไม่ได้แปลว่าเสร็จตามลำดับ**
> คิวรับประกันลำดับการ *หยิบ* เท่านั้น ไม่ใช่ลำดับการ *เสร็จ* — ถ้า concurrency มากกว่า 1 job ที่ 2 อาจเสร็จก่อน job ที่ 1 ได้ ถ้าต้องการลำดับเคร่งครัดจริง ๆ ต้องตั้ง concurrency เป็น 1 หรือใช้ FlowProducer  *((ตัวจัด job เป็นสายพ่อ-ลูก ให้ทำต่อกันเป็นสเต็ป))*

> 🛑 **⚠ สไลด์บทนี้ผิดเรื่อง Bull vs BullMQ หลายจุด**
> 1. **สไลด์ผสม Bull กับ BullMQ** — ติดตั้ง `@nestjs/bull` คู่กับ `bullmq` แต่ import `from 'bull'` ซึ่งใช้ด้วยกันไม่ได้ ต้องเลือกชุดเดียว: `@nestjs/bullmq` + `bullmq` (แนะนำ) หรือ `@nestjs/bull` + `bull`
> 2. `timeout` ไม่มีใน BullMQ (มีใน Bull v4) ให้ใช้ `Promise.race`
> 3. `job.progress(n)` เป็นของ Bull — BullMQ ใช้ `job.updateProgress(n)`
> 4. `queue.on('completed')` ใช้ไม่ได้กับ BullMQ Queue ต้องใช้ `QueueEvents` หรือ `@OnWorkerEvent()`
> 5. สไลด์อ้างทั้ง at-least-once และ exactly-once — **exactly-once ผิด**
> 6. ตัวอย่าง DLQ push แล้ว throw ต่อ ทำให้เกิด attempt เกินและได้รายการซ้ำ
> 7. `limiter` ถูกวางที่ `registerQueue` แต่ที่ถูกคือเป็น option ของ Worker
> 8. เทส "should not retry on permanent failure" คาดหวัง `result.success === false` แต่ processor ที่แสดงไว้ throw ทุกกรณี — ขาด branch ตรวจ 5xx
> 9. ตัวอย่าง publisher ใช้ `this.db.user.create()` ซึ่งเป็น Prisma  *((ORM อีกยี่ห้อ — ตัวแปลงระหว่าง object ในโค้ดกับตารางใน DB))* ทั้งที่ทั้งวิชาใช้ TypeORM

## 7. 🔗 บทนี้ต่อกับบทอื่นตรงไหน

> 🔗 **เส้นเชื่อม**
> - **← บท 02:** เพราะ business logic อยู่ใน service ไม่ใช่ controller → worker จึงเรียกใช้ logic เดิมได้เลยโดยไม่ต้อง copy โค้ด
> - **← บท 03:** "ห้ามส่งอีเมลหรือตัดบัตรใน transaction ให้ enqueue แทน"  *((transaction = กลุ่มคำสั่ง DB ที่ต้องสำเร็จทั้งหมดหรือไม่เกิดอะไรเลย))* คือ**ประโยคที่ทำให้บทนี้มีอยู่** — และต้อง enqueue  *((โยนงานเข้าคิว))* หลัง commit  *((ยืนยันจบ transaction แล้วข้อมูลลง DB จริง))* เท่านั้น / backoff + jitter คือหลักการเดียวกับ retry deadlock / idempotency ต้องพึ่ง unique constraint ที่ DB
> - **← บท 04:** queue อยู่บน Redis จึงต้องแยก instance จาก cache เพราะ eviction จะกิน job / pub/sub ใช้บอกทุก instance ให้ล้าง cache
> - **→ บท 06:** Pub/Sub + หลาย instance = ทำงานซ้ำ N ครั้ง เป็นเหตุผลตรง ๆ ที่ต้องเข้าใจ horizontal scaling / graceful shutdown ของ worker คือเรื่องเดียวกับ graceful shutdown ของ API / queue lag เป็น metric ที่ต้องอยู่บน dashboard
> - **→ บท 06:** การย้ายงานหนักออกไปที่ queue คือ**ขั้นตอนที่ต้องทำก่อน scale out** เพราะการเพิ่ม instance ไม่ได้ทำให้ SendGrid ตอบเร็วขึ้น

## 8. 📝 คลังคำตอบอัตนัย

<details>
<summary><b>Pub/Sub กับ Message Queue ต่างกันอย่างไร และควรเลือกใช้อันไหนในกรณีใด</b></summary>

โครง: รูปแบบการส่ง → การรับประกัน 4 ข้อ → เกณฑ์เลือก → กับดักตอน multi-instance

**Pub/Sub** เป็นรูปแบบ one-to-many คือ publisher ส่งข้อความไปยัง channel แล้ว subscriber ทุกตัวที่ฟังอยู่จะได้รับข้อความนั้นทั้งหมด ส่วน **Queue** เป็น point-to-point คือ job หนึ่งชิ้นจะถูกหยิบไปทำโดย worker เพียงตัวเดียวเท่านั้น

ความต่างที่สำคัญกว่าคือการรับประกัน Pub/Sub **ไม่มี persistence** หากไม่มี subscriber ฟังอยู่ในขณะนั้นข้อความจะหายทันที อีกทั้ง**ไม่มี ack ไม่มี retry และไม่รับประกันลำดับ** ขณะที่ Queue เก็บ job ไว้ใน Redis จนกว่าจะมี worker มาหยิบ มีการ ack มี auto-retry และเป็น FIFO ในการหยิบงาน

เกณฑ์การเลือกสรุปได้เป็นประโยคเดียวคือ **หากงานนั้น "ต้องเกิดขึ้นให้ได้" ใช้ Queue หากเป็นกรณี "เกิดก็ดี ไม่เกิดก็ไม่เสียหาย" ใช้ Pub/Sub**

ดังนั้น Pub/Sub จึงเหมาะกับ cache invalidation, การแจ้งเตือนแบบ real-time, การส่ง metric และการซิงค์สถานะระหว่าง instance ส่วน Queue ต้องใช้กับการส่งอีเมล การชำระเงิน การประมวลผลไฟล์ งาน batch และงานตั้งเวลา โดยห้ามใช้ Pub/Sub กับงานเหล่านี้เด็ดขาด

กับดักที่ต้องระวังคือเมื่อมีหลาย instance เนื่องจาก Pub/Sub เป็น broadcast ทุก instance ที่ subscribe จะได้รับข้อความและทำงานนั้นซ้ำกันทั้งหมด หาก subscriber นั้นส่งอีเมล ผู้ใช้จะได้รับอีเมลเท่ากับจำนวน instance ดังนั้น logic ที่มี side effect ต้องอยู่ใน queue เท่านั้น ส่วน subscriber ควรทำเฉพาะงานที่ทำซ้ำแล้วได้ผลเหมือนเดิม เช่นการลบ cache key
</details>

<details>
<summary><b>เหตุใดระบบคิวจึงรับประกันได้เพียง at-least-once และเราต้องออกแบบระบบอย่างไรเพื่อรับมือ</b></summary>

โครง: ลำดับเหตุการณ์ที่ทำให้ซ้ำ → ทำไมเป็นข้อจำกัดเชิงทฤษฎี → idempotency → ตัวรับประกันสุดท้ายอยู่ที่ DB

สาเหตุคือระหว่าง "การทำงานเสร็จ" กับ "การแจ้งคิวว่าทำเสร็จแล้ว" หรือ ack นั้นเป็นสองเหตุการณ์ที่**ไม่สามารถทำให้เป็น atomic ได้**

ลำดับที่เกิดขึ้นจริงคือ worker หยิบ job ไปส่งอีเมลสำเร็จแล้ว แต่เกิด crash ก่อนที่จะ ack ซึ่งอาจเกิดจากการ deploy, OOM  *((โดนระบบฆ่าเพราะใช้ RAM เกินที่ให้ไว้))* หรือไฟดับ คิวจึงเห็นว่า job นี้ไม่มีผู้ใดยืนยันว่าทำเสร็จ และคืน job กลับเข้าคิวให้ worker ตัวอื่นหยิบไปทำใหม่ ผลคือผู้ใช้ได้รับอีเมลสองฉบับ

นี่เป็นข้อจำกัดเชิงทฤษฎีของระบบกระจาย ไม่ใช่ข้อบกพร่องของ BullMQ ดังนั้นคำกล่าวที่ว่าระบบคิวให้การรับประกันแบบ exactly-once จึงไม่ถูกต้อง

วิธีรับมือคือทำให้ทุก handler **idempotent** คือทำกี่ครั้งก็ได้ผลลัพธ์เหมือนทำครั้งเดียว ในทางปฏิบัติคือมีตาราง dedupe  *((ตารางกันซ้ำ เก็บ idempotency key ของงานที่ทำไปแล้ว))* ที่บันทึกว่างานนี้เคยทำไปแล้ว โดยใช้ `jobId` หรือ business key เป็นตัวระบุ แล้วตรวจสอบก่อนทำงานว่ามีบันทึกอยู่หรือไม่ หากมีก็ return ทันทีโดยไม่ถือเป็น error

จุดสำคัญคือ **การตรวจสอบด้วย `if` ในโค้ดเพียงอย่างเดียวไม่เพียงพอ** เพราะการอ่านแล้วค่อยเขียนยังคงมีช่องว่างให้เกิด race แบบเดียวกับที่ทำให้เกิด oversell ในบทฐานข้อมูล ตัวรับประกันสุดท้ายจึงต้องเป็น **unique constraint ที่ระดับ database**

เพิ่มเติมคือ เมื่อ job อยู่ในสถานะ stalled แล้วถูกกู้คืน มันจะถูกรันใหม่ทั้งงานตั้งแต่ต้น ไม่ใช่ทำต่อจากจุดที่ค้างอยู่ จึงยิ่งตอกย้ำความจำเป็นของ idempotency
</details>

<details>
<summary><b>ออกแบบระบบส่งอีเมลยืนยันคำสั่งซื้อให้ทนทานต่อความล้มเหลว จงอธิบายการตั้งค่าและเหตุผล</b></summary>

โครง: ย้ายออกจาก request → ตั้ง retry → แยก transient/permanent → DLQ → idempotency → rate limit → ops

ขั้นแรก **ย้ายการส่งอีเมลออกจากเส้นทางของ request** โดยให้ API บันทึก order ลง database แล้ว enqueue job หลังจาก commit สำเร็จเท่านั้น จากนั้นตอบผู้ใช้ทันที เหตุผลคือลด response time จากหลายวินาทีเหลือหลักสิบมิลลิวินาที และทำให้ความล้มเหลวของ SendGrid ไม่ทำให้การสร้าง order ล้มเหลวตามไปด้วย

ขั้นที่สอง ตั้ง **retry แบบ exponential backoff ร่วมกับ jitter** เช่น `attempts: 3–5` และ `backoff: { type: 'exponential', delay: 1000 }` เหตุผลของ exponential คือหากปลายทางกำลังมีปัญหา การ retry ถี่ ๆ จะยิ่งซ้ำเติม ส่วน jitter จำเป็นเพราะหาก job นับพันตัวล้มเหลวพร้อมกันแล้วใช้ delay เท่ากันหมด มันจะกลับมาชนกันซ้ำเป็นระลอกที่จังหวะเดิม

ขั้นที่สาม **แยกความล้มเหลวชั่วคราวออกจากความล้มเหลวถาวร** SMTP code กลุ่ม 4xx เช่น 421, 450, 451, 452 เป็นความล้มเหลวชั่วคราวที่ควร retry ส่วน 5xx เช่น 550, 551, 552, 553 หมายถึงที่อยู่อีเมลไม่มีอยู่จริง ซึ่งไม่ควร retry เลย เพราะนอกจากจะเปลือง attempt แล้วยังทำลาย sender reputation ทำให้ provider มองว่าเราส่งสแปม ในโค้ดคือเมื่อพบ 5xx ให้บันทึกเป็น permanent failure แล้ว `return` ไม่ใช่ `throw`

ขั้นที่สี่ มี **dead letter queue พร้อม alert** สำหรับ job ที่ retry ครบแล้วยังล้มเหลว เพราะหากไม่มี ความล้มเหลวจะเงียบและกลายเป็นการสูญหายของข้อมูลที่ไม่มีผู้ใดทราบ ควรตั้ง `removeOnFail: false` เพื่อเก็บหลักฐานไว้วิเคราะห์ และตั้ง `removeOnComplete` ตามอายุหรือจำนวน เพื่อไม่ให้ job ที่สำเร็จสะสมจน Redis เต็ม

ขั้นที่ห้า ทำ handler ให้ **idempotent** ด้วยตาราง dedupe ที่มี unique constraint เนื่องจากระบบคิวรับประกันแบบ at-least-once

สุดท้ายในเชิง operation ต้องตั้ง **rate limiter ให้ตรงกับโควตาของ provider** เช่น SendGrid ประมาณ 100 ต่อวินาที มิฉะนั้นจะได้รับ 429 ซึ่งจะถูก retry แล้วยิ่งส่งหนักขึ้นเป็นวงจร, ตั้ง concurrency ประมาณ 5–20 เพราะเป็นงาน I/O-bound, แยกคิวอีเมลออกจากคิวงานหนักอย่างการประมวลผลวิดีโอ, ส่ง payload เป็น `orderId` ไม่ใช่ object ทั้งก้อน, ใช้ Redis คนละ instance กับ cache และเปิด AOF, ทำ graceful shutdown ของ worker และเฝ้าติดตาม queue lag กับจำนวน failed ต่อชั่วโมง
</details>

<details>
<summary><b>ทำไมงานที่ใช้ CPU หนักจึงต้องตั้ง concurrency ต่ำ</b></summary>

โครง: กลไก event loop → ผลที่เกิด → ตัวเลขแนะนำ → ทางเลือกเชิงสถาปัตยกรรม

เพราะ Node.js ประมวลผล JavaScript ด้วย **thread เดียว** ผ่าน event loop งานประเภท I/O เช่นการเรียก API หรือ query database จะปล่อยให้ event loop ไปทำงานอื่นระหว่างรอ แต่งานที่ใช้ CPU เช่นการสร้าง PDF หรือ resize รูปภาพจะ**ยึด event loop ไว้จนกว่าจะทำเสร็จ**

ผลคือหากตั้ง concurrency สูงสำหรับงาน CPU-bound งานหลายชิ้นจะแย่ง event loop เดียวกัน ทำให้ทุกชิ้นช้าลงพร้อมกัน และที่แย่กว่านั้นคือหาก worker อยู่ใน process เดียวกับ API งานเหล่านั้นจะทำให้ทุก request ค้างไปด้วย

ค่าที่แนะนำจึงเป็น concurrency 1–2 สำหรับงาน CPU-bound, 5–20 สำหรับงาน I/O-bound เช่นการส่งอีเมลหรือเรียก API และ 20–50 สำหรับงานที่เบามาก

หากต้องการ throughput มากขึ้นสำหรับงาน CPU-bound วิธีที่ถูกต้องคือ**เพิ่มจำนวน process ไม่ใช่เพิ่ม concurrency** เช่นใช้ `pm2 -i 4` ซึ่งได้ 4 process แยกกันโดยแต่ละตัวมี event loop ของตัวเอง และควรแยกคิวของงานหนักออกจากคิวงานเบา เพื่อไม่ให้งานประมวลผลวิดีโอไปขวางคิวอีเมล
</details>

<details>
<summary><b>ทำไมไม่ควรส่งข้อมูลขนาดใหญ่หรือไฟล์เป็น payload ของ job</b></summary>

โครง: job อยู่ที่ไหน → ผลกระทบ → ทางที่ถูก → ประโยชน์แถม

เพราะ **job ทั้งหมดถูกเก็บอยู่ใน Redis ซึ่งเป็น in-memory store** การส่งไฟล์หรือ buffer ขนาดหลายเมกะไบต์เข้าไปในคิวจึงหมายถึงการนำข้อมูลเหล่านั้นไปกองไว้ใน RAM หากมี job ลักษณะนี้หลักพันชิ้นในคิว Redis จะใช้ memory จนเต็มและเริ่ม evict ข้อมูล ซึ่งอาจทำให้ job หายไปเลย

สิ่งที่ควรทำคือส่ง **reference แทนตัวข้อมูล** เช่นส่ง `{ orderId: 123 }` หรือ `{ videoUrl: 's3://...' }` แล้วให้ worker ไปดึงข้อมูลจริงจาก database หรือ object storage  *((ที่เก็บไฟล์ก้อนใหญ่อย่าง S3 ไม่ใช่ DB))* เอง

ประโยชน์ที่ได้เพิ่มคือ worker จะอ่าน**ข้อมูลล่าสุด ณ เวลาที่ประมวลผลจริง** ไม่ใช่ข้อมูล ณ เวลาที่ enqueue ซึ่งอาจเก่าไปแล้วหากงานรออยู่ในคิวเป็นเวลานาน

ข้อควรระวังเพิ่มเติมคือ หากต้องเปลี่ยนรูปร่างของ payload ต้องคำนึงว่ามี job รูปแบบเก่าค้างอยู่ในคิวแล้ว จึงต้องเขียน handler ให้รองรับทั้งสองรูปแบบไว้อย่างน้อยหนึ่ง release ก่อนจะถอดแบบเก่าออก ซึ่งเป็นหลักการเดียวกับ expand-and-contract ของการเปลี่ยน schema
</details>

<details>
<summary><b>ควรทำงานใดแบบ synchronous และงานใดแบบ asynchronous จงอธิบายเกณฑ์และผลกระทบ</b></summary>

โครง: เกณฑ์ → ตัวอย่างสองฝั่ง → ผลด้าน latency → ผลด้าน resilience (สำคัญกว่า) → ข้อแลกเปลี่ยน

เกณฑ์คือ **หากงานใช้เวลาเกินประมาณ 1 วินาที หรือผลลัพธ์ไม่จำเป็นต้องใช้ทันที ให้ทำแบบ asynchronous**

สิ่งที่ต้องทำแบบ synchronous คือสิ่งที่ผู้ใช้ต้องทราบผลทันทีเพื่อดำเนินการต่อได้ เช่นการบันทึก order และคืนหมายเลข order การตรวจสอบสิทธิ์ และการ validate ข้อมูล ส่วนสิ่งที่ควรเป็น asynchronous คือการส่งอีเมลยืนยัน การส่ง SMS การสร้างไฟล์ PDF การประมวลผลรูปภาพหรือวิดีโอ และการส่งข้อมูลไปยังระบบวิเคราะห์

ผลกระทบด้านแรกคือ latency  *((เวลาที่ 1 request ใช้ตอบกลับ ต่างจาก throughput ที่นับงานต่อวินาที))* จากตัวอย่างที่ทำทุกอย่างแบบ synchronous ซึ่งใช้เวลารวมราว 8 วินาที เมื่อย้ายงานที่ไม่จำเป็นออกไปจะเหลือเพียงหลักสิบมิลลิวินาที

ผลกระทบด้านที่สองสำคัญกว่าและมักตอบไม่ถึง คือ **ความทนทานต่อความล้มเหลว** เมื่อทำแบบ synchronous ระบบของเราจะล้มเหลวตามทุกครั้งที่บริการภายนอกล้มเหลว ผู้ใช้จะเห็น error ทั้งที่ order ถูกสร้างสำเร็จไปแล้ว จากนั้นเขาจะกดซ้ำจนเกิด order ซ้ำ แต่เมื่อย้ายไปเป็น asynchronous ความล้มเหลวของ SendGrid จะไม่กระทบการสร้าง order เลย และ job จะถูก retry โดยอัตโนมัติเมื่อบริการกลับมาทำงาน

ข้อแลกเปลี่ยนที่ต้องยอมรับคือระบบซับซ้อนขึ้น ต้องมี worker เพิ่ม ต้องมี Redis ที่ทนทาน ต้องเฝ้าติดตามคิว และที่สำคัญที่สุดคือ**ทุก handler ต้อง idempotent** เพราะการรับประกันเป็นแบบ at-least-once นอกจากนี้ผู้ใช้จะไม่เห็นผลลัพธ์ทันที จึงต้องออกแบบ UX ให้สื่อสารว่างานกำลังดำเนินการอยู่

ข้อควรระวังเชิงลำดับคือต้อง enqueue **หลังจาก transaction commit สำเร็จแล้วเท่านั้น** ไม่ใช่ภายใน transaction เพราะหาก transaction ถูก rollback  *((ย้อนคืนทุกอย่างเหมือนไม่เคยทำ))* แต่ job ถูกส่งไปแล้ว worker จะทำงานกับข้อมูลที่ไม่มีอยู่จริง
</details>

## 9. ✅ เช็คตัวเองก่อนปิดบท

- ตอบได้ทันทีว่า pub/sub กับ queue ต่างกันตรงไหน และเลือกยังไง
- อธิบายได้ว่าทำไม exactly-once **เป็นไปไม่ได้** (สไลด์เขียนผิด) โดยเล่าเป็นลำดับเหตุการณ์
- เขียน handler แบบ idempotent ได้ และรู้ว่าตัวรับประกันสุดท้ายอยู่ที่ไหน
- แยก transient (4xx) กับ permanent (5xx) ได้ และรู้ว่าทำผิดแล้วเกิดอะไร
- บอกได้ว่าทำไม CPU-bound ต้อง concurrency 1–2
- รู้ว่าทำไม pub/sub + 3 instance = อีเมล 3 ฉบับ
