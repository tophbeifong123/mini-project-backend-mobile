# Backend 04 — Redis: Caching & Atomic Operations

> บทนี้ตอบคำถามเดียว: **ทำยังไงให้ DB ไม่ตายเพราะโดนถามคำถามเดิมซ้ำ ๆ วินาทีละหมื่นครั้ง โดยที่ข้อมูลไม่เก่าเกินรับได้**

### 📌 หัวข้อหลักในบทนี้:
- **Cache-aside / Write-through / Write-behind (อ่านไม่เจอค่อยไปเอาจาก DB / เขียน cache กับ DB พร้อมกัน / เขียน cache ก่อนแล้วค่อยลง DB)**
- **TTL + Jitter (อายุของข้อมูลใน cache + สุ่มบวกลบกันหมดอายุพร้อมกัน)**
- **Invalidation (ล้างของเก่าใน cache เมื่อข้อมูลจริงเปลี่ยน)**
- **Stampede / Avalanche (คีย์เดียวหมดอายุแล้วแห่ไป DB พร้อมกัน / หลายคีย์หมดอายุพร้อมกันทั้งชุด)**
- **INCR / Atomic (คำสั่งเดียวจบ ไม่มีใครแทรกกลางคัน)**
- **Distributed Lock (ล็อกข้ามหลายเครื่อง ให้มีแค่ตัวเดียวทำงานนั้น)**
- **Eviction Policy (memory เต็มแล้วจะเลือกลบคีย์ไหนทิ้ง)**

## 0. จุดที่เรื่องเดินมาถึง

Flash Sale ตัดสต็อกถูกต้องแล้ว (บท 03) แต่พอเปิดขายจริง **DB ตายก่อนที่จะมีใครกดซื้อทัน**

เพราะคนห้าพันคนเปิดหน้า product พร้อมกันแล้วรีเฟรชรัว ๆ ทุกครั้งคือ query เดิมเป๊ะ ๆ วิ่งไปที่ DB — และคำตอบก็เหมือนกันทุกครั้งด้วย

> 🎯 **ความคิดตั้งต้นของทั้งบท**
> Cache คือการ **"จำคำตอบของคำถามที่ถูกถามบ่อย ไว้ในที่ที่ตอบได้เร็ว"**
>
> DB ต้องอ่านจากดิสก์แล้วประมวลผล query ประมาณ 100ms ส่วน Redis  *((ที่เก็บข้อมูลใน RAM ใช้จำคำตอบไว้ตอบแทน DB))* อ่านจาก RAM ประมาณ 1ms ต่างกันราว 100 เท่า
>
> แต่ทันทีที่เก็บสำเนาข้อมูลไว้สองที่ เราก็ได้ปัญหาใหม่มาฟรี ๆ คือ **"สองที่ไม่ตรงกัน"** ซึ่งครึ่งหนึ่งของบทนี้คือการจัดการปัญหานั้น

### Redis คืออะไรกันแน่

Redis เป็น **in-memory key-value store** พูดง่าย ๆ คือ "ตู้เก็บของที่มีป้ายชื่อ" ที่วางอยู่ใน RAM ไม่ใช่ดิสก์ เราสั่ง `SET product:1 "{...}"` แล้ว `GET product:1` ก็ได้กลับมา ไม่มีตาราง ไม่มี JOIN ไม่มี query language ซับซ้อน

และมันเป็น **single-threaded** คือประมวลผลคำสั่งทีละคำสั่งเรียงกันไป

> 🧠 **2 คุณสมบัตินี้อธิบายเกือบทุกอย่างในบทนี้**
> - **อยู่ใน RAM** → เร็วมาก แต่ RAM แพงกว่าดิสก์เยอะ → เลยต้องมี TTL  *((อายุของข้อมูลใน cache ครบเวลาแล้วหายเอง))*, ต้อง cache เฉพาะข้อมูลที่ร้อนจริง ๆ และต้องมี eviction policy  *((กฎว่าพอ RAM เต็มแล้วจะเตะ key ไหนออกก่อน))*
> - **Single-threaded** → คำสั่งเดียวเป็น atomic  *((ทำจบในทีเดียว ไม่มีใครแทรกกลางคันได้))* โดยธรรมชาติ (เลยใช้ `INCR`  *((บวกเลขให้ตัวนับ จบในคำสั่งเดียว))* และทำ distributed lock  *((กุญแจกลางที่วางไว้นอกเครื่อง ให้หลายเครื่องถือได้ทีละตัว))* ได้) แต่ก็แปลว่า **คำสั่งช้าตัวเดียวบล็อกทั้ง server** (เลยห้ามใช้ `KEYS`)

## 1. ควร cache อะไร และไม่ควร cache อะไร

| ควร cache | ไม่ควร cache |
| --- | --- |
| ข้อมูลที่อ่านบ่อยกว่าเขียนมาก ๆ (read-heavy) | ข้อมูลที่เขียนบ่อยกว่าอ่าน เพราะจะ invalidate  *((สั่งล้าง cache ตัวเก่าทิ้งเมื่อข้อมูลจริงเปลี่ยน))* จนไม่เหลือประโยชน์ |
| query ที่แพง เช่น JOIN หลายตาราง หรือ aggregate | ข้อมูลที่เปลี่ยนตลอดเวลา |
| ข้อมูลกึ่งนิ่ง เช่น product, category, config | ข้อมูลที่ต้องถูกต้อง 100% เสมอ เช่น **ยอดเงินคงเหลือ, สต็อกที่ใช้ตัดขาย** |
| endpoint ที่ร้อนที่สุด 10 อันดับแรก | ข้อมูลที่ผู้ใช้แต่ละคนไม่ซ้ำกันเลย เพราะ hit ratio  *((สัดส่วนคำขอที่หาเจอใน cache))* จะต่ำมาก |

**วัดผลด้วย hit ratio:** `hits / (hits + misses)` เป้าหมายคือเกิน **80%** ถ้าต่ำกว่านั้นแปลว่าเรากำลังจ่ายค่า RAM และความซับซ้อนโดยแทบไม่ได้อะไรกลับมา ให้ย้อนไปดูว่า cache ผิดของ หรือ TTL สั้นเกินไป

> 🔗 **🔗 สำคัญมาก — อย่าสับสนระหว่างบท 03 กับ 04**
> **Cache แก้ปัญหา "ช้า" ไม่ได้แก้ปัญหา "ผิด"**
>
> สต็อกที่เอาไปโชว์หน้าเว็บ → cache ได้ (เห็นเลขคลาดไปนิดหน่อยไม่เป็นไร)
>
> สต็อกที่ใช้ตัดตอนกดซื้อ → **ต้องอ่านจาก DB ภายใต้ lock เท่านั้น**  *((lock = จองข้อมูลไว้ ไม่ให้คนอื่นเข้ามาแก้พร้อมกัน))* (บท 03)
>
> ถ้าเอา cache ไปตัดสต็อก จะได้ oversell  *((ขายเกินจำนวนที่มีจริง))* กลับมาเหมือนเดิม เพราะ cache ไม่มี transaction  *((กลุ่มคำสั่ง DB ที่ต้องสำเร็จทั้งหมดหรือไม่เกิดอะไรเลย))* ไม่มี lock ไม่มี constraint

## 2. Cache Strategy 3 แบบ

### 2.1 Cache-Aside (Lazy Loading)  *((ถาม cache ก่อน ไม่เจอค่อยไป DB แล้วเก็บคำตอบกลับเข้า cache))* — ตัวหลักที่ใช้จริง

> 📊 **แผนภาพ: เส้นทางปกติจบแค่ ①→②ก — DB โดนแตะเฉพาะตอน miss  *((หาใน cache ไม่เจอ ต่างจาก hit ที่เจอแล้วตอบได้เลย))* เท่านั้น**
>
> *ข้อความ/ลำดับในแผนภาพ:*
> - App
> - (NestJS)
> - Redis
> - RAM
> - ~1 ms
> - PostgreSQL
> - ดิสก์
> - ~100 ms
> - ① GET product:1
> - ②ก มีอยู่ (HIT) → คืนเลย จบ
> - ②ข ไม่มี (MISS)
> - ③ MISS เท่านั้นถึงจะไป DB
> - ④ SET + TTL (พร้อม jitter)
> - ครั้งแรกช้าเสมอ (cold) แต่ครั้งที่ 2 เป็นต้นไปจบที่ Redis · ถ้า Redis ล่ม เส้น ③ ก็ยังทำงานได้ ระบบแค่ช้าลง
> - ทุกการเรียก Redis ต้องอยู่ใน try/catch ที่ fallback ไป DB ได้

```typescript
async getProduct(id: string) {
  const key = `product:${id}`;
  const cached = await this.redis.get(key);
  if (cached) return JSON.parse(cached);        // HIT

  const product = await this.repo.findOne({ where: { id } });   // MISS → ไป DB
  await this.redis.set(key, JSON.stringify(product), 'EX', 300);
  return product;
}
```

**ข้อดี:** เก็บเฉพาะข้อมูลที่มีคนขอจริง ๆ และถ้า Redis ล่ม ระบบยังทำงานได้เพราะยัง fallback  *((ถอยไปใช้ทางสำรอง))* ไป DB ได้

**ข้อเสีย:** request แรกช้าเสมอ (cold) และมีความเสี่ยงเรื่อง stampede  *((คีย์ดังหมดอายุพอดีตอนคนแห่เข้ามา เลย miss พร้อมกันทั้งหมด))* (ดูข้อ 4)

### 2.2 Write-Through

เขียน DB แล้วอัปเดต cache ทันทีในจังหวะเดียวกัน → cache สดใหม่หลังเขียนเสมอ

**แลกกับ:** write latency  *((เวลาที่การเขียน 1 ครั้งใช้จนตอบกลับ))* สูงขึ้นเพราะต้องทำสองที่ และเปลือง cache กับข้อมูลที่อาจไม่มีใครอ่านเลย

### 2.3 Write-Behind (Write-Back)

เขียนลง cache ก่อนแล้วตอบผู้ใช้ทันที ค่อยทยอย flush  *((เทของที่ค้างอยู่ลง DB จริง))* ลง DB ทีหลัง → write เร็วที่สุด

> ⚠️ **อันตราย — ต้องพูดถึงถ้าข้อสอบถาม**
> **ถ้า Redis ล่มก่อน flush ข้อมูลหายจริง** ใช้ได้เฉพาะข้อมูลที่หายแล้วไม่เดือดร้อน เช่น counter จำนวนวิว หรือ analytics — **ห้ามใช้เด็ดขาดกับ payment, order, auth**

|  | Cache-Aside | Write-Through | Write-Behind |
| --- | --- | --- | --- |
| Read latency | ดี (หลัง warm) | ดี | ดี |
| Write latency | ปกติ | ช้าลง | เร็วที่สุด |
| ความสดของข้อมูล | อาจ stale  *((ค่าเก่าค้างอยู่ ไม่ตรงกับ DB))* ตาม TTL | สดหลังเขียน | DB ตามหลัง cache |
| เสี่ยงข้อมูลหาย | ไม่ | ไม่ | **ใช่** |
| ใช้เมื่อ | **read-heavy ทั่วไป** | ต้องสดทันทีหลังเขียน | counter / analytics เท่านั้น |

## 3. TTL และ Invalidation — จุดที่ทำให้ระบบพัง

### 3.1 ทุก key ต้องมี TTL ไม่มีข้อยกเว้น

> 🧠 **เหตุผล 2 ชั้น**
> **ชั้นที่ 1:** key ที่ไม่มี TTL คือ **memory leak**  *((กินหน่วยความจำเพิ่มไปเรื่อย ๆ ไม่มีคืน))* — มันอยู่ไปเรื่อย ๆ จน Redis ชน `maxmemory`  *((เพดาน RAM ที่ตั้งให้ Redis ใช้ได้))* แล้วเริ่ม evict ซึ่งอาจไปเตะข้อมูลที่ยังใช้อยู่ออก
>
> **ชั้นที่ 2 (สำคัญกว่า):** TTL คือ **ตาข่ายนิรภัยของ invalidation** ต่อให้เขียน invalidation ดีแค่ไหน ก็จะมีจังหวะที่มันพลาดเสมอ เช่น process ตายกลางคัน หรือลืม invalidate key ที่เกี่ยวข้องบางตัว TTL คือสิ่งที่รับประกันว่า *ข้อมูลเก่าจะหายไปเองภายในเวลาที่กำหนด* ไม่ใช่ค้างอยู่ตลอดกาล

| ประเภทข้อมูล | TTL แนะนำ |
| --- | --- |
| เปลี่ยนบ่อย (สต็อกที่แสดงผล, ราคาโปรโมชัน) | 30 วินาที – 5 นาที |
| กึ่งนิ่ง (โปรไฟล์, รายละเอียดสินค้า) | 10 นาที – 1 ชั่วโมง |
| นิ่ง (หมวดหมู่, config, รายชื่อประเทศ) | 1 – 24 ชั่วโมง |

### 3.2 Invalidation ต้องล้างทั้งสาย

```typescript
async updateUser(id, dto) {
  await this.repo.update(id, dto);
  await this.redis.del(
    `user:${id}`,          // ตัวมันเอง
    `user:${id}:posts`,    // ของที่ประกอบขึ้นจากมัน
    `users:list`,          // list ที่มันอยู่ในนั้น
  );
}
```

คนมักลืมข้อ 2 กับ 3 ผลคือหน้ารายละเอียดอัปเดตแล้ว แต่หน้า list ยังโชว์ชื่อเก่า บั๊กแบบนี้หายากมากเพราะโค้ดดูเหมือนถูกต้องแล้ว

**ตั้งชื่อ key ให้เป็นระบบ:** `{namespace}:{entity}:{id}:{field}`  *((namespace = คำนำหน้าบอกว่า key นี้ของแอปไหน กันชนกับระบบอื่นที่ใช้ Redis ตัวเดียวกัน))* เช่น `app:user:42:posts` และควรมี **key-builder ตัวกลาง** ไม่ใช่ต่อ string เอาเองกระจายทั่วโค้ด เพราะพิมพ์ผิดที่เดียวคือได้ cache ที่ไม่มีวันถูก invalidate

### 3.3 ลำดับการเขียนกับการลบ

ให้ **update DB ก่อน แล้วค่อย DEL cache** ไม่ใช่ DEL ก่อนแล้วค่อย update เพราะถ้า DEL ก่อน จะมีช่องให้ request อื่นเข้ามาอ่าน DB ค่าเก่าแล้วเขียนกลับเข้า cache พอดี

แต่ต้องรู้ด้วยว่า**ลำดับไหนก็ยังมี race เหลืออยู่**  *((race condition = สองคำขอเข้ามาพร้อมกันแล้วแย่งข้อมูลก้อนเดียวกันจนผลเพี้ยน))* เลยต้องมี TTL สั้นคุมไว้ หรือใช้เทคนิค delayed double-delete  *((ลบ cache ซ้ำอีกรอบหลังหน่วงเวลา กันค่าเก่าที่แอบเขียนกลับเข้ามา))* ในระบบที่ซีเรียส

## 4. Cache Stampede & Avalanche

> 📊 **แผนภาพ: สองอันนี้คนละปัญหาและแก้คนละวิธี — stampede แก้ด้วย lock, avalanche แก้ด้วย jitter  *((สุ่มบวกลบเวลานิดหน่อย กันทุกตัวมาพร้อมกันเป๊ะ))***
>
> *ข้อความ/ลำดับในแผนภาพ:*
> - Stampede — คีย์เดียว คนเยอะ
> - Avalanche — คีย์เป็นหมื่น หมดพร้อมกัน
> - product:hot ✕
> - หมดอายุพอดี
> - 5,000 request กำลังขอคีย์นี้อยู่
> - DB
> - ทุกคน miss พร้อมกัน → ยิง query เดียวกันพร้อมกัน
> - แก้: ให้คนเดียวถือ lock ไปเติม cache ที่เหลือรอ
> - TTL เท่ากันหมด
> - ระเบิด
> - พร้อมกัน
> - TTL + jitter สุ่ม
> - หมดอายุกระจายกันไป โหลดที่ DB เรียบขึ้น

### 4.1 Stampede (แห่เข้าคีย์เดียว)

key ยอดฮิตหมดอายุพอดีตอนมีคน 5,000 คนขออยู่ → ทั้งหมด miss พร้อมกัน → ทั้งหมดยิง query เดิมไป DB พร้อมกัน → **DB ตาย**

ทางแก้คือให้ **คนเดียวไปเติม cache** ที่เหลือรอ โดยใช้ distributed lock (ข้อ 6)

> 🛑 **⚠ สไลด์เขียนทางแก้ผิด**
> สไลด์แก้ stampede โดยเรียก `return this.getPopularPost()` ตัวเอง**ซ้ำแบบไม่มีขอบเขต** ถ้าคนที่ถือ lock ตายไป คนที่เหลือจะวนเรียกตัวเองจน stack overflow  *((เรียกตัวเองซ้อนลึกจนหน่วยความจำ stack เต็ม แล้วโปรแกรมตาย))*
>
> ทางที่ถูกคือ **retry loop ที่จำกัดจำนวนครั้ง + backoff + ถ้าครบแล้วยังไม่ได้ให้ fallback ไปอ่าน DB ตรง ๆ**  *((backoff = ลองใหม่โดยเว้นระยะห่างขึ้นเรื่อย ๆ ไม่ถล่มซ้ำทันที))*

### 4.2 Avalanche (หมดอายุพร้อมกันเป็นกอง)

ตอน deploy หรือ warm-up  *((โหลดข้อมูลใส่ cache ล่วงหน้าก่อนเปิดใช้จริง))* เรา set key พร้อมกัน 10,000 ตัวด้วย TTL 300 เท่ากันหมด อีก 5 นาทีข้างหน้ามันจะ**หมดอายุพร้อมกันทั้งหมด** แล้ว DB โดนถล่มเป็นระลอก

```typescript
// ✅ ใส่ jitter — สุ่มบวกเข้าไป ไม่ให้หมดอายุตรงกัน
const ttl = 300 + Math.floor(Math.random() * 60);   // 300–360 วินาที
await redis.set(key, value, 'EX', ttl);
```

> 🧠 **jitter คือหลักการเดียวกันทั้งวิชา**
> บท 03 retry deadlock ต้องมี jitter / บท 04 TTL ต้องมี jitter / บท 05 retry job ต้องมี jitter
>
> เหตุผลเดียวกันหมด: **อะไรก็ตามที่ทำพร้อมกันเป๊ะ ๆ จะกลับมาชนกันเป็นระลอกซ้ำ ๆ** jitter คือการจงใจทำให้มันไม่ตรงกัน

### 4.3 Redis ต้องเป็นตัวเลือก ไม่ใช่ตัวบังคับ

```typescript
async getProduct(id: string) {
  try {
    const cached = await this.redis.get(key);
    if (cached) return JSON.parse(cached);
  } catch (e) {
    this.logger.warn('cache read failed, falling back to DB', e);
  }
  return this.repo.findOne({ where: { id } });   // ยังทำงานได้แม้ Redis ล่ม
}
```

> ⚠️ **ประโยคที่ควรเขียนลงในข้อสอบ**
> **Cache คือการ optimize ถ้าระบบพังเมื่อ cache ล่ม แปลว่าเราเพิ่งใส่ single point of failure เข้าไปในระบบโดยไม่ตั้งใจ**  *((จุดเดียวที่ถ้าพังแล้วลากทั้งระบบล้มตาม))*
>
> ทุกการเรียก cache ต้องอยู่ใน try/catch ที่ fallback ไป DB ได้

## 5. Atomic Operations

### 5.1 ทำไม get → +1 → set ถึงผิด

```typescript
// ❌ race condition แบบเดียวกับบท 03 เป๊ะ ๆ
const count = await redis.get('views:1');
await redis.set('views:1', Number(count) + 1);

// ✅ คำสั่งเดียว เป็น atomic เพราะ Redis เป็น single-threaded
await redis.incr('views:1');
```

สังเกตว่านี่คือ **read-check-write**  *((อ่านค่ามาก่อน ค่อยตัดสินใจแล้วเขียนกลับ — มีช่องว่างให้คนอื่นแทรก))* รูปแบบเดียวกับ oversell ในบท 03 เป๊ะ ๆ พอเป็น 3 instance  *((ตัวสำเนาของแอปที่รันอยู่จริง 1 ตัว))* (บท 06) ยิ่งชนกันหนักขึ้นไปอีก การใช้ `INCR` คือการให้ Redis ทำทั้งหมดในคำสั่งเดียว จึงไม่มีช่องว่างให้ใครแทรก

### 5.2 คำสั่งที่ควรรู้

- `INCR` / `INCRBY` — counter (จำนวนวิว, rate limit)  *((rate limit = จำกัดจำนวนครั้งที่ยิงได้ต่อช่วงเวลา))*
- `SET key value EX 300 NX` — เขียนเฉพาะเมื่อยังไม่มี key นี้ (พื้นฐานของ lock)
- `SCAN` — ไล่ดู key ทีละชุด

> ⚠️ **ห้ามใช้ `KEYS` ใน production เด็ดขาด**
> `KEYS pattern` เป็น O(N)  *((เวลาที่ใช้โตตามจำนวน key ทั้งหมดที่มี))* และเพราะ Redis เป็น **single-threaded** มันจะ**บล็อกทั้ง server** ระหว่างที่ไล่ดูทุก key — ทุก request ของทุกคนค้างหมดพร้อมกัน ให้ใช้ `SCAN` ที่แบ่งทำเป็นชุด ๆ หรือดีกว่านั้นคือเก็บ index ไว้ใน SET เอง
>
> **⚠ สไลด์มีตัวอย่างที่เรียก `redis.keys(pattern)` ทั้งที่ comment ของตัวเองเขียนไว้ว่าให้ใช้ SCAN**

## 6. Distributed Lock

บท 03 เราใช้ DB lock ได้เพราะทุกอย่างอยู่ใน DB เดียว แต่ถ้าต้องกันไม่ให้ **งานหนึ่งถูกทำซ้ำจาก 3 instance พร้อมกัน** (เช่น cron  *((งานตั้งเวลาให้รันเองเป็นรอบ ๆ))* ที่รันทุกเครื่อง หรือ "ใครสักคนไปเติม cache") ก็ต้องมี lock ที่อยู่นอกทั้งสามเครื่อง = Redis

```typescript
const token = randomUUID();                                  // ① token เฉพาะตัว
const ok = await redis.set(key, token, 'EX', 10, 'NX');       // ② NX + TTL

if (!ok) return;   // มีคนถืออยู่
try {
  await doWork();
} finally {
  // ③ ปล่อยด้วย Lua: เทียบ token ก่อนลบ (เป็นคำสั่งเดียว atomic)
  await redis.eval(
    `if redis.call("get",KEYS[1])==ARGV[1] then return redis.call("del",KEYS[1]) else return 0 end`,
    1, key, token,
  );
}
```

> 📊 **แผนภาพ: A ลบ lock ที่ไม่ใช่ของตัวเอง เพราะ `DEL` ไม่รู้ว่าใครเป็นเจ้าของ — จึงต้องมี token  *((รหัสสุ่มประจำตัวคนถือ lock ไว้พิสูจน์ว่าเป็นเจ้าของจริง))* ประจำตัวและเทียบก่อนลบ**
>
> *ข้อความ/ลำดับในแผนภาพ:*
> - ถ้าปล่อย lock ด้วย DEL เฉย ๆ (ไม่เทียบ token) จะเกิดแบบนี้
> - Worker A
> - ได้ lock 🔒
> - TTL 10 วินาที
> - งานช้ากว่าที่คิด…
> - TTL หมดตอนนี้ (lock หลุด)
> - ทำเสร็จ → สั่ง DEL
> - ลบ lock ของ B ทิ้ง!
> - Worker B
> - ได้ lock 🔒 (ว่างแล้ว)
> - เริ่มทำงาน
> - Worker C
> - เข้ามาได้เลย
> - ทำซ้อนกับ B
> - เวลา →
> - แก้ด้วย: เทียบ token ก่อนลบ ผ่าน Lua script (เพื่อให้เป็นคำสั่งเดียว)

| องค์ประกอบ | ถ้าไม่มีจะเกิดอะไร |
| --- | --- |
| **TTL บังคับ** | worker ที่ถือ lock crash → **lock ค้างตลอดกาล** ไม่มีใครทำงานนั้นได้อีกเลย |
| **token เฉพาะตัว + ปล่อยด้วย Lua** | เกิดเหตุการณ์ตามรูปด้านบน การแยก `GET` แล้วค่อย `DEL` ก็ยังมีช่องว่างระหว่างสองคำสั่ง จึงต้องรวมเป็น Lua script  *((สคริปต์สั้น ๆ ที่ Redis รันรวดเดียวจบ จึงเป็น atomic))* เดียว |
| **`try/finally`** | งาน throw แล้ว lock ไม่ถูกปล่อย ต้องรอ TTL หมดเอง |
| **heartbeat / extendLock**  *((ส่งสัญญาณต่ออายุ lock เป็นระยะระหว่างที่ยังทำงานอยู่))* | งานยาวกว่า TTL → lock หลุดกลางคันทั้งที่ยังทำอยู่ |

> ⚠️ **ข้อจำกัดที่ต้องรู้ (ตอบข้อนี้ได้คะแนนพิเศษ)**
> **Distributed lock เป็น best-effort ไม่ใช่การรับประกัน**  *((best-effort = พยายามให้ดีที่สุด แต่ไม่การันตี 100%))* — GC pause  *((จังหวะที่ Node หยุดทุกอย่างไปเก็บขยะหน่วยความจำ))* ของ Node หรือ clock drift  *((นาฬิกาของแต่ละเครื่องเดินไม่ตรงกัน))* ทำให้ process เชื่อว่ายังถือ lock อยู่ทั้งที่ TTL หมดไปแล้ว
>
> ดังนั้น **ความถูกต้องต้องมาจาก idempotency + unique constraint ที่ DB**  *((idempotency = ทำซ้ำกี่รอบผลก็เท่าเดิม / unique constraint = กฎที่ DB บังคับว่าห้ามมีค่าซ้ำ))* ส่วน lock มีไว้แค่ "ลดการทำงานซ้ำ" เท่านั้น (Redlock  *((สูตรทำ lock พร้อมกันข้าม Redis หลายตัว))* เองก็ยังเป็นที่ถกเถียงในเชิงวิชาการ และถ้าจะใช้ instance ต้องแยกกันจริง ๆ ไม่ใช่ primary กับ replica  *((ตัวสำเนาที่ก๊อปข้อมูลตามตัวหลัก))* ของกันเอง)
>
> ประโยคนี้เชื่อมตรงไปยังบท 05 เรื่อง **at-least-once + idempotent handler**  *((at-least-once = job อาจถูกส่งซ้ำได้ ตัวรับงานเลยต้องกันซ้ำเอง))*

> 🛑 **⚠ สไลด์บทนี้ผิดหลายจุด**
> 1. `cache.set(lockKey,'1',{ttl:10,nx:true})` — `Cache` ของ `@nestjs/cache-manager` **ไม่มี option `nx`** ต้องใช้ ioredis  *((ไลบรารีที่คุยกับ Redis ตรง ๆ จาก Node))* ตรง ๆ: `set(k,v,'EX',10,'NX')`
> 2. `cache.ttl(key)` ก็ไม่มีเช่นกัน ต้องใช้ `redis.ttl`
> 3. ตัวอย่างปล่อย lock ด้วย `cache.del(lockKey)` เฉย ๆ โดยไม่เทียบ token — **ขัดกับหัวข้อ lock ของสไลด์เอง** และลบ lock ของคนอื่นได้ตามรูปด้านบน
> 4. `finally { releaseLock(key, token) }` อ้าง `token` ที่อาจเป็น undefined ถ้าตอน acquire โยน error ต้องเช็ค `if (token)` ก่อน
> 5. ตัวอย่าง cache-aside ครอบ `cache.set` ไว้ใน try เดียวกับการอ่าน DB ทำให้ถ้า cache write พัง จะไป query DB ซ้ำอีกรอบใน catch ควรครอบ try เฉพาะส่วนที่คุยกับ cache
> 6. `this.userRepo.findOne(id)` เป็น API ของ TypeORM  *((ORM ของ Node — ตัวแปลงระหว่าง object ในโค้ดกับตารางใน DB))* 0.2 ที่ถูกถอดออกไปแล้ว ให้ใช้ `findOne({ where: { id } })` ตามบท 03
> 7. สไลด์ไม่พูดถึง Redis HA  *((High Availability — มีตัวสำรองพร้อมขึ้นแทนเมื่อตัวหลักล่ม))* เลย ทั้งที่ Redis เดี่ยวเป็น SPOF  *((ย่อจาก single point of failure))* ของ session

## 7. Memory & Operations

### 7.1 maxmemory + eviction policy

เพราะ RAM มีจำกัด เราต้องบอก Redis ล่วงหน้าว่า "ถ้าเต็มแล้วให้ทำยังไง"

| Policy | ทำอะไร | ใช้เมื่อ |
| --- | --- | --- |
| `allkeys-lru`  *((LRU = ดูว่าใครถูกใช้ครั้งล่าสุดนานสุด))* | เตะ key ที่ไม่ถูกใช้นานที่สุดออก ไม่ว่าจะมี TTL หรือไม่ | ใช้เป็น cache ล้วน ๆ |
| `volatile-lru` | เตะเฉพาะ key ที่มี TTL | ปนกันระหว่าง cache กับข้อมูลที่ต้องอยู่ |
| `noeviction` | ไม่เตะอะไรเลย พอเต็มก็ error | ข้อมูลสำคัญที่หายไม่ได้ |

> ⚠️ **กับดักที่โยงไปบท 05 โดยตรง**
> ถ้าใช้ Redis ตัวเดียวกันทั้งเป็น **cache** และเป็น **queue (BullMQ)**  *((ไลบรารีคิวงานของ Node ที่เก็บคิวไว้ใน Redis))* แล้วตั้ง `allkeys-lru` ไว้ พอ memory เต็ม Redis จะ **เตะ job ในคิวทิ้ง** เพราะมันมองว่าเป็น key ที่ไม่ถูกใช้นาน = งานของผู้ใช้หายเงียบ ๆ โดยไม่มี error ให้เห็น
>
> **ต้องแยก instance หรืออย่างน้อยแยก database index ระหว่าง cache กับ queue เสมอ**  *((database index ของ Redis = เลขช่อง 0–15 ที่แบ่งพื้นที่กัน ไม่ใช่ index ของตาราง))*

### 7.2 สิ่งที่ต้อง monitor

- `keyspace_hits` / `keyspace_misses` → เอามาคำนวณ hit ratio
- `used_memory` → ใกล้ `maxmemory` หรือยัง
- `evicted_keys` → ถ้าพุ่ง แปลว่า memory ไม่พอและกำลังทิ้งข้อมูลที่ยังใช้อยู่
- `SLOWLOG GET 10` → หาคำสั่งที่ไปบล็อก server

**ข้ออื่น ๆ:** ใช้ connection ซ้ำ อย่าเปิดใหม่ทุก request · value ที่ใหญ่เกิน 1MB ให้แยกหรือบีบอัด · Redis เดี่ยวเป็น SPOF ของ session ต้องวางแผน Sentinel  *((ตัวเฝ้าดู คอยดัน replica ขึ้นเป็นตัวหลักเมื่อตัวหลักล่ม))* หรือใช้ managed Redis  *((Redis ที่เช่าคลาวด์ให้เขาดูแลให้))*

## 9. 📝 คลังคำตอบอัตนัย

<details>
<summary><b>Cache-aside คืออะไร มีข้อดีข้อเสียอย่างไร เทียบกับ write-through และ write-behind</b></summary>

โครง: อธิบายกลไกทีละแบบ → เทียบ 3 มิติ (latency / freshness / ความเสี่ยง) → บอกว่าเลือกอันไหนเมื่อไร

**Cache-aside** หรือ lazy loading คือแอปพลิเคชันอ่านจาก cache ก่อน หากพบข้อมูล (hit) ก็คืนค่าทันที หากไม่พบ (miss) จึงไปอ่านจาก database แล้วนำผลลัพธ์ไปเขียนลง cache พร้อมกำหนด TTL ก่อนคืนค่า ข้อดีคือ cache เก็บเฉพาะข้อมูลที่มีผู้ขอจริง และหาก Redis ล่มระบบยังทำงานต่อได้เพราะสามารถ fallback ไป database ได้ ข้อเสียคือ request แรกช้าเสมอเพราะ cache ยังว่าง และมีความเสี่ยงเรื่อง cache stampede

**Write-through** คือเมื่อมีการเขียนข้อมูล จะเขียนลง database แล้วอัปเดต cache ทันทีในจังหวะเดียวกัน ทำให้ cache สดใหม่เสมอหลังการเขียน แต่ write latency สูงขึ้นเพราะต้องดำเนินการสองที่ และอาจสิ้นเปลือง memory กับข้อมูลที่ไม่มีผู้ใดอ่าน

**Write-behind** คือเขียนลง cache ก่อนแล้วตอบผู้ใช้ทันที จากนั้นจึงทยอย flush ลง database แบบ asynchronous ทำให้ write latency ต่ำที่สุด แต่มีความเสี่ยงร้ายแรงคือ **หาก Redis ล่มก่อน flush ข้อมูลจะสูญหายจริง** จึงใช้ได้เฉพาะข้อมูลที่ยอมให้สูญหายได้ เช่น counter จำนวนการเข้าชมหรือข้อมูล analytics และห้ามใช้กับ payment, order หรือ authentication โดยเด็ดขาด

โดยทั่วไปจึงเลือก cache-aside เป็นค่าเริ่มต้นสำหรับงาน read-heavy เพราะให้ความปลอดภัยและความเรียบง่ายมากที่สุด
</details>

<details>
<summary><b>Cache stampede และ cache avalanche คืออะไร ต่างกันอย่างไร และแก้อย่างไร</b></summary>

โครง: นิยามทั้งคู่ + ความต่าง → ทางแก้ของแต่ละอัน → ข้อควรระวังของทางแก้

**Cache stampede** คือกรณีที่ key ยอดนิยม*ตัวเดียว*หมดอายุในขณะที่มี request จำนวนมากกำลังขอข้อมูลนั้นอยู่ ทำให้ทุก request เกิด miss พร้อมกันและวิ่งไป query database ตัวเดียวกันพร้อมกันทั้งหมด ซึ่งอาจทำให้ database ล่มได้

วิธีแก้คือให้มีเพียง request เดียวที่ได้ไป query database และเติม cache โดยใช้ **distributed lock** ผ่านคำสั่ง `SET key token EX ttl NX` ส่วน request ที่เหลือให้รอแล้วลองอ่าน cache ใหม่ ข้อควรระวังคือการรอนั้นต้องเป็น **loop ที่จำกัดจำนวนครั้งพร้อม backoff และมี fallback ไปอ่าน database โดยตรงเมื่อครบกำหนด** ไม่ใช่การเรียกฟังก์ชันตัวเองซ้ำแบบไม่มีขอบเขต เพราะหากผู้ถือ lock เกิดล่มไป request ที่เหลือจะวนไม่สิ้นสุดจนเกิด stack overflow

**Cache avalanche** ต่างออกไปตรงที่เป็นปัญหาของ key *จำนวนมาก* ที่หมดอายุพร้อมกัน มักเกิดหลังการ deploy หรือ warm-up ที่มีการ set key นับหมื่นตัวด้วย TTL เท่ากันในเวลาไล่เลี่ยกัน เมื่อถึงเวลา key ทั้งหมดจะหมดอายุพร้อมกันและ database ถูกถล่มเป็นระลอก

วิธีแก้คือ **เติม jitter แบบสุ่มลงใน TTL** เช่นใช้ค่า 300 บวกกับเลขสุ่ม 0 ถึง 60 วินาที เพื่อกระจายเวลาหมดอายุออกจากกัน ซึ่งเป็นหลักการเดียวกับที่ใช้ใน retry ของ deadlock ในบท 03 และ retry ของ job ในบท 05 คือสิ่งใดก็ตามที่เกิดขึ้นพร้อมกันเป๊ะจะกลับมาชนกันซ้ำเป็นระลอก
</details>

<details>
<summary><b>ทำไมทุก cache key ต้องมี TTL ทั้งที่เราเขียน invalidation ไว้ครบแล้ว</b></summary>

โครง: เหตุผลด้าน memory → เหตุผลด้าน correctness (สำคัญกว่า) → สรุปบทบาทของทั้งสองกลไก

เหตุผลแรกเป็นเรื่อง memory เนื่องจาก Redis เก็บข้อมูลใน RAM ซึ่งมีจำกัดและมีต้นทุนสูงกว่าดิสก์มาก key ที่ไม่มี TTL จะคงอยู่ไปเรื่อย ๆ กลายเป็น memory leak จนกระทั่ง Redis ชน `maxmemory` แล้วเริ่มทำ eviction ซึ่งอาจไปลบข้อมูลที่ยังจำเป็นออกแทน

เหตุผลที่สองสำคัญกว่าและเป็นเรื่องความถูกต้อง คือ **TTL ทำหน้าที่เป็นตาข่ายนิรภัยของ invalidation** ไม่ว่าจะเขียน invalidation รอบคอบเพียงใด ก็จะมีจังหวะที่พลาดเสมอ เช่น process ล่มระหว่างลบ key, ลืม invalidate key ที่ประกอบขึ้นจากข้อมูลนั้น เช่นลบ `user:1` แต่ลืม `users:list` หรือเกิด race ระหว่างการเขียน database กับการลบ cache

ในกรณีเหล่านั้น หากไม่มี TTL ข้อมูลเก่าจะค้างอยู่ใน cache ตลอดกาลโดยไม่มีผู้ใดทราบ แต่หากมี TTL ความเสียหายจะถูกจำกัดอยู่เพียงช่วงเวลาที่กำหนดไว้เท่านั้น

สรุปคือทั้งสองกลไกทำหน้าที่คนละอย่าง **invalidation ทำให้ข้อมูลสดเร็ว** ส่วน **TTL รับประกันว่าข้อมูลเก่าจะไม่ค้างตลอดไป** จึงต้องมีทั้งคู่ และควรกำหนด TTL ตามความถี่ในการเปลี่ยนแปลงของข้อมูล เช่น 30 วินาทีถึง 5 นาทีสำหรับข้อมูลที่เปลี่ยนบ่อย และหลายชั่วโมงสำหรับข้อมูลที่แทบไม่เปลี่ยน
</details>

<details>
<summary><b>จงอธิบายวิธีทำ distributed lock ด้วย Redis ให้ถูกต้อง พร้อมบอกว่าแต่ละองค์ประกอบป้องกันอะไร</b></summary>

โครง: คำสั่งหลัก → อธิบายทีละองค์ประกอบว่ากันอะไร → ข้อจำกัดที่ต้องยอมรับ

คำสั่งหลักคือ `SET lockKey  EX 10 NX` โดย `NX` ทำให้เขียนสำเร็จก็ต่อเมื่อยังไม่มี key นี้อยู่ ซึ่งเป็น atomic เพราะ Redis เป็น single-threaded ผู้ที่เขียนสำเร็จคือผู้ที่ได้ lock

**TTL** เป็นสิ่งที่ขาดไม่ได้ เพราะหาก worker ที่ถือ lock เกิดล่มโดยไม่ได้ปล่อย lock นั้นจะค้างอยู่ตลอดกาลและไม่มีผู้ใดทำงานนั้นได้อีกเลย

**token ที่ไม่ซ้ำกันของแต่ละผู้ถือ** ใช้ควบคู่กับการปล่อย lock ผ่าน Lua script ที่เปรียบเทียบ token ก่อนลบ เหตุผลคือ หากใช้ `DEL` เฉย ๆ จะเกิดกรณีที่ process A ทำงานช้าจน TTL หมด, process B ได้ lock ไปแล้ว, จากนั้น A ทำงานเสร็จแล้วสั่ง `DEL` ซึ่งกลายเป็นการ**ลบ lock ของ B** ทำให้ process ที่สามเข้ามาได้และเกิดการทำงานซ้อนกัน การแยกเป็น `GET` แล้วเปรียบเทียบแล้วจึง `DEL` ก็ยังคงมีช่องว่างระหว่างสองคำสั่ง จึงต้องรวมเป็น Lua script เดียวเพื่อให้เป็น atomic

นอกจากนี้ต้องปล่อย lock ใน `finally` เพื่อให้ปล่อยแม้เกิด exception และควรตรวจสอบว่า token มีค่าจริงก่อนปล่อย เผื่อกรณีที่การขอ lock ล้มเหลวตั้งแต่ต้น ส่วนงานที่อาจใช้เวลานานกว่า TTL ต้องมีกลไก heartbeat เพื่อต่ออายุ lock ระหว่างทำงาน

ข้อจำกัดสำคัญที่ต้องยอมรับคือ **distributed lock เป็นเพียง best-effort ไม่ใช่การรับประกันความถูกต้อง** เพราะ GC pause หรือ clock drift อาจทำให้ process เชื่อว่ายังถือ lock อยู่ทั้งที่หมดอายุไปแล้ว ดังนั้นความถูกต้องที่แท้จริงต้องมาจาก **การออกแบบให้ operation เป็น idempotent และมี unique constraint ที่ database** โดยให้ lock ทำหน้าที่เพียงลดการทำงานซ้ำเท่านั้น
</details>

<details>
<summary><b>ทำไมห้ามใช้คำสั่ง `KEYS` ใน production</b></summary>

โครง: โยงกับสถาปัตยกรรมของ Redis → ผลที่เกิด → ทางเลือก

เพราะ `KEYS pattern` มีความซับซ้อน O(N) คือต้องไล่ตรวจ key ทุกตัวใน database และที่สำคัญกว่านั้นคือ **Redis เป็น single-threaded** จึงประมวลผลได้ทีละคำสั่งเท่านั้น

ผลคือระหว่างที่ `KEYS` ทำงานอยู่ คำสั่งอื่นทั้งหมดจากทุก client จะถูกบล็อกไว้ บน Redis ที่มี key หลักล้านตัวอาจใช้เวลาเป็นวินาที ซึ่งหมายความว่าทุก request ในระบบที่ต้องพึ่ง cache จะค้างพร้อมกันหมด กลายเป็น outage ที่เราสร้างขึ้นเอง

ทางเลือกคือใช้ `SCAN` ซึ่งทำงานเป็นชุดย่อยพร้อม cursor  *((ตัวคั่นหน้าว่าไล่ถึงไหนแล้ว รอบหน้าไปต่อจากตรงนั้น))* จึงไม่บล็อก server แม้จะไม่รับประกันภาพ snapshot  *((ภาพนิ่งของข้อมูลทั้งก้อน ณ วินาทีเดียว))* ที่สมบูรณ์ หรือทางที่ดีกว่าคือ**ออกแบบไม่ให้ต้องค้นหา key ตั้งแต่แรก** โดยเก็บรายการ key ที่เกี่ยวข้องไว้ใน SET ของตัวเอง แล้วอ่าน SET นั้นเมื่อต้อง invalidate เป็นกลุ่ม
</details>

<details>
<summary><b>ถ้า Redis ล่ม ระบบควรมีพฤติกรรมอย่างไร และควรออกแบบโค้ดอย่างไร</b></summary>

โครง: หลักการ → โค้ด → ผลที่ยอมรับได้ → เชื่อมกับกรณีที่ Redis ไม่ใช่แค่ cache

หลักการคือ **cache เป็นการ optimize ไม่ใช่ dependency ที่ขาดไม่ได้** ระบบต้องทำงานต่อได้เมื่อ Redis ล่ม เพียงแต่ช้าลง หากระบบล่มตามไปด้วย แสดงว่าเราได้เพิ่ม single point of failure เข้าไปโดยไม่ตั้งใจ

ในทางปฏิบัติคือทุกการเรียก cache ต้องอยู่ใน `try/catch` ที่เมื่อเกิด error จะบันทึก log ไว้แล้ว **fallback ไปอ่านจาก database** แทน ไม่ใช่โยน error ออกไปยังผู้ใช้ และควรครอบ try เฉพาะส่วนที่ติดต่อกับ cache เท่านั้น ไม่ปะปนกับการอ่าน database เพื่อไม่ให้เกิดการ query ซ้ำโดยไม่ตั้งใจเมื่อการเขียน cache ล้มเหลว

ผลที่ยอมรับได้คือ latency สูงขึ้นและภาระที่ database เพิ่มขึ้นชั่วคราว จึงต้องเผื่อ capacity ของ database ไว้ระดับหนึ่งสำหรับกรณีนี้

ข้อควรระวังคือหลักการนี้ใช้ได้เฉพาะเมื่อ Redis ทำหน้าที่เป็น cache เท่านั้น หากเราเก็บ **session** หรือ **queue** ไว้ใน Redis ด้วย ข้อมูลเหล่านั้นไม่มีที่ให้ fallback Redis จะกลายเป็น single point of failure จริง ๆ จึงต้องวางแผน high availability ด้วย Sentinel หรือใช้ managed Redis และควรแยก instance ระหว่าง cache กับ queue เพราะ eviction policy แบบ `allkeys-lru` จะลบ job ในคิวทิ้งเมื่อ memory เต็ม
</details>

<details>
<summary><b>ระบบขายสินค้าจำกัดจำนวน ควรใช้ Redis cache เก็บจำนวนสต็อกเพื่อลดภาระ DB หรือไม่</b></summary>

โครง: แยกสองการใช้งานของ "สต็อก" ให้ชัด → ตอบคนละแบบ → เหตุผลเชิงกลไก

ต้องแยกให้ชัดก่อนว่า "สต็อก" ถูกใช้ในสองบริบทที่มีข้อกำหนดต่างกันโดยสิ้นเชิง

**สต็อกสำหรับแสดงผลบนหน้าเว็บ** สามารถ cache ได้และควร cache ด้วย เพราะเป็นงาน read-heavy อย่างมาก และการที่ผู้ใช้เห็นตัวเลขคลาดเคลื่อนไปเล็กน้อยในช่วงไม่กี่วินาทีนั้นยอมรับได้ ควรกำหนด TTL สั้นประมาณ 30 วินาทีถึง 1 นาทีพร้อม jitter

**สต็อกที่ใช้ตัดตอนกดซื้อจริง** **ห้ามใช้ cache โดยเด็ดขาด** ต้องอ่านจาก database ภายใต้ transaction และ pessimistic lock  *((ล็อกแถวไว้ตั้งแต่ตอนอ่าน ไม่ให้ใครแตะจนกว่าจะเสร็จ))* ตามบท 03

เหตุผลเชิงกลไกคือ cache ไม่มี transaction ไม่มี lock และไม่มี constraint การอ่านค่าจาก cache แล้วตัดสินใจขายก็คือรูปแบบ **read-check-write** ที่มีช่องว่างของเวลาแบบเดียวกับที่ทำให้เกิด oversell ตั้งแต่แรก และร้ายแรงกว่าเดิมเพราะค่าใน cache อาจเก่ากว่าความเป็นจริงด้วย

หลักการสรุปคือ **cache แก้ปัญหาเรื่องความช้า ไม่ได้แก้ปัญหาเรื่องความถูกต้อง** สิ่งที่ต้องถูกต้องเสมอต้องมาจาก database ที่มีคุณสมบัติ ACID  *((คุณสมบัติ 4 ข้อที่การันตีว่า transaction จะไม่ทำข้อมูลเพี้ยน))* เท่านั้น

เพิ่มเติมคือ ก่อนตัดสินใจใส่ cache ควรตรวจสอบก่อนว่า query ที่ช้านั้นมี index ครบและไม่มีปัญหา N+1 หรือไม่ เพราะการวาง cache ทับ query ที่เขียนไม่ดีเป็นเพียงการซ่อนปัญหาไว้ และจะปรากฏขึ้นทันทีที่เกิด cache miss
</details>

## 10. ✅ เช็คตัวเองก่อนปิดบท

- อธิบายได้ว่า "single-threaded" ของ Redis ทำให้เกิดทั้ง*ข้อดี* (atomic) และ*ข้อห้าม* (KEYS) ยังไง
- บอกได้ว่า TTL มีไว้ 2 เหตุผล ไม่ใช่เหตุผลเดียว
- แยก stampede กับ avalanche ออกจากกันได้ และรู้ว่าแก้คนละวิธี
- เขียน distributed lock ได้ครบทั้ง NX + TTL + token + Lua release และเล่าบั๊ก "ลบ lock ของคนอื่น" ได้
- ตอบได้ทันทีว่า "เอา cache ไปตัดสต็อกได้ไหม" พร้อมเหตุผล
- รู้ว่าทำไมต้องแยก Redis ของ cache กับของ queue
