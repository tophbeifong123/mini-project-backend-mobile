# Backend 03 — Database Engineering

> บทนี้ตอบคำถามเดียว: **ทำยังไงให้ข้อมูลถูกต้องเมื่อมีคนใช้พร้อมกันเป็นพัน และเปลี่ยนโครงสร้างตารางได้โดยไม่ทำข้อมูลหาย**

### 📌 หัวข้อหลักในบทนี้:
- **TypeORM / Data Mapper (ตัวแปลงระหว่าง object ในโค้ดกับตารางใน DB)**
- **Migration (ไฟล์เวอร์ชันของโครงสร้างตาราง DB ที่รันตามลำดับได้)**
- **ACID (คุณสมบัติ 4 ข้อที่การันตีว่ากลุ่มคำสั่ง DB จะไม่ทำข้อมูลเพี้ยน)**
- **Race Condition (สองคำขอเข้ามาพร้อมกันแล้วแย่งข้อมูลก้อนเดียวกันจนผลเพี้ยน)**
- **Pessimistic vs Optimistic Lock (ล็อกกันไว้ก่อน vs ปล่อยให้ชนแล้วค่อยตรวจตอนเขียน)**
- **Deadlock (สองฝ่ายรอ lock ของกันและกันจนค้างทั้งคู่)**
- **N+1 (ยิง query ซ้ำทีละแถวจนกลายเป็นร้อยรอบ)**
- **Connection Pool (ถังเก็บ connection DB ไว้ใช้ซ้ำ ไม่ต้องเปิดใหม่ทุกครั้ง)**

## 0. จุดที่เรื่องเดินมาถึง

Flash Sale เปิดขาย iPhone ราคาถูก มีของ **100 เครื่อง** โค้ดเราเขียนไว้แบบนี้:

```typescript
async buy(productId: string) {
  const p = await this.repo.findOne({ where: { id: productId } });
  if (p.stock < 1) throw new BadRequestException('ของหมด');   // ① อ่านและตรวจ
  p.stock -= 1;
  await this.repo.save(p);                                     // ② เขียน
  return this.orderRepo.save({ productId });
}
```

ทดสอบคนเดียวผ่านฉลุย พอขึ้น production เปิดขาย 10 วินาทีแรกมีคนกด 5,000 คน ผลคือ **ขายไป 130 เครื่อง ทั้งที่มีของ 100** แถมไม่มี error สักตัวใน log ให้ตามด้วย

> 🎯 **ทำไมมันพัง**
> ระหว่างบรรทัด ① กับ ② มี**ช่องว่างของเวลา** ในช่องว่างนั้นมี request อีก 30 ตัวที่อ่านค่า `stock` ตัวเดียวกันไปแล้ว ทุกตัวเลยผ่าน `if` ไปได้หมด แล้วมาเขียนทับกันเป็น `stock = 0`
>
> รูปแบบ **"อ่าน → ตรวจ → เขียน" (read-check-write)** คือหน้าตาของ race condition ทุกตัวในโลก บทนี้คือวิธีปิดช่องว่างนั้น

> 📊 **แผนภาพ: สังเกตว่าไม่มีขั้นตอนไหนผิดเลยสักขั้นเมื่อดูทีละ request — มันผิดเพราะสองอันนี้ทำงานสลับกันอยู่**
>
> *ข้อความ/ลำดับในแผนภาพ:*
> - Race condition: ทั้งสอง request อ่านค่าเดียวกันก่อนที่ใครจะเขียน
> - Request A
> - SELECT stock
> - ได้ 1
> - if (1 < 1) ?
> - ผ่าน
> - UPDATE
> - stock = 0
> - Request B
> - ได้ 1 ← ค่าเดิม!
> - เวลา →
> - ขายไป 2 เครื่อง แต่ stock ลดแค่ 1
> - คูณด้วย 5,000 request ก็ได้ 130 จาก 100
> - ช่องว่างระหว่าง "อ่าน" กับ "เขียน" คือรูรั่ว
> - ปิดได้ 2 ทาง: ล็อกช่วงนั้น หรือรวมเป็นคำสั่งเดียว

## 1. ปูพื้นฐาน: ORM คืออะไร แลกอะไร

ORM (Object-Relational Mapping) ทำหน้าที่แปลง object ใน TypeScript ↔ แถวในตาราง SQL ให้อัตโนมัติ เราเขียน `repo.findOne(...)` แทนที่จะต่อ SQL string เอง

| ได้อะไร | แลกอะไร |
| --- | --- |
| type safety + auto-complete + refactor แล้วชื่อตามไปเอง | **abstraction leak**  *((ของที่ ORM ซ่อนไว้ โผล่ทะลุออกมาให้เห็นอยู่ดี))* — ตอน tune performance ยังต้องรู้ SQL อยู่ดี |
| ไม่ต้องต่อ SQL string เอง กัน SQL injection ได้ระดับหนึ่ง | สร้าง SQL ที่แย่ได้ง่ายมาก (N+1, cartesian join  *((JOIN ที่ทำให้แถวคูณกันจนบานปลาย))*) ทั้งที่โค้ดดูสวย |
| entity  *((คลาสในโค้ดที่แทน 1 ตารางใน DB))* + repository  *((ตัวกลางที่รับหน้าที่อ่าน/เขียน entity ลง DB))* + migration อยู่ในระบบเดียวกัน | มี overhead จากการแปลงแถวเป็น object |

**Data Mapper vs Active Record:** TypeORM ใช้ Data Mapper เป็นหลัก คือ entity เป็นข้อมูลล้วน ๆ ส่วน repository เป็นคนรับผิดชอบเรื่องการบันทึก เหมาะกับแอปใหญ่เพราะแยกความรับผิดชอบชัด (ตรงกับชั้น Repository ในบท 02) ส่วน Active Record คือ entity มี `.save()` ติดมาในตัว เหมาะกับ CRUD ง่าย ๆ

> 🧠 **ประโยคที่ต้องพูดได้**
> ORM **ซ่อน SQL ไว้ แต่ไม่ได้ทำให้ SQL หายไป** — ยังต้องเปิด `logging: true` ใน dev เพื่อดูว่ามันยิงอะไรออกไปจริง ๆ และใช้ `EXPLAIN ANALYZE`  *((สั่งให้ DB โชว์ว่าจริง ๆ มันหา query นี้ยังไง ใช้เวลาเท่าไร))* กับ query ที่ช้า

## 2. Migration — version control ของ schema  *((โครงสร้างตารางกับคอลัมน์ของ DB))*

### 2.1 `synchronize: true` คือความเสี่ยงอันดับหนึ่งของบทนี้

`synchronize: true` สั่งให้ TypeORM "ทำให้ schema ในฐานข้อมูลตรงกับ entity" ซึ่งฟังดูสะดวกดี แต่คำว่า "ตรงกัน" รวมถึง **`DROP COLUMN` และ `DROP TABLE`** ด้วย

> ⚠️ **สถานการณ์จริง**
> เราลบ field `phoneNumber` ออกจาก entity เพราะไม่ใช้แล้ว → TypeORM เห็นว่า DB มีคอลัมน์นี้แต่ entity ไม่มี → สั่ง `ALTER TABLE users DROP COLUMN phone_number` → **เบอร์โทรของผู้ใช้ทุกคนหายถาวร** ไม่มีการถาม ไม่มี backup ไม่มีคำเตือน
>
> นี่ไม่ใช่ downtime ที่รอเดี๋ยวก็กลับมา แต่เป็น **data loss** ที่กู้ไม่ได้ถ้าไม่มี backup

ทางที่ถูกคือ `synchronize: false` เสมอ แล้วใช้ migration ทุก environment

### 2.2 กฎของ migration

| กฎ | เหตุผล |
| --- | --- |
| เขียนทั้ง `up()` และ `down()`  *((คำสั่งย้อนสิ่งที่ up() ทำ))* แล้ว**ทดสอบ revert จริง** | ถ้า deploy แล้วพังตอนตี 2 ต้อง rollback  *((ย้อน DB กลับไปสถานะก่อนหน้า))* ได้ทันที ไม่ใช่มานั่งเขียน SQL แก้สดตอนนั้น |
| **ห้ามแก้ migration ที่ deploy ไปแล้ว** | migration ที่รันแล้วถูกบันทึกไว้ในตาราง `migrations` การไปแก้ไฟล์เก่าทำให้ environment ที่รันไปแล้วกับที่ยังไม่รัน **มี schema ต่างกันถาวร** เรียกว่า schema drift ซึ่งหาสาเหตุยากมาก |
| 1 migration = 1 การเปลี่ยนแปลงเชิงตรรกะ | review ง่าย rollback แม่นยำ และหาตัวที่ทำพังได้เร็ว |
| อ่าน migration ที่ generate มา**ก่อน commit เสมอ** | generator เดาจาก diff ของ entity — การ *rename* คอลัมน์มักถูกตีความเป็น `DROP` แล้ว `CREATE` ใหม่ ซึ่งข้อมูลหาย |
| รัน migration เป็น **job แยกก่อน deploy app** | ถ้ารันตอน app boot แล้วมี 3 instance  *((ตัวสำเนาของแอปที่กำลังรันอยู่จริง 1 ตัว))* ขึ้นพร้อมกัน (บท 06) ทั้งสามจะแย่งกันรัน migration ตัวเดียวกัน |
| ทดสอบบน**สำเนาข้อมูลจริง** | migration ที่ผ่านฉลุยบน DB เปล่า อาจใช้เวลา 40 นาทีและล็อกตารางบน DB จริงที่มี 50 ล้านแถว |

### 2.3 Migration ที่ล็อกตาราง

`ALTER TABLE orders ADD COLUMN status VARCHAR NOT NULL DEFAULT 'pending'` ดูไม่มีพิษภัย แต่บน PostgreSQL รุ่นเก่ามันจะ **เขียนตารางใหม่ทั้งตาราง** และถือ `ACCESS EXCLUSIVE`  *((ล็อกแรงสุด ห้ามแม้แต่คนที่จะมาอ่าน))* lock ระหว่างนั้น ผลคือ API ค้างทั้งระบบ

> 🧠 **รูปแบบปลอดภัย (จำโครงนี้)**
> 1. เพิ่มคอลัมน์เป็น **nullable** ก่อน — เร็ว ไม่ต้องเขียนตารางใหม่
> 2. **backfill ทีละ batch**  *((ไล่เติมค่าให้แถวเก่าที่ยังว่างอยู่))* ครั้งละหมื่นแถว
> 3. ค่อยเติม `NOT NULL` constraint  *((กฎที่ DB บังคับเองว่าข้อมูลต้องเป็นแบบไหน))* ทีหลัง

### 2.4 Expand-and-Contract

ปัญหาคือ ตอน rolling update  *((ทยอยเปลี่ยน instance ทีละตัว ไม่ดับทั้งระบบ))* จะมีโค้ดสองเวอร์ชันรันพร้อมกันเสมอ (บท 06) ถ้า migration ลบคอลัมน์ไปแล้ว แต่ instance เก่ายังอ่านคอลัมน์นั้นอยู่ ก็ 500 ทันที

| ระยะ | ทำอะไร |
| --- | --- |
| **Expand** | เพิ่มของใหม่เข้าไป โดยยังไม่ลบของเก่า (มีทั้งสองคอลัมน์อยู่ด้วยกัน) |
| **Migrate** | deploy โค้ดที่**อ่านได้ทั้งเก่าและใหม่** และเขียนลงทั้งสองที่ |
| **Contract** | release ถัดไปค่อยลบของเก่า เมื่อแน่ใจแล้วว่าไม่มี instance เก่าเหลืออยู่ |

## 3. Transaction & ACID

### 3.1 Transaction คืออะไรจริง ๆ

Transaction คือการบอก database ว่า "คำสั่งกลุ่มนี้ให้นับเป็นก้อนเดียว" หน้าตาจริง ๆ ของมันคือ:

```typescript
BEGIN;                                    -- เปิดก้อน
  UPDATE products SET stock = stock - 1 WHERE id = 'x';
  INSERT INTO orders (...) VALUES (...);
COMMIT;                                   -- ปิดก้อน ยืนยันทั้งหมด
-- หรือ ROLLBACK; ถ้าอยากยกเลิกทั้งก้อน
```

ระหว่าง `BEGIN` กับ `COMMIT` คนอื่นจะยังมองไม่เห็นสิ่งที่เราทำ และถ้าเกิดอะไรผิดพลาดก็ `ROLLBACK` ให้ทุกอย่างกลับไปเหมือนไม่เคยเกิดขึ้น

### 3.2 ACID ทีละตัว

| ตัวอักษร | ความหมาย | ถ้าไม่มีจะเป็นยังไงในระบบเรา |
| --- | --- | --- |
| **A**tomicity | ทำหมดหรือไม่ทำเลย | ตัดสต็อกสำเร็จ แต่สร้าง order ไม่สำเร็จ → ของหายไปเฉย ๆ |
| **C**onsistency | constraint ถูกบังคับเสมอ | `stock` ติดลบได้ / order ชี้ไปหา product ที่ไม่มีอยู่จริง |
| **I**solation | transaction ไม่กวนกัน | คนอื่นเห็นข้อมูลครึ่ง ๆ กลาง ๆ ที่ยังไม่ commit |
| **D**urability | commit แล้วอยู่ถาวร | ไฟดับแล้ว order ที่ยืนยันไปแล้วหายไป |

### 3.3 กฎเหล็ก 3 ข้อ

#### ① transaction ต้องสั้นที่สุด

ยิ่งเปิดนาน ยิ่งถือ lock นาน คนอื่นก็รอ แถม connection ใน pool ถูกจองค้าง และโอกาสเกิด deadlock ก็สูงขึ้น

#### ② ห้ามเรียก external API / ส่งอีเมล / ตัดบัตรใน transaction

> ⚠️ **เหตุผล 2 ชั้น — ต้องตอบให้ครบทั้งคู่**
> **ชั้นที่ 1 (performance):** HTTP call ใช้เวลา 5–30 วินาที ระหว่างนั้น DB ถือ lock ค้างไว้ทั้งหมด
>
> **ชั้นที่ 2 (correctness — ข้อนี้สำคัญกว่า):** ถ้า transaction rollback ทีหลัง เรา **"ยกเลิกอีเมลที่ส่งออกไปแล้ว" ไม่ได้** และ "คืนเงินที่ตัดบัตรไปแล้ว" ก็ทำไม่ได้ด้วยการ rollback เพราะ side effect  *((ผลข้างเคียงที่เกิดนอก DB เช่นอีเมลที่ส่งไปแล้ว))* ที่เกิดข้างนอกไม่ได้อยู่ในขอบเขตของ transaction
>
> ทางแก้: **โยนเข้า queue แทน**  *((queue = ที่พักงาน ให้ worker ซึ่งเป็นโปรเซสแยก มาหยิบไปทำทีหลัง))* แล้วให้ worker ทำหลัง commit สำเร็จ → นี่คือเหตุผลตรง ๆ ที่ทำให้บท 05 มีอยู่

#### ③ ต้องใช้ `manager`  *((ตัวจัดการ DB ของ transaction ก้อนนั้นโดยเฉพาะ))* ที่ transaction ส่งมาให้

```typescript
await this.dataSource.transaction(async (manager) => {
  await manager.save(order);        // ✅ อยู่ใน transaction
  await this.repo.save(payment);    // ❌ วิ่งนอก transaction เงียบ ๆ ไม่ถูก rollback
});
```

บั๊กนี้หายากมาก เพราะโค้ดดูถูกต้องทุกอย่าง ไม่มี error ให้เห็น และจะโผล่ก็ต่อเมื่อเกิด rollback จริงเท่านั้น

### 3.4 Isolation Level  *((ตั้งว่า transaction ที่รันพร้อมกันจะมองเห็นงานของกันมากแค่ไหน))*

| Level | ป้องกันอะไร | ใช้เมื่อไร |
| --- | --- | --- |
| READ UNCOMMITTED | แทบไม่ป้องกันอะไร (อ่าน dirty data  *((= dirty read คืออ่านของที่อีกฝั่งยังไม่ commit แล้วอาจ rollback ทีหลัง))* ได้) | แทบไม่ใช้ |
| **READ COMMITTED** | ไม่อ่านข้อมูลที่ยังไม่ commit | **ค่าเริ่มต้นของ PostgreSQL ใช้อันนี้เป็นหลัก** |
| REPEATABLE READ | อ่านซ้ำใน transaction เดียวได้ค่าเดิมเสมอ | รายงานที่ต้องอ่านหลายตารางให้เห็นภาพ ณ เวลาเดียวกัน |
| SERIALIZABLE | เสมือนรันทีละ transaction | **เฉพาะธุรกรรมการเงิน** — แลกกับ throughput  *((จำนวนงานที่ระบบทำได้ต่อวินาที))* ที่ตกชัดเจน และมี serialization failure  *((DB ยอมแพ้แล้วสั่งให้ลองใหม่ เมื่อสองงานสลับกันไม่ลงตัว))* ที่ต้อง retry |

## 4. Race Condition & Locking — หัวใจของบทนี้

### 4.1 Lock คืออะไร

Lock คือป้าย "มีคนใช้อยู่" ที่ database แปะไว้บนแถว ใครมาขอแถวนั้นแบบที่จะแก้ไข ต้องรอจนกว่าเจ้าของป้ายจะ `COMMIT` หรือ `ROLLBACK`

สำคัญ: **lock ผูกกับ transaction ไม่ได้ผูกกับคำสั่ง** — มันถูกปล่อยตอนจบ transaction เท่านั้น นี่คือเหตุผลที่การ lock นอก transaction ไม่มีความหมายอะไรเลย

### 4.2 Pessimistic Lock (มองโลกในแง่ร้าย)

สมมติไว้ก่อนเลยว่า "ต้องมีคนแย่งแน่ ๆ" → **ล็อกแถวไว้ตั้งแต่ตอนอ่าน** ใครมาทีหลังต้องรอ

```typescript
await this.dataSource.transaction(async (manager) => {
  const p = await manager.findOne(Product, {
    where: { id },
    lock: { mode: 'pessimistic_write' },   // = SELECT ... FOR UPDATE
  });
  if (p.stock < 1) throw new BadRequestException('ของหมด');
  p.stock -= 1;
  await manager.save(p);
});   // ← lock ถูกปล่อยตอน COMMIT
```

> 📊 **แผนภาพ: หัวใจอยู่ที่ B ไม่ได้อ่านค่าเก่าไปคิดเอง แต่ถูกบังคับให้รออ่านค่าหลังสุด**
>
> *ข้อความ/ลำดับในแผนภาพ:*
> - Pessimistic lock: B ถูกบังคับให้รอจนกว่า A จะ COMMIT
> - Request A
> - SELECT … FOR UPDATE
> - ได้ 1 + ยึด lock 🔒
> - UPDATE
> - stock = 0
> - COMMIT
> - ปล่อย lock 🔓
> - Request B
> - SELECT … FOR UPDATE → ถูกบล็อก รออยู่ตรงนี้
> - (ยังไม่ได้อ่านค่าอะไรเลย)
> - ได้ lock แล้วอ่านใหม่
> - ได้ 0 → ตอบ "ของหมด"
> - เวลา →
> - B อ่านค่า หลัง A เขียนเสร็จ จึงเห็นความจริง — ช่องว่างที่เคยมีถูกปิดสนิท

> ⚠️ **2 จุดที่พลาดกันบ่อย**
> 1. **lock ต้องอยู่ใน transaction เดียวกับการเขียน** เพราะ lock ถูกปล่อยตอน COMMIT ถ้าอ่านนอก transaction แล้วไปเขียนใน transaction lock ไม่มีผลอะไรเลย
> 2. **สไลด์เขียนว่า `pessimistic_write` "blocks both reads and writes" ซึ่งผิดบน PostgreSQL** — เพราะ PostgreSQL ใช้ MVCC (แต่ละ transaction เห็น "ภาพถ่าย" ของข้อมูลคนละใบ) ทำให้ `SELECT` ธรรมดายังอ่านเวอร์ชันเก่าได้ตามปกติ `FOR UPDATE`  *((SELECT ที่จองแถวนั้นไว้จนจบ transaction))* บล็อกเฉพาะ `FOR UPDATE` / `FOR SHARE` / `UPDATE` / `DELETE` เท่านั้น

### 4.3 Optimistic Lock (มองโลกในแง่ดี)

สมมติไว้ว่า "คงไม่ค่อยมีใครแย่งหรอก" → ไม่ล็อกอะไรเลย แต่**ตรวจตอนจะเขียนว่ามีใครแก้ไปก่อนหรือเปล่า** โดยดูจาก `@VersionColumn` ที่เพิ่มขึ้นทุกครั้งที่ save

> 📊 **แผนภาพ: ไม่มีใครต้องรอ แต่คนที่มาช้าต้องยอมโหลดใหม่แล้วทำซ้ำ**
>
> *ข้อความ/ลำดับในแผนภาพ:*
> - Optimistic lock: ไม่ล็อก แต่ตรวจ version ตอนเขียน
> - A
> - อ่านเอกสาร version = 5
> - เขียน (ต้องยัง = 5)
> - สำเร็จ → version = 6
> - B
> - เขียน (คิดว่ายัง = 5)
> - affected = 0 → 409 Conflict
> - เวลา →
> - ไม่มีใครถูกบล็อกเลยระหว่างนี้ — B รู้ตัวก็ตอนจะเขียน

> 🛑 **⚠ สไลด์ 30 เขียนตัวอย่างผิด — ข้อนี้น่าจะเป็นข้อสอบ**
> `// ❌ แบบในสไลด์ — ยังมี race อยู่ (TOCTOU)
> const doc = await repo.findOne({ where: { id } });
> if (doc.version !== expectedVersion)          // ← ตรวจ
>   throw new ConflictException();
> doc.content = content;
> await repo.save(doc);                          // ← เขียน (ช่องว่างตรงนี้ยังมีคนแทรกได้)`
> การเช็ค version ด้วยมือแบบนี้**ไม่ใช่ optimistic locking จริง** — มันคือ read-check-write อีกรอบ แค่ย้ายที่เท่านั้นเอง
>
> `// ✅ แบบที่ถูก — ให้ DB ตรวจในคำสั่งเดียวแบบ atomic
> const r = await repo.update({ id, version: expectedVersion }, { content });
> if (r.affected === 0) throw new ConflictException('Document was modified');`
> หรือปล่อยให้ TypeORM ตรวจเองผ่าน `@VersionColumn` แล้วดัก `OptimisticLockVersionMismatchError`

### 4.4 เลือกอันไหน

|  | Pessimistic | Optimistic |
| --- | --- | --- |
| **ใช้เมื่อ** | ชนกันบ่อย, งานสำคัญที่ผิดไม่ได้ | ชนกันนาน ๆ ที, ผู้ใช้เปิดฟอร์มค้างนาน |
| **ตัวอย่าง** | สต็อก Flash Sale, ที่นั่งคอนเสิร์ต, ยอดเงินในบัญชี | แก้เอกสาร, แก้โปรไฟล์, ระบบ CMS |
| **ข้อดี** | กันชนได้แน่นอน เขียน logic ง่าย | ไม่มี DB lock, scale ดี, ไม่มีใครต้องรอ |
| **ข้อเสีย** | ถือ lock = คนอื่นรอ, เสี่ยง deadlock, ไม่เหมาะกับ session ยาว | ต้องเขียน logic จัดการ conflict + UX บอกผู้ใช้ให้ refresh; ถ้าชนบ่อยจะ retry ไม่จบ |

> 🧠 **วิธีเลือกในหนึ่งประโยค**
> ถามว่า "โอกาสที่สองคนจะแก้แถวเดียวกันพร้อมกันมีมากแค่ไหน" — **บ่อย → pessimistic** (เพราะ optimistic จะ retry จนไม่จบ) / **นาน ๆ ที → optimistic** (เพราะ pessimistic จะทำให้คนรอฟรี ๆ)

### 4.5 Deadlock

> 📊 **แผนภาพ: สาเหตุคือ "วงกลมของการรอ" (circular wait) — ถ้าทำให้วงกลมเกิดไม่ได้ deadlock ก็เกิดไม่ได้**
>
> *ข้อความ/ลำดับในแผนภาพ:*
> - Transaction A
> - ถือ 🔒 User
> - Transaction B
> - ถือ 🔒 Account
> - แถว User
> - แถว Account
> - ต่างฝ่ายต่างขอของที่อีกฝ่ายถืออยู่
> - PostgreSQL ตรวจเจอวงกลมนี้ แล้ว ฆ่าตัวหนึ่งทิ้ง พร้อม error 40P01

| ป้องกัน | เหตุผล |
| --- | --- |
| **ล็อก resource ตามลำดับเดียวกันเสมอ** เช่นล็อก User ก่อน Account ทุกที่ | ถ้าทุกคนล็อกเรียงลำดับเหมือนกัน วงกลมจะเกิดขึ้นไม่ได้เลยตั้งแต่ต้น |
| retry เมื่อเจอ `40P01`  *((error code ของ PostgreSQL ที่แปลว่าเจอ deadlock))* ด้วย **exponential backoff + jitter**  *((รอนานขึ้นเรื่อย ๆ ก่อนลองใหม่ + สุ่มบวกลบเวลานิดหน่อย กันกลับมาชนพร้อมกันอีก))* | deadlock เป็นเรื่องปกติของระบบที่มี concurrency ไม่ใช่บั๊ก ตัวที่ถูกฆ่าควรลองใหม่ |

> 🛑 **⚠ สไลด์ใช้ `sleep(100)` คงที่**
> ถ้าทุก transaction ที่ชนกันรอ 100ms เท่ากันหมด มันจะ**กลับมาชนกันซ้ำที่จังหวะเดิม** ต้องใช้ exponential backoff (100ms → 200ms → 400ms) **บวก jitter แบบสุ่ม** เพื่อกระจายไม่ให้กลับมาพร้อมกัน — เป็นหลักการเดียวกับ retry ในบท 05 และ TTL jitter ในบท 04

## 5. Query Optimization

### 5.1 Index

ก่อนอื่น index คืออะไร: มันคือ**ดัชนีท้ายเล่มหนังสือ** ถ้าไม่มี เวลาจะหาคำว่า "transaction" ต้องเปิดอ่านทีละหน้าตั้งแต่ต้นจนจบ (นี่คือ full table scan) แต่ถ้ามีดัชนี ก็เปิดไปดูว่าอยู่หน้า 142 แล้วกระโดดไปเลย

บนตาราง 10 ล้านแถว ความต่างคือ 2ms กับ 8s

- สร้าง index บนทุกคอลัมน์ที่ใช้ใน **WHERE / JOIN / ORDER BY**  *((JOIN = ดึงหลายตารางมาต่อกันในคำสั่งเดียว))*
- แต่**ไม่ใช่ทุกคอลัมน์** เพราะ index ทำให้ write ช้าลงและกินพื้นที่ (ทุกครั้งที่เขียนต้องไปอัปเดตดัชนีด้วย)
- **Composite index มีกฎ left-most prefix:** index `(authorId, createdAt)` ใช้ได้กับ query ที่กรอง `authorId` หรือกรองทั้งคู่ แต่**ใช้ไม่ได้**กับ query ที่กรอง `createdAt` อย่างเดียว — เหมือนสมุดโทรศัพท์ที่เรียงตาม "นามสกุล แล้วชื่อ" หาจากนามสกุลได้ แต่หาจากชื่ออย่างเดียวไม่ได้

### 5.2 ปัญหา N+1

> 📊 **แผนภาพ: N+1 ไม่ได้แพงเพราะ query หนัก แต่แพงเพราะ "จำนวนรอบไป-กลับ" — ทุกรอบต้องรอ network**
>
> *ข้อความ/ลำดับในแผนภาพ:*
> - ❌ N+1 — 101 รอบ
> - ✅ JOIN — 1 รอบ
> - App
> - DB
> - หา user 100 คน
> - × อีก 100 ครั้ง (posts ของแต่ละคน)
> - แต่ละลูกศรมี network latency ของตัวเอง
> - ไม่กี่ ms กลายเป็นหลายวินาที
> - relations: ['posts']
> - = 1 JOIN
> - แต่ระวัง: JOIN ลึกหลายชั้นทำให้ข้อมูลซ้ำ
> - (cartesian product) ซึ่งอาจแย่กว่าเดิม

```typescript
// ❌ N+1
const users = await repo.find();
for (const u of users) u.posts = await postRepo.find({ where: { userId: u.id } });

// ✅ 1 query
const users = await repo.find({ relations: ['posts'] });
```

> ⚠️ **แต่ eager loading ก็มีกับดักของมัน**
> `relations: ['posts', 'posts.comments']`  *((eager loading = สั่งดึง relation มาพร้อมกันตั้งแต่แรก ต่างจาก lazy ที่ค่อยดึงตอนใช้))* บน user ที่มี 500 post คูณ 20 comment จะสร้าง **cartesian product** คือได้ 10,000 แถวที่ข้อมูล user ถูกทำซ้ำในทุกแถว กินทั้ง network และ memory มากกว่าเดิม
>
> ในกรณีแบบนี้ **ยิง 2 query แยกแล้ว map ในแอป (DataLoader pattern) เร็วกว่า**
>
> บทเรียนคือ "แก้ N+1 ด้วย relations" ไม่ใช่กฎสากล — มันคือการแลก *จำนวนรอบ* กับ *ปริมาณข้อมูลที่ดึงมา*

### 5.3 select และ pagination

- **ระบุ `select: [...]` เสมอ** — ลด I/O ลด payload และเปิดโอกาสให้ DB ใช้ index-only scan  *((ตอบได้จากดัชนีอย่างเดียว ไม่ต้องแตะตารางจริง))*
- **list endpoint ต้อง paginate เสมอ** — `find()` เปล่า ๆ บนตารางที่โตไม่จำกัด = OOM  *((โปรเซสถูกฆ่าเพราะใช้ RAM เกิน))* ของทั้ง process
- **offset ลึก ๆ ให้ใช้ keyset/cursor pagination**  *((เลื่อนหน้าด้วย "ค่าสุดท้ายที่อ่านไป" แทนการนับข้ามทีละแถว))* — เพราะ `OFFSET 100000` ยังต้องอ่านและทิ้ง 100,000 แถวแรกทุกครั้ง มันไม่ได้ "กระโดด" ไปอย่างที่ชื่อชวนให้คิด

### 5.4 `onDelete: 'CASCADE'` เป็นดาบสองคม

ลบ user คนเดียวอาจลบ post กับ comment เป็นแสนแถวโดยไม่มีใครรู้ตัว และ **rollback ไม่ได้หลัง commit** สำหรับข้อมูลสำคัญให้พิจารณา `RESTRICT`  *((ห้ามลบถ้ายังมีลูกอ้างอยู่))* หรือ soft delete  *((ทำเครื่องหมายว่าลบแล้ว แต่ยังเก็บแถวไว้))* แทน

## 6. Connection Pool

การเปิด connection ใหม่ทุกครั้งแพงมาก (ต้อง TCP handshake + authenticate ใหม่) pool เลยเปิดค้างไว้จำนวนหนึ่งแล้วให้ request หมุนเวียนกันใช้

> 🧠 **สูตรที่ต้องจำ (จะโผล่ซ้ำในบท 06)**
> **connection ทั้งหมด = จำนวน instance × pool size** และต้องไม่เกิน `max_connections` ของ PostgreSQL
>
> ค่าแนะนำ: dev ~10 / prod 20–50 / traffic สูง 50–100 **ต่อ instance**

> 🛑 **⚠ สูตร `(core × 2) + spindle` ในสไลด์**
> สูตรนี้เป็นสูตรกำหนดขนาดของ **DB server** ไม่ใช่ของ pool ในแอป และไม่ได้คิดเรื่องหลาย instance เลย ต้องอ่านคู่กับบท 06 เสมอ ซึ่งจะบอกอีกว่าถ้ามี read replica  *((สำเนา DB ที่ใช้อ่านอย่างเดียว แบ่งโหลดจากตัวหลัก))* ด้วย ตัวเลขจริงคือ **instances × (1 + replicas) × poolSize** เพราะ TypeORM สร้าง pool แยกต่อ master และต่อ slave แต่ละตัว

> ⚠️ **อาการที่ต้องรู้จัก**
> **Long transaction ทำให้ pool หมดทั้งที่ DB ยังว่าง** — ถ้ามี 20 request เปิด transaction ค้างพร้อมกันบน pool size 20 request ที่ 21 จะรอจน timeout ทั้งที่ CPU ของ DB แทบไม่ทำงานเลย นี่เป็นอีกเหตุผลที่ transaction ต้องสั้น

## 7. Map error code เป็น HTTP status

| PostgreSQL code | ความหมาย | ตอบกลับ |
| --- | --- | --- |
| `23505` | unique violation  *((ใส่ค่าซ้ำในคอลัมน์ที่ห้ามซ้ำ))* | **409 Conflict**  *((HTTP status ที่แปลว่า "ข้อมูลชนกัน"))* |
| `23503` | foreign key violation | 400 Bad Request |
| `23502` | not null violation | 400 Bad Request |
| `23514` | check violation | 400 Bad Request |
| `40P01` | deadlock detected | **retry** ไม่ใช่ตอบ error ทันที |

เหตุผล: ถ้าปล่อยเป็น 500 ดิบ ๆ ฝั่ง client แก้ปัญหาตัวเองไม่ได้เลย และทีมเราก็แยกไม่ออกว่า error ตัวไหนคือ "ผู้ใช้ส่งมาผิด" กับ "ระบบเราพัง" — ต่อยอดจากหลัก "โยน exception ไม่ return null" ในบท 02

**Optimistic locking** ตั้งสมมติฐานว่าคงไม่ค่อยชนกัน จึงไม่ล็อกสิ่งใดเลย แต่ใช้ `@VersionColumn` ซึ่งเพิ่มค่าทุกครั้งที่บันทึก แล้วตรวจตอนเขียนว่า version ยังตรงกับตอนที่อ่านมาหรือไม่ หากไม่ตรงแสดงว่ามีผู้อื่นแก้ไขไปก่อน ต้องโยน conflict ให้ผู้ใช้โหลดข้อมูลใหม่

เกณฑ์การเลือกพิจารณาสองปัจจัย คือ **ความถี่ของการชนกัน** และ **ระยะเวลาที่ผู้ใช้ถือข้อมูลไว้**

ใช้ pessimistic เมื่อมีการแย่งกันสูงและเป็นการปรับปรุงข้อมูลสำคัญที่ผิดพลาดไม่ได้ เช่น การตัดสต็อกใน flash sale การจองที่นั่ง หรือการตัดยอดเงิน เพราะหากใช้ optimistic ในกรณีเช่นนี้ ผู้ใช้ส่วนใหญ่จะพบ conflict และต้อง retry ซ้ำจนไม่สิ้นสุด ข้อเสียคือผู้อื่นต้องรอและมีความเสี่ยงเกิด deadlock

ใช้ optimistic เมื่อการชนกันเกิดขึ้นน้อยและผู้ใช้ถือข้อมูลไว้นาน เช่น การแก้ไขเอกสารหรือแก้ไขโปรไฟล์ที่เปิดฟอร์มค้างไว้หลายนาที เนื่องจากการล็อกแถวไว้ตลอดเวลานั้นจะบล็อกผู้อื่นโดยไม่จำเป็น ข้อเสียคือต้องเขียน logic จัดการ conflict และต้องออกแบบ UX ให้แจ้งผู้ใช้

ข้อควรระวังคือการเขียน optimistic lock ต้องให้ database เป็นผู้ตรวจ version ภายในคำสั่งเดียว เช่น `repo.update({ id, version }, patch)` แล้วตรวจว่า `affected === 0` ไม่ใช่การ `findOne` มาเปรียบเทียบ version ด้วยตนเองแล้วจึง `save()` เพราะวิธีหลังยังคงมีช่องว่างแบบ TOCTOU  *((ตรวจตอนหนึ่ง แต่ใช้จริงอีกตอน ระหว่างนั้นมีคนแทรกได้))* เหลืออยู่
</details>

<details>
<summary><b>ทำไมห้ามใช้ `synchronize: true` ใน production และควรใช้อะไรแทน</b></summary>

โครง: มันทำอะไร → เหตุการณ์จริงที่เกิด → ทำไมร้ายแรงกว่า downtime → migration + กฎของมัน

`synchronize: true` สั่งให้ TypeORM ปรับ schema ในฐานข้อมูลให้ตรงกับ entity โดยอัตโนมัติทุกครั้งที่แอปพลิเคชันเริ่มทำงาน ซึ่งการทำให้ตรงกันนั้นรวมถึงคำสั่ง `DROP COLUMN` และ `DROP TABLE` ด้วย

ตัวอย่างที่เกิดขึ้นจริงคือ เมื่อลบ field ออกจาก entity เพราะเข้าใจว่าไม่ได้ใช้แล้ว TypeORM จะสั่งลบคอลัมน์นั้นทิ้งพร้อมข้อมูลทั้งหมด โดยไม่ถามและไม่มีคำเตือนใด ๆ

เหตุที่ร้ายแรงเป็นพิเศษคือ นี่ไม่ใช่เพียง downtime ที่รอให้ระบบกลับมาทำงานได้ แต่เป็น **data loss ถาวร** ที่กู้คืนไม่ได้เลยหากไม่มี backup

สิ่งที่ควรใช้แทนคือ **migration** ซึ่งเป็น version control ของ schema โดยเขียนเป็นไฟล์ที่มี `up()` และ `down()` เรียงตาม timestamp และบันทึกไว้ว่ารันไปแล้วในตาราง `migrations`

กฎที่ต้องปฏิบัติตามคือ เขียน `down()` เสมอและทดสอบ revert จริง, ห้ามแก้ไข migration ที่ deploy ไปแล้วเพราะจะทำให้เกิด schema drift ระหว่าง environment, ให้หนึ่ง migration ต่อหนึ่งการเปลี่ยนแปลงเชิงตรรกะ, อ่านไฟล์ที่ `migration:generate` สร้างขึ้นก่อน commit เสมอเพราะ generator มักตีความการ rename เป็นการ drop แล้ว create ใหม่ และควรรัน migration เป็น job แยกก่อน deploy แอปพลิเคชัน ไม่ใช่รันตอน boot เนื่องจากเมื่อมีหลาย instance ขึ้นพร้อมกันจะแย่งกันรัน
</details>

<details>
<summary><b>ทำไมห้ามเรียก external API หรือส่งอีเมลภายใน database transaction</b></summary>

โครง: เหตุผลชั้น performance → เหตุผลชั้น correctness (สำคัญกว่า) → ทางแก้ที่ถูก

เหตุผลแรกเป็นเรื่อง performance การเรียก HTTP ไปยังบริการภายนอกอาจใช้เวลา 5 ถึง 30 วินาที และตลอดเวลานั้น transaction ยังคงเปิดค้างอยู่ ทำให้ database ถือ lock ไว้ทั้งหมด ผู้อื่นที่ต้องการแถวเดียวกันต้องรอ และ connection ใน pool ถูกจองค้าง ซึ่งอาจทำให้ pool หมดทั้งที่ database ยังว่างอยู่

เหตุผลที่สองสำคัญกว่าและเป็นเรื่องความถูกต้อง คือ **side effect ที่เกิดขึ้นนอก database ไม่อยู่ในขอบเขตของ transaction** หากหลังจากส่งอีเมลหรือตัดบัตรไปแล้ว transaction เกิด rollback การ rollback นั้นย้อนคืนเฉพาะข้อมูลใน database เท่านั้น อีเมลที่ส่งออกไปแล้วเรียกคืนไม่ได้ และเงินที่ตัดไปแล้วก็ไม่ได้ถูกคืนโดยอัตโนมัติ ผลคือข้อมูลใน database กับสิ่งที่เกิดขึ้นจริงในโลกภายนอกไม่ตรงกัน

วิธีที่ถูกต้องคือทำเฉพาะงานที่เกี่ยวกับ database ภายใน transaction แล้ว **ส่งงานที่มี side effect ภายนอกเข้า queue** ให้ worker ดำเนินการหลังจาก commit สำเร็จแล้ว ตามที่กล่าวถึงในบท 05 ซึ่งนอกจากจะแก้ปัญหาทั้งสองข้อแล้ว ยังได้กลไก retry อัตโนมัติเมื่อบริการภายนอกล้มเหลวด้วย โดยมีเงื่อนไขว่า handler ต้องเขียนให้ idempotent  *((ทำซ้ำกี่รอบผลก็เท่าเดิม ไม่เกิดของซ้ำ))* เพราะระบบคิวรับประกันแบบ at-least-once  *((งานถึงอย่างน้อย 1 ครั้ง แต่อาจซ้ำได้))*
</details>

<details>
<summary><b>N+1 problem คืออะไร แก้อย่างไร และการแก้นั้นมีข้อควรระวังอะไร</b></summary>

โครง: กลไก → ตัวเลข → ทางแก้ → กับดักของทางแก้ (จุดที่ได้คะแนนพิเศษ)

N+1 เกิดขึ้นเมื่อเราดึงรายการหลักด้วย query หนึ่งครั้ง แล้ววน loop ยิง query เพื่อหา relation ของแต่ละแถวอีก N ครั้ง เช่นการดึง user 100 คนแล้ววนหา post ของแต่ละคน ผลคือมีการติดต่อ database ถึง 101 รอบ ซึ่งแต่ละรอบมี network latency ของตัวเอง ทำให้ endpoint ที่ควรใช้เวลาเพียงไม่กี่มิลลิวินาทีกลายเป็นหลายวินาที

วิธีแก้พื้นฐานคือใช้ `relations: ['posts']` เพื่อให้ TypeORM ทำ JOIN ในคำสั่งเดียว ลดจาก 101 query เหลือเพียง 1

ข้อควรระวังที่สำคัญคือการทำ eager loading ลึกหลายชั้น เช่น `relations: ['posts', 'posts.comments']` จะสร้าง **cartesian product** หาก user หนึ่งคนมี 500 post และแต่ละ post มี 20 comment ผลลัพธ์จะมี 10,000 แถวโดยที่ข้อมูลของ user ถูกทำซ้ำในทุกแถว ซึ่งกินทั้ง network และ memory มากกว่าเดิม

ในกรณีเช่นนั้นการยิงสอง query แยกกันแล้วจับคู่ความสัมพันธ์ในแอปพลิเคชันตามแนวคิด DataLoader จะเร็วกว่า สรุปคือการแก้ N+1 เป็นการแลกเปลี่ยนระหว่าง *จำนวนรอบการติดต่อ* กับ *ปริมาณข้อมูลที่ดึงมา* ไม่ใช่กฎตายตัว จึงต้องตรวจสอบจาก SQL log จริงว่าวิธีใดเหมาะสมกว่าในแต่ละกรณี
</details>

<details>
<summary><b>Deadlock คืออะไร เกิดจากอะไร และป้องกันอย่างไร</b></summary>

โครง: นิยาม + ตัวอย่างคู่ → DB ทำอะไร → ป้องกัน 2 ชั้น → ทำไม fixed delay ไม่พอ

Deadlock คือสถานการณ์ที่ transaction สองตัวรอ lock ของกันและกันจนไม่มีฝ่ายใดดำเนินการต่อได้ ตัวอย่างเช่น transaction A ล็อกแถว User ไว้แล้วขอ lock ของ Account ในขณะที่ transaction B ล็อก Account ไว้แล้วขอ lock ของ User

PostgreSQL มีกลไกตรวจจับ deadlock ซึ่งจะเลือก**ยกเลิก transaction หนึ่งทิ้ง**พร้อมคืน error code `40P01` เพื่อให้อีกตัวดำเนินการต่อได้ ดังนั้น deadlock จึงไม่ใช่ข้อบกพร่องของ database แต่เป็นเรื่องปกติของระบบที่มีการทำงานพร้อมกัน

การป้องกันมีสองชั้น ชั้นแรกคือ **ล็อก resource ตามลำดับเดียวกันเสมอทั้งระบบ** เช่นกำหนดว่าต้องล็อก User ก่อน Account ทุกกรณี เนื่องจาก deadlock เกิดจาก circular wait หากทุกฝ่ายล็อกเรียงลำดับเหมือนกัน วงรอบของการรอจะเกิดขึ้นไม่ได้ตั้งแต่ต้น

ชั้นที่สองคือมี **retry logic** สำหรับ error `40P01` เพราะยังมีกรณีที่หลีกเลี่ยงไม่ได้ แต่ต้องใช้ **exponential backoff ร่วมกับ jitter** ไม่ใช่การหน่วงเวลาคงที่ เพราะหาก transaction ที่ชนกันรอเป็นเวลาเท่ากันแล้วกลับมาพร้อมกัน จะชนกันซ้ำที่จังหวะเดิมไปเรื่อย ๆ ส่วน jitter แบบสุ่มทำหน้าที่กระจายเวลาที่กลับมาให้ไม่ตรงกัน ซึ่งเป็นหลักการเดียวกับ retry ของ job ในบท 05 และ TTL jitter ในบท 04

นอกจากนี้การทำให้ transaction สั้นที่สุดยังช่วยลดโอกาสเกิด deadlock โดยตรง เพราะช่วงเวลาที่ถือ lock สั้นลง
</details>

<details>
<summary><b>Connection pool คืออะไร และตั้งค่าอย่างไรจึงจะไม่ทำให้ระบบล่ม</b></summary>

โครง: ทำไมต้องมี pool → สูตร → เล็กไป/ใหญ่ไปเป็นยังไง → กับดัก long transaction

การเปิด connection ใหม่ไปยัง database ทุกครั้งที่มี request มีต้นทุนสูง เพราะต้องทำ TCP handshake และ authentication ใหม่ connection pool จึงเปิด connection ค้างไว้จำนวนหนึ่งแล้วให้ request หมุนเวียนกันใช้

หลักการตั้งค่าที่สำคัญที่สุดคือต้องคิดจากภาพรวมทั้งระบบ ไม่ใช่คิดต่อ instance กล่าวคือ **จำนวน connection ทั้งหมดเท่ากับจำนวน instance คูณด้วย pool size** และค่านี้ต้องไม่เกิน `max_connections` ของ PostgreSQL โดยควรอยู่ราว 80% เพื่อสำรอง connection สำหรับงานดูแลระบบ หากมี read replica ด้วยต้องคูณเพิ่มเป็น `instances × (1 + replicas) × poolSize` เนื่องจาก TypeORM สร้าง pool แยกสำหรับ master และสำหรับ slave แต่ละตัว

หากตั้ง pool เล็กเกินไป request จะเข้าคิวรอ connection ทำให้ latency สูงขึ้นทั้งที่ database ยังว่าง หากตั้งใหญ่เกินไปโดยเฉพาะเมื่อ scale out หลาย instance database จะปฏิเสธ connection ใหม่ทั้งหมด ซึ่งทำให้ระบบล่มทั้งระบบพร้อมกัน นี่เป็นสาเหตุอันดับหนึ่งของอาการ "too many connections" หลังจากเพิ่มจำนวน instance

ค่าอ้างอิงคือ dev ประมาณ 10, production 20–50 และระบบที่มี traffic สูง 50–100 ต่อ instance ส่วนสูตร `(core × 2) + spindle` ที่มักถูกอ้างถึงนั้นเป็นสูตรสำหรับกำหนดขนาดของ DB server ไม่ใช่ของ pool ในแอปพลิเคชัน

กับดักที่ต้องระวังคือ **long transaction** หากมี request จำนวนเท่ากับ pool size ที่เปิด transaction ค้างไว้พร้อมกัน request ถัดไปจะรอจน timeout ทั้งที่ CPU ของ database แทบไม่ทำงานเลย ในระบบที่มี instance จำนวนมากควรพิจารณาใช้ PgBouncer  *((ตัวรวม connection กลาง ให้หลาย instance ใช้ชุดเดียวกัน))* เป็น connection pooler กลาง
</details>

## 10. ✅ เช็คตัวเองก่อนปิดบท

- วาดไทม์ไลน์ของ race condition ให้เพื่อนดูได้ โดยไม่ต้องเปิดชีท
- รู้ว่า lock ต้องอยู่ใน**transaction เดียวกับการเขียน** เพราะอะไร
- เขียน optimistic lock แบบที่**ถูกจริง** ได้ (conditional update แล้วเช็ค `affected`)
- อธิบายได้ว่าทำไม external call ใน transaction ผิดทั้งด้าน performance และ correctness
- ท่องสูตร connection ได้ และรู้ว่าบท 06 จะเติมอะไรเข้าไปในสูตร
- รู้ว่า `synchronize: true` ทำให้เกิด *data loss* ไม่ใช่แค่ downtime
