# Backend 06 — Scaling, Load Balancing & Observability

> บทนี้ตอบคำถามเดียว: **เครื่องเดียวเอาไม่อยู่แล้ว จะเพิ่มเครื่องยังไงให้ระบบเร็วขึ้นจริง แทนที่จะพังหนักกว่าเดิม**

### 📌 หัวข้อหลักในบทนี้:
- **Stateless (ไม่เก็บข้อมูลผู้ใช้ไว้ในตัวเอง ทุก instance รับ request แทนกันได้)**
- **Nginx Load Balancing (ตัวกลางที่กระจาย request ไปหลายเครื่อง)**
- **PostgreSQL Replication (ก๊อป DB ไว้อีกตัว ให้ช่วยรับ read และกันตาย)**
- **Health Check (ถามเป็นระยะว่ายังไหวอยู่ไหม)**
- **Graceful Shutdown (ปิดแบบรอ request ที่ค้างอยู่ให้จบก่อน)**
- **Logging / Metrics (บันทึกเหตุการณ์ / ตัวเลขวัดสุขภาพระบบ)**
- **p95 / p99 (ช้ากว่านี้แค่ 5% / 1% ของ request ทั้งหมด)**
- **Load Testing (ยิงโหลดจำลองดูว่าพังที่เท่าไหร่)**

## 1. Stateless  *((ไม่เก็บข้อมูลผู้ใช้ไว้ในตัวเอง ทุกเครื่องจึงรับงานแทนกันได้))* — เงื่อนไขบังคับที่ต้องมาก่อนทุกอย่าง

### 1.1 ทำไม state ใน memory ถึงใช้ไม่ได้

Load balancer  *((ตัวกลางที่กระจาย request ไปยัง instance หลายตัว))* ส่ง request ไปเครื่องไหนก็ได้ — request แรกไปเครื่อง A request ถัดไปอาจไปเครื่อง B ถ้า A จำอะไรไว้ใน memory แล้ว B ไม่รู้เรื่อง ระบบก็พัง แถมข้อมูลทั้งหมดหายทุกครั้งที่ restart ซึ่งเกิดขึ้นทุก deploy

> 📊 **แผนภาพ: ต้นเหตุไม่ใช่ load balancer แต่คือการที่เราสมมติว่า request ถัดไปจะกลับมาที่เครื่องเดิม**
>
> *ข้อความ/ลำดับในแผนภาพ:*
> - ❌ session อยู่ใน memory ของ instance
> - ผู้ใช้ login
> - Nginx
> - App 1
> - เก็บ session ไว้ใน RAM ✓
> - กดหน้าถัดไป
> - App 2
> - ไม่รู้จัก session นี้ → เด้งออก 401
> - ✅ session อยู่ที่ Redis
> - App 3
> - Redis — ทุกเครื่องเห็นเหมือนกัน
> - ไปเครื่องไหนก็ได้

| เก็บอะไรไว้ในเครื่อง | ย้ายไปไหน |
| --- | --- |
| Session | **Redis** หรือใช้ JWT  *((token ที่เซ็นลายเซ็นมาในตัว ตรวจได้เลย ไม่ต้องเก็บ session ฝั่ง server))* |
| Cache (`Map`) | **Redis** (บท 04) |
| Counter / rate limit | **Redis `INCR`** (บท 04) |
| ไฟล์ที่ผู้ใช้อัปโหลด | S3 / object storage  *((ที่เก็บไฟล์กลางนอกเครื่อง ทุก instance เข้าถึงได้))* |
| งานเบื้องหลัง | **Queue** (บท 05) |

### 1.2 Session ใน Redis กับ JWT

|  | Session ใน Redis | JWT |
| --- | --- | --- |
| ตรวจสิทธิ์ | ต้องอ่าน Redis ทุก request | ตรวจ signature ได้เลย ไม่ต้องอ่านอะไร |
| **เพิกถอน (revoke)** | **ทำได้ทันที** ลบ key ทิ้งก็จบ | **ทำไม่ได้** token ยังใช้ได้จนกว่าจะหมดอายุ |
| ข้อแลก | Redis กลายเป็น SPOF  *((จุดเดียวที่ถ้าล่มแล้วระบบล่มทั้งหมด))* ของ auth | ต้องตั้ง TTL  *((อายุที่ตั้งไว้ ครบเวลาแล้วหมดอายุเอง))* สั้นแล้วมี refresh token  *((token อายุยาวไว้ขอ token ใหม่ตอนของเดิมหมดอายุ))* หรือทำ blacklist ใน Redis |

> 🛑 **⚠ สไลด์เสนอ JWT ว่า "zero database queries for auth" โดยไม่พูดถึงข้อเสีย**
> ข้อจำกัดที่ต้องพูดถึงเสมอคือ **JWT เพิกถอนไม่ได้** — ผู้ใช้กด "ออกจากระบบทุกอุปกรณ์" หรือแอดมินแบนบัญชี token เดิมก็ยังใช้ได้อยู่จนหมดอายุ
>
> ทางแก้คือตั้งอายุ token ให้สั้น เช่น 15 นาที แล้วใช้ refresh token หรือทำ blacklist ใน Redis — แต่ blacklist ก็คือการเอา shared state กลับเข้ามา ซึ่งลบล้างข้อดี "ไม่ต้องอ่านอะไรเลย" ไปพอสมควร มันเป็น trade-off ไม่ใช่ของฟรี

### 1.3 Graceful Shutdown

ถ้า process ถูกฆ่าทันที request ที่กำลังทำอยู่จะถูกตัดกลางคัน ผู้ใช้เห็น 502 **ทุกครั้งที่ deploy** ลำดับที่ถูกต้องคือ:

1. ได้รับ `SIGTERM`  *((สัญญาณบอกให้ process เตรียมปิดตัวเอง ไม่ใช่ฆ่าทันที))* → **หยุดรับ request ใหม่** และให้ `/health/ready` ตอบ fail เพื่อให้ LB  *((ตัวย่อของ load balancer))* ถอดเครื่องนี้ออกจากกลุ่ม
2. **drain** — รอ request ที่ค้างอยู่ให้ทำจนเสร็จ
3. ปิด DB connection / Redis / worker แล้วค่อยจบ process

Worker ของ queue (บท 05) ก็ต้องทำแบบเดียวกัน ไม่งั้นทุก deploy จะทิ้ง job ค้างสถานะ stalled  *((งานที่ worker หายไปกลางคัน ระบบไม่รู้ว่าเสร็จหรือยัง))*

### 1.4 สูตร connection pool  *((ถังเก็บ connection DB ไว้ใช้ซ้ำ ไม่ต้องเปิดใหม่ทุกครั้ง))* ฉบับสมบูรณ์

> 📊 **แผนภาพ: ตัวคูณที่คนลืมคือ replica — TypeORM  *((ORM ของ Node — ตัวแปลงระหว่าง object ในโค้ดกับตารางใน DB))* สร้าง pool แยกต่อ master และต่อ slave  *((ชื่อเก่าของ primary/replica — master รับเขียน slave เป็นสำเนาไว้อ่าน))* แต่ละตัว**
>
> *ข้อความ/ลำดับในแผนภาพ:*
> - ทำไม "too many connections" ถึงโผล่มาทันทีที่ scale
> - App 1
> - App 2
> - App 3
> - 3 instance
> - แต่ละ instance
> - สร้าง pool
> - แยกต่อ 1 target
> - Primary
> - Replica 1
> - Replica 2
> - 1 + 2 = 3 targets
> - สูตรในสไลด์: instances × poolSize
> - 3 × 20 = 60 ← นับขาดไป 3 เท่า
> - สูตรจริง: instances × (1 + replicas) × poolSize
> - 3 × 3 × 20 = 180
> - ถ้า max_connections = 100
> - → DB ปฏิเสธ connection ทั้งระบบ ล่มพร้อมกันหมด
> - เป้าหมายคือให้อยู่ไม่เกิน 80% ของ max_connections · instance เยอะมากให้ใช้ PgBouncer เป็นตัวรวม connection

> 🧠 **สูตรที่ต้องจำ — สาเหตุอันดับหนึ่งของ "too many connections"**
> `instances × (1 + replicas) × poolSize ≤ 80% ของ max_connections`

## 2. Load Balancing (Nginx)  *((Nginx = reverse proxy ตัวกลางที่รับ request แทน backend แล้วกระจายต่อ))*

| Algorithm | ใช้เมื่อ | หมายเหตุ |
| --- | --- | --- |
| `round_robin`  *((วนส่งทีละเครื่องไปเรื่อย ๆ ไม่สนว่าใครยุ่ง))* | **ค่าเริ่มต้น** — request มีต้นทุนพอ ๆ กัน และ app stateless แล้ว | เรียบง่ายและพอสำหรับ API ทั่วไป |
| `least_conn`  *((ส่งให้ตัวที่มีงานค้างน้อยสุด))* | request ใช้เวลาต่างกันมาก เช่น upload, long-polling, websocket | ส่งไปเครื่องที่มี connection ค้างน้อยที่สุด |
| `ip_hash`  *((ล็อก IP เดิมให้ไปเครื่องเดิมเสมอ คือการทำ sticky session))* | **หลีกเลี่ยง** | ผู้ใช้จาก NAT  *((หลายเครื่องออกเน็ตผ่าน IP สาธารณะเดียวกัน))* หรือ proxy เดียวกันจะกองไปเครื่องเดียว, เครื่องล้ม = คนกลุ่มนั้นหลุด session หมด, และตอน scale-in การจับคู่จะเปลี่ยนทั้งหมด — **ถ้าทำ stateless ถูกต้องแล้วก็ไม่ต้องใช้เลย** |

### 2.1 ค่าที่ต้องตั้ง

- `max_fails` + `fail_timeout` — เกณฑ์ที่จะถอด upstream  *((backend ที่ Nginx กระจาย request ไปหา))* ที่ล้มเหลวออกจากกลุ่ม
- `proxy_connect_timeout` / `send` / `read` — ถ้าไม่ตั้ง upstream ที่ค้างจะยึด worker connection ของ Nginx จนหมด แล้วลามเป็น outage ทั้งระบบ
- `X-Real-IP` / `X-Forwarded-For` — ถ้าไม่ forward ระบบ rate limiting, audit log และ geo ทั้งหมดจะเห็นแต่ IP ของ load balancer

> 🛑 **⚠ สไลด์ 44 ผิดอย่างมีนัยสำคัญ — น่าจะเป็นข้อสอบ**
> สไลด์เขียนว่า *"Docker mark ว่า unhealthy → Nginx หยุดส่ง traffic"* ซึ่ง **ไม่จริง**
>
> **Nginx อ่านสถานะ health ของ Docker ไม่ได้เลย** เพราะเป็นคนละระบบที่ไม่รู้จักกัน สิ่งที่ Nginx รุ่นฟรีทำได้คือ **passive health check**  *((รู้ว่าเครื่องล่มก็ต่อเมื่อ request ของผู้ใช้จริงพัง))* เท่านั้น คือถอด upstream ออกก็ต่อเมื่อ*request จริงของผู้ใช้*ล้มเหลวครบ `max_fails` ครั้งภายใน `fail_timeout`
>
> ส่วน **active health check** ที่ LB ยิงไปตรวจเองเป็นระยะ (`health_check` directive) มีเฉพาะใน **Nginx Plus** ซึ่งเสียเงิน ถ้าอยากได้พฤติกรรมแบบที่สไลด์บรรยาย ต้องใช้ **Kubernetes readinessProbe**, Docker Swarm หรือ Nginx Plus
>
> **ทำไมเรื่องนี้อันตราย:** คนที่เชื่อตามสไลด์จะคิดว่าตัวเองมี failover  *((สลับไปใช้ตัวสำรองอัตโนมัติเมื่อตัวหลักล่ม))* ทั้งที่ไม่มี แล้วจะรู้ตัวก็ตอนระบบล่มจริงเท่านั้น
>
> เช่นเดียวกัน `HEALTHCHECK` ใน Dockerfile (บท 01) ถ้าไม่มี orchestrator  *((ตัวคุมการรัน container หลายเครื่อง เช่น Kubernetes))* มันแค่เปลี่ยนข้อความในคอลัมน์ STATUS ของ `docker ps` เท่านั้น ไม่มีใครเอาผลนั้นไปทำอะไรต่อ

> 🛑 **⚠ Nginx ตัวเดียวก็เป็น SPOF**
> สไลด์วาดสถาปัตยกรรมที่มี Nginx ตัวเดียวเป็นทางเข้าเดียว แต่ตั้งเป้า "99.9%+ uptime, no single point of failure" ซึ่งขัดกันเอง ต้องรัน Nginx 2 ตัวคู่กับ VIP  *((IP กลางที่ย้ายไปเครื่องสำรองได้เมื่อตัวหลักล่ม))* หรือ DNS failover หรือใช้ managed load balancer ของ cloud

## 3. Database Replication  *((ก๊อปข้อมูลจาก primary ไปไว้ที่ replica แบบต่อเนื่อง))*

### 3.1 มันช่วยอะไรและไม่ช่วยอะไร

Primary รับ write ทั้งหมด ส่วน replica รับ read ซึ่งกินสัดส่วน **80–90% ของ query ทั้งระบบ**

> ⚠️ **ประโยคที่ต้องพูดในข้อสอบ**
> **Replication ไม่ได้เพิ่ม write throughput เลย**  *((throughput = จำนวนงานที่ระบบทำได้ต่อวินาที))* เพราะทุกการเขียนยังต้องผ่าน primary ตัวเดียว แถมยังต้องส่ง WAL  *((log ที่ Postgres เขียนก่อนแก้ข้อมูลจริง ใช้ส่งต่อให้ replica))* ไปให้ replica อีก ถ้า bottleneck  *((จุดคอขวดที่ช้าที่สุด ตัวกำหนดความเร็วรวมของระบบ))* คือการเขียน ต้องแก้ด้วย sharding, partitioning  *((sharding = แยกข้อมูลไปคนละเครื่อง, partitioning = ซอยตารางใหญ่เป็นส่วนย่อยในเครื่องเดียว))* หรือรวมงานเขียนเป็น batch ผ่าน queue (บท 05)

```typescript
// TypeORM
replication: {
  master: { host: 'primary', ... },
  slaves: [{ host: 'replica-1' }, { host: 'replica-2' }],
}
// ⚠️ สร้าง pool แยกต่อ master และต่อ slave แต่ละตัว → ดูสูตรใน §1.4
```

### 3.2 Replication Lag  *((ช่วงที่ replica ยังตามข้อมูลของ primary ไม่ทัน))* และ Read-Your-Writes

Replica ตามหลัง primary เสมอ ปกติ 10–100ms และตอนโหลดหนักอาจถึง 100ms–1s (ควรตั้ง alert เมื่อเกิน 1 วินาที)

> 🧠 **บั๊กคลาสสิกที่ต้องรู้จัก**
> ผู้ใช้สร้างโปรไฟล์ (เขียนไป primary) แล้วหน้าเว็บ redirect ไปดูโปรไฟล์ทันที (อ่านจาก replica ที่ยังไม่ได้รับข้อมูล) → **404 ทั้งที่เพิ่งสร้างสำเร็จ**
>
> อาการนี้ **ไม่เกิดตอน dev เลย** เพราะ lag เป็นศูนย์ และจะโผล่เฉพาะตอน production มีโหลด ซึ่งทำให้หาสาเหตุยากมาก
>
> **ทางแก้:** operation แบบ read-your-writes  *((เขียนเสร็จแล้วอ่านต่อทันที ต้องเห็นของที่เพิ่งเขียน))* ต้องบังคับให้อ่านจาก primary หรือทำทั้งชุดอยู่ใน transaction  *((กลุ่มคำสั่ง DB ที่ต้องสำเร็จทั้งหมดหรือไม่เกิดอะไรเลย))* ซึ่ง TypeORM จะใช้ master เสมอ

### 3.3 เรื่อง ops ที่สไลด์ไม่พูด

> ⚠️ **Replication slot ที่ถูกลืม ทำให้ primary ล่มได้**
> ถ้า replica ตายไปแต่ **replication slot ยังค้างอยู่**  *((slot = จุดที่ primary จำไว้ว่า replica อ่าน WAL ไปถึงไหนแล้ว))* primary จะ**เก็บ WAL ไว้ตลอดไป** เพราะคิดว่ายังมีคนต้องใช้ ผลคือดิสก์ของ primary เต็ม แล้ว**ระบบเขียนทั้งหมดหยุดทำงาน**
>
> ต้อง monitor `pg_replication_slots`, ตั้ง `max_slot_wal_keep_size` และลบ slot ที่ไม่ใช้แล้ว

**Config ฝั่ง primary:** `wal_level=replica`, `max_wal_senders` เท่ากับจำนวน replica + 1, สร้าง replication slot, ใช้ role `replicator` แยกต่างหาก และ**ต้องซ้อมทำ failover จริง** ด้วย Patroni หรือ repmgr  *((เครื่องมือจัดการ failover ของ PostgreSQL ให้อัตโนมัติ))* ก่อนถึงวันที่ต้องใช้จริง

> 🛑 **⚠ สไลด์อ้างความสามารถของ TypeORM เกินจริง**
> สไลด์บอกว่า "TypeORM ตรวจจับ connection failure, ข้าม replica ที่ล่ม และให้ master รับ read ถ้า replica ล่มหมด" ซึ่ง**เกินจริง** TypeORM ไม่มีการ health check replica แบบ active มันแค่วน round-robin ไปที่ slave และการ failover ขึ้นกับพฤติกรรม error ของ driver **อย่าออกแบบระบบโดยพึ่งพาข้อนี้**
>
> อีกจุด: compose ในสไลด์ใช้ `pg_basebackup -U postgres` ขณะที่ init script สร้าง role `replicator` และสไลด์ถัดไปใช้ `-U replicator` ซึ่งไม่สอดคล้องกัน

## 4. Health Check — ต้องแยกสองแบบ

|  | `/health/live` (Liveness) | `/health/ready` (Readiness) |
| --- | --- | --- |
| ถามว่า | "process ยังไม่ตายใช่ไหม" | "พร้อมรับ traffic หรือยัง" |
| เช็คอะไร | **ไม่เช็ค dependency เลย** ตอบ 200 เฉย ๆ | เช็ค DB + Redis |
| ถ้า fail | **restart container** | **ถอดออกจาก LB** แต่ container ยังรันต่อ |

> ⚠️ **ทำไม liveness ห้ามเช็ค DB — เหตุผลที่ต้องอธิบายให้ได้**
> ถ้า liveness เช็ค DB ด้วย แล้ว DB สะดุดไป 5 วินาที → **ทุก container จะ fail liveness พร้อมกัน → ถูก restart พร้อมกันทั้งหมด**
>
> ผลคือระบบล่มยาวจากปัญหาที่จริง ๆ แล้วแค่สะดุดชั่วครู่ — **เราสร้าง outage ขึ้นเองจากกลไกที่ตั้งใจจะป้องกัน outage**
>
> ในทางกลับกัน readiness ควรเช็ค DB เพราะถ้า instance ต่อ DB ไม่ได้ มันก็ให้บริการไม่ได้จริง ควรถูกถอดออกจาก LB ชั่วคราวแล้วกลับเข้ามาเองเมื่อเชื่อมต่อได้
>
> **⚠ สไลด์ใช้ `/health` เดียว (เช็คทั้ง DB และ memory) สำหรับทั้งสองหน้าที่ ซึ่งขัดกับตารางเปรียบเทียบของสไลด์เอง** ถ้าเอาไปใช้เป็น livenessProbe ของ Kubernetes มันจะทำให้ทุก pod restart วนทุกครั้งที่ DB สะดุด

**อีกข้อ:** ต้องทำให้ endpoint นี้**เบา** เพราะภาระของ probe  *((การยิงเช็คสุขภาพเป็นระยะ))* จะถูกคูณด้วยความถี่และจำนวน instance ถ้า probe หนักแล้ว DB เริ่มช้า probe เองจะกลายเป็นตัวเร่งให้ instance ถูกถอดออกเป็นลูกโซ่

## 5. Observability  *((ความสามารถในการรู้ว่าข้างในระบบเกิดอะไรขึ้น จากสิ่งที่มันพ่นออกมา))*

### 5.1 Logging

- **JSON แบบมีโครงสร้าง** ไม่ใช่ข้อความดิบ เพื่อให้ query ได้
- **correlation หรือ trace id ทุก request**  *((id เดียวแปะไปทุก log ของ request นั้น ใช้ตามรอยข้ามระบบ))* และ**ส่งต่อไปถึง worker** ด้วย (บท 05) ไม่งั้นจะตาม request เดียวข้ามระบบไม่ได้เลย
- **centralized logging** (ELK / CloudWatch) เพราะ log ที่กระจายอยู่ใน 5 เครื่องใช้งานไม่ได้จริงตอนเกิดเหตุ
- ระดับต่ำสุดใน prod คือ `info` — `debug` ทำให้ดิสก์เต็ม ค่าใช้จ่ายบาน และ**กลบสัญญาณจริง**
- **ห้าม log รหัสผ่าน, token, ข้อมูลส่วนบุคคล, เลขบัตร** เพราะ log ไปอยู่ในที่ที่คนเข้าถึงได้กว้างและเก็บไว้นาน
- ค่า log อาจแพงกว่าค่า compute ควร sample  *((เก็บแค่บางส่วนแทนที่จะเก็บทุกอัน))* เส้นทางที่มี volume สูง

### 5.2 Metrics  *((ตัวเลขวัดพฤติกรรมระบบที่เก็บต่อเนื่องตามเวลา))* ที่ต้องมี

request rate · error rate (**แยก 4xx กับ 5xx**) · p50/p95/p99 latency  *((เวลาตอบกลับที่ช้ากว่านี้แค่ 50% / 5% / 1% ของ request — ดูคนซวย ไม่ใช่ค่าเฉลี่ย))* · queue depth และ queue lag  *((งานค้างในคิวกี่ชิ้น / รอนานแค่ไหนกว่าจะถูกหยิบไปทำ))* (บท 05) · cache hit ratio  *((สัดส่วนที่หาเจอใน cache ไม่ต้องไปถาม DB))* (บท 04) · replication lag · pool utilization

### 5.3 ทำไมต้องดู percentile ไม่ใช่ค่าเฉลี่ย

> 📊 **แผนภาพ: ค่าเฉลี่ยไม่ได้โกหก แต่มันเล่าเรื่องของคนที่ไม่มีปัญหา ส่วน p99 เล่าเรื่องของคนที่กำลังจะเลิกใช้**
>
> *ข้อความ/ลำดับในแผนภาพ:*
> - เร็ว
> - ช้า
> - เวลาตอบสนองของแต่ละ request
> - ค่าเฉลี่ย ~100ms
> - "ดูดีมาก"
> - p99 ~5,000ms
> - คนกลุ่มนี้รอ 5 วินาที
> - p99 มักไม่ใช่ผู้ใช้แบบสุ่ม แต่เป็นคนที่มีข้อมูลเยอะที่สุด — ซึ่งมักเป็นลูกค้ารายใหญ่ที่สุดของเรา

> 🧠 **ประโยคที่ควรจำไปเขียน**
> ถ้า 99 request ใช้เวลา 50ms และ 1 request ใช้ 5,000ms ค่าเฉลี่ยจะเป็นราว 100ms ซึ่ง**ดูดีมาก** ทั้งที่มีผู้ใช้ที่ต้องนั่งรอ 5 วินาที
>
> **p99 คือผู้ใช้ที่โกรธที่สุด และมักเป็นคนที่มีข้อมูลมากที่สุด** เช่นลูกค้ารายใหญ่ที่มี order เป็นหมื่นรายการ แปลว่า p99 มักตรงกับลูกค้าที่เราเสียไม่ได้ ค่าเฉลี่ยซ่อนคนกลุ่มนี้ไว้ทั้งหมด

## 6. ตัวเลขเป้าหมาย & ลำดับการทำงาน

| Metric | เป้าหมาย |
| --- | --- |
| RPS  *((request ต่อวินาทีที่รับไหว))* | 1,000+ สำหรับ API ทั่วไป |
| p50 / p95 / p99 | < 100ms / < 200ms / < 500ms |
| Error rate | < 0.1% |
| Replication lag | < 1 วินาที |
| CPU ต่อ instance หลัง scale | ราว 45% |

**ตัวเลขอ้างอิงจากสไลด์:** 1 instance ได้ 500 RPS ที่ p95 300ms → 3 instance ได้ 1,400 RPS ที่ p95 150ms คือ **ราว 2.8 เท่า ไม่ใช่ 3 เท่า** เพราะมี overhead ของ LB และการแย่งทรัพยากรที่ DB (และนี่เป็นแค่ตัวอย่างประกอบ ไม่ใช่การรับประกัน)

> 🧠 **ลำดับที่ต้องทำ — ข้อนี้คือบทสรุปของทั้งวิชา**
> 1. **วัดก่อน** หา bottleneck จริง ไม่ใช่เดา
> 2. **แก้ query + index** (บท 03)
> 3. **ใส่ cache** (บท 04)
> 4. **ย้ายงานหนักไป queue** (บท 05)
> 5. **ค่อย scale out** (บทนี้)
>
> เหตุผล: **การ scale แอปที่มี N+1 query คือการซื้อ query ห่วย ๆ ที่เร็วขึ้นเท่านั้น**  *((N+1 = วน loop ยิง query ทีละแถว จนกลายเป็นหลายร้อยรอบ))* ถ้า bottleneck อยู่ที่ DB การเพิ่ม instance จะได้ผลตอบแทนแทบเป็นศูนย์ ซ้ำร้ายยังทำให้ DB โดนหนักขึ้นจาก connection ที่เพิ่มขึ้นตาม

**Load testing:**  *((ยิงโหลดจำลองใส่ระบบ เพื่อดูว่ารับได้ถึงไหนก่อนพัง))* ใช้ k6  *((เครื่องมือยิง load test สคริปต์เป็น JS — สายเดียวกับ JMeter))* ทำแบบ ramp-up → peak → ramp-down เพื่อให้ได้ baseline ที่เอาไปเทียบก่อน-หลังได้จริง ไม่ใช่ยิงพรวดครั้งเดียว

## 7. 🔗 แผนที่รวมทั้ง 6 บท

> 🔗 **ทุกอย่างมาบรรจบที่นี่**
> - **บท 01 →** container ที่เล็กและ config มาจาก env ทำให้ scale ออกและ rolling update  *((ทยอยเปลี่ยนเครื่องทีละตัว ไม่ดับพร้อมกันทั้งระบบ))* ได้เร็ว / `HEALTHCHECK` ของ Docker ไม่มีผลกับ Nginx จริง
> - **บท 02 →** service ที่ stateless คือ**เงื่อนไขบังคับ**ของทุกอย่างในบทนี้ / correlation id จาก interceptor คือรากฐานของ observability
> - **บท 03 →** สูตร connection pool ที่ต้องคูณ replica เข้าไป / expand-and-contract  *((เพิ่มของใหม่ก่อน ค่อยลบของเก่าทีหลัง ให้โค้ดสองเวอร์ชันอยู่ร่วมกันได้))* จำเป็นเพราะ rolling update ทำให้มีสองเวอร์ชันรันพร้อมกัน / read-your-writes ต้องไป primary
> - **บท 04 →** Redis คือที่เก็บ session และ cache ที่แชร์ระหว่าง instance / hit ratio เป็น metric หลัก / Redis เดี่ยวเป็น SPOF ต้องวางแผน HA  *((High Availability — ออกแบบให้ระบบไม่ล่มแม้เครื่องหนึ่งตาย))*
> - **บท 05 →** pub/sub + N instance = ทำงานซ้ำ N ครั้ง / queue lag เป็น metric หลัก / graceful shutdown ของ worker / ต้อง offload ก่อน scale
>
> **ถ้าจำได้ประโยคเดียวจากทั้งวิชา:** *ทุกบทกำลังแก้ปัญหาเดียวกันในระดับที่ต่างกัน — "มีหลายสิ่งเกิดขึ้นพร้อมกัน" ไม่ว่าจะเป็นหลาย request (บท 03), หลายชั้นของข้อมูล (บท 04), หลายงานที่ค้างอยู่ (บท 05) หรือหลายเครื่อง (บท 06)*

<details>
<summary><b>เหตุใดแอปพลิเคชันต้อง stateless ก่อนจึงจะทำ horizontal scaling ได้</b></summary>

โครง: กลไก LB → ผลเมื่อมี state → สิ่งที่ต้องย้าย → เงื่อนไขเพิ่มเติม

เพราะ load balancer สามารถส่ง request ไปยัง instance ใดก็ได้ และไม่มีการรับประกันว่า request ถัดไปของผู้ใช้คนเดิมจะไปยังเครื่องเดิม

หาก instance เก็บ state ไว้ในหน่วยความจำของตนเอง จะเกิดปัญหาสองประการ ประการแรกคือ **ข้อมูลไม่ตรงกันระหว่างเครื่อง** เช่นผู้ใช้ล็อกอินที่เครื่อง A แล้ว request ถัดไปถูกส่งไปเครื่อง B ซึ่งไม่รู้จัก session นั้น ทำให้หลุดออกจากระบบแบบสุ่ม หรือ cache ที่เก็บใน `Map` ของแต่ละเครื่องไม่ตรงกัน ทำให้ผู้ใช้เห็นราคาสินค้าไม่เหมือนกัน ประการที่สองคือ **ข้อมูลสูญหายทุกครั้งที่ restart** ซึ่งเกิดขึ้นทุกครั้งที่ deploy

สิ่งที่ต้องย้ายออกจากหน่วยความจำ ได้แก่ session ไปไว้ที่ Redis หรือเปลี่ยนไปใช้ JWT, cache ไปไว้ที่ Redis, counter และ rate limit ใช้คำสั่ง `INCR` ของ Redis, ไฟล์ที่ผู้ใช้อัปโหลดไปไว้ที่ object storage และงานเบื้องหลังไปไว้ที่ queue

เงื่อนไขเพิ่มเติมที่มาคู่กันคือ ทุก instance ต้องรันโค้ดเวอร์ชันเดียวกันและใช้ image เดียวกันที่รับ config ผ่าน environment variable, ต้องมี graceful shutdown เพื่อไม่ให้ทุกการ deploy เกิด 502 และต้องคำนวณ connection pool ใหม่ทั้งระบบ เพราะจำนวน connection รวมจะเพิ่มขึ้นตามจำนวน instance
</details>

<details>
<summary><b>เหตุใดหลังจากเพิ่มจำนวน instance จึงเกิด error "too many connections" และป้องกันอย่างไร</b></summary>

โครง: กลไก pool ต่อ instance → สูตรเต็ม → ตัวอย่างตัวเลข → ทางแก้

เพราะ connection pool ถูกสร้าง**แยกกันในแต่ละ instance** ไม่ได้ใช้ร่วมกัน เมื่อเพิ่มจำนวน instance จำนวน connection รวมที่วิ่งไปยัง database จึงเพิ่มขึ้นเป็นทวีคูณ ในขณะที่ `max_connections` ของ PostgreSQL ยังคงเท่าเดิม

สูตรที่ถูกต้องคือ **จำนวน instance คูณด้วย (1 บวกจำนวน replica) คูณด้วย pool size** และค่านี้ควรอยู่ไม่เกินประมาณ 80% ของ `max_connections` เพื่อสำรอง connection สำหรับงานดูแลระบบ

ตัวคูณ (1 + replicas) เป็นจุดที่มักถูกลืม เนื่องจาก TypeORM สร้าง pool แยกสำหรับ master และสำหรับ slave แต่ละตัว ตัวอย่างเช่นระบบที่มี 3 instance, 1 primary กับ 2 replica และ pool size 20 จะใช้ connection จริงถึง 180 ในขณะที่สูตรอย่างง่ายที่คิดเพียง instances คูณ poolSize จะได้เพียง 60 ซึ่งต่ำกว่าความเป็นจริงถึงสามเท่า หาก `max_connections` ตั้งไว้ที่ 100 ระบบจะปฏิเสธ connection ทั้งหมดและล่มทันทีที่ scale

การป้องกันคือคำนวณตามสูตรเต็มก่อน scale ทุกครั้ง ปรับ pool size ต่อ instance ให้เล็กลงเมื่อจำนวน instance มากขึ้น และหากมี instance จำนวนมากควรใช้ **PgBouncer** เป็น connection pooler กลางเพื่อรวม connection ก่อนถึง database นอกจากนี้ควรหลีกเลี่ยง long transaction เพราะจะทำให้ pool ถูกจองค้างจนหมดทั้งที่ database ยังว่างอยู่

โครง: คำถามที่ต่างกัน → การกระทำที่ต่างกัน → หายนะถ้ารวมกัน → ข้อควรระวังเรื่องน้ำหนัก

เพราะทั้งสองตอบคำถามคนละข้อและนำไปสู่การกระทำคนละอย่าง

**Liveness** ถามว่า "process นี้ยังไม่ตายใช่หรือไม่" หากล้มเหลว orchestrator จะ **restart container** ดังนั้นจึงต้องเบาและ**ไม่ตรวจสอบ dependency ภายนอกใด ๆ** เพียงตอบ 200 กลับมาก็เพียงพอ

**Readiness** ถามว่า "พร้อมรับ traffic แล้วหรือยัง" หากล้มเหลว instance จะถูก **ถอดออกจาก load balancer** แต่ container ยังทำงานต่อและกลับเข้ามาได้เองเมื่อพร้อม จึงเหมาะที่จะตรวจสอบการเชื่อมต่อ database และ Redis

หากรวมทั้งสองไว้ใน endpoint เดียวที่ตรวจสอบ database ด้วย จะเกิดผลเสียร้ายแรงเมื่อ database สะดุดเพียงไม่กี่วินาที กล่าวคือ **ทุก container จะ fail liveness พร้อมกันและถูก restart พร้อมกันทั้งหมด** ทำให้ระบบล่มเป็นเวลานานจากปัญหาที่เดิมทีเป็นเพียงการสะดุดชั่วครู่ นั่นคือกลไกที่ตั้งใจป้องกัน outage กลับสร้าง outage เสียเอง

ข้อควรระวังเพิ่มเติมคือต้องทำให้ endpoint เหล่านี้เบาที่สุด เพราะภาระของ probe จะถูกคูณด้วยความถี่ในการเรียกและจำนวน instance หาก probe หนักและ database เริ่มช้าลง probe เองจะกลายเป็นตัวเร่งให้ instance ถูกถอดออกจาก load balancer เป็นลูกโซ่
</details>

<details>
<summary><b>Database replication ช่วยเรื่องอะไร ไม่ช่วยเรื่องอะไร และมีข้อควรระวังอะไร</b></summary>

โครง: กลไก → ช่วยอะไร → ไม่ช่วยอะไร (จุดสำคัญ) → lag และ read-your-writes → ops

Replication คือการให้ primary รับงานเขียนทั้งหมดแล้วส่งข้อมูลไปยัง replica ซึ่งรับเฉพาะงานอ่าน โดยงานอ่านคิดเป็นราว 80–90% ของ query ทั้งระบบ จึงช่วยแบ่งเบาภาระ primary ได้มาก และยังได้สำเนาข้อมูลไว้สำหรับการทำ failover ด้วย

สิ่งที่ replication **ไม่ช่วย** คือ **write throughput** เพราะทุกการเขียนยังต้องผ่าน primary เพียงตัวเดียว ซ้ำยังเพิ่มภาระให้ primary ในการส่ง WAL ไปยัง replica อีก หาก bottleneck อยู่ที่การเขียน ต้องแก้ด้วยวิธีอื่น เช่น sharding, partitioning หรือรวมงานเขียนเป็น batch ผ่าน queue

ข้อควรระวังหลักคือ **replication lag** ซึ่งปกติอยู่ที่ 10–100 มิลลิวินาที และอาจถึงหลักวินาทีเมื่อโหลดสูง ทำให้เกิดปัญหา **read-your-writes** เช่นผู้ใช้สร้างข้อมูลเสร็จแล้วระบบ redirect ไปหน้าแสดงผลทันที แต่อ่านจาก replica ที่ยังไม่ได้รับข้อมูลนั้น จึงได้ 404 ทั้งที่บันทึกสำเร็จ อาการนี้จะไม่ปรากฏตอนพัฒนาเพราะ lag เป็นศูนย์ และจะโผล่เฉพาะบน production ที่มีโหลด วิธีแก้คือบังคับให้ operation ประเภทนี้อ่านจาก primary หรือดำเนินการภายใน transaction ซึ่งจะใช้ master เสมอ

ในเชิง operation ต้องเฝ้าติดตาม lag และตั้ง alert เมื่อเกิน 1 วินาที และต้องเฝ้าดู `pg_replication_slots` ด้วย เพราะหาก replica ล่มไปแต่ slot ยังค้างอยู่ primary จะเก็บ WAL ไว้ตลอดไปจนดิสก์เต็มและหยุดรับการเขียนทั้งหมด ควรตั้ง `max_slot_wal_keep_size` และลบ slot ที่ไม่ใช้แล้ว สุดท้ายต้องซ้อม failover จริงด้วยเครื่องมืออย่าง Patroni หรือ repmgr และไม่ควรออกแบบระบบโดยพึ่งพาความสามารถ failover อัตโนมัติของ ORM เพราะ TypeORM ไม่มีการ health check replica แบบ active
</details>

<details>
<summary><b>เหตุใดจึงต้องวัด p95 และ p99 แทนที่จะดูค่าเฉลี่ยของ response time</b></summary>

โครง: ตัวอย่างตัวเลข → สิ่งที่ค่าเฉลี่ยซ่อนไว้ → ทำไม p99 สำคัญเป็นพิเศษ → metric อื่นที่ควรดูคู่กัน

เพราะค่าเฉลี่ยถูกกลบด้วยกรณีปกติจนมองไม่เห็นกรณีที่แย่ ตัวอย่างเช่นหาก 99 request ใช้เวลา 50 มิลลิวินาที และอีก 1 request ใช้เวลา 5,000 มิลลิวินาที ค่าเฉลี่ยจะออกมาราว 100 มิลลิวินาที ซึ่งดูดีมากบน dashboard ทั้งที่มีผู้ใช้ที่ต้องรอถึง 5 วินาทีจริง ๆ

Percentile บอกสิ่งที่ค่าเฉลี่ยซ่อนไว้ โดย p95 หมายถึงเวลาที่ 95% ของ request ทำได้ดีกว่านั้น และ p99 คือ 1% ที่แย่ที่สุด

เหตุผลที่ p99 สำคัญเป็นพิเศษคือ **โดยมากไม่ใช่ผู้ใช้แบบสุ่ม** แต่เป็นผู้ใช้ที่มีข้อมูลมากที่สุด เช่นลูกค้าที่มีคำสั่งซื้อเป็นหมื่นรายการ ซึ่ง query ของเขาหนักที่สุดโดยธรรมชาติ นั่นแปลว่า p99 มักตรงกับ**ลูกค้ารายใหญ่ที่สำคัญที่สุด** การมองแต่ค่าเฉลี่ยจึงเท่ากับมองข้ามกลุ่มที่เราเสียไม่ได้

ค่าเป้าหมายอ้างอิงคือ p50 น้อยกว่า 100 มิลลิวินาที, p95 น้อยกว่า 200 และ p99 น้อยกว่า 500 มิลลิวินาที นอกจากนี้ควรดู error rate โดย**แยก 4xx กับ 5xx** ออกจากกัน เพราะ 4xx คือผู้ใช้ส่งข้อมูลผิดส่วน 5xx คือระบบเราล้มเหลว ซึ่งมีความหมายต่างกันโดยสิ้นเชิง และควรดู queue lag, cache hit ratio, replication lag และ pool utilization ควบคู่กันเพื่อระบุว่า bottleneck อยู่ที่ชั้นใด
</details>

<details>
<summary><b>ระบบมี p95 สูงและ CPU ของ instance เต็ม ควรเพิ่มจำนวน instance ทันทีหรือไม่</b></summary>

โครง: ตอบไม่ → ลำดับที่ถูกต้อง → เหตุผลเชิงกลไก → ผลข้างเคียงของการ scale ผิดที่

ไม่ควรทำทันที ต้อง **วัดเพื่อหา bottleneck ที่แท้จริงก่อน** เสมอ

ลำดับที่ถูกต้องคือ วัดก่อน จากนั้นแก้ปัญหา query และ index เป็นอันดับแรก ตามด้วยการใส่ cache สำหรับข้อมูลที่อ่านบ่อย จากนั้นย้ายงานที่ช้าหรือไม่จำเป็นต้องตอบทันทีไปยัง queue แล้วจึงค่อยพิจารณา scale out เป็นขั้นสุดท้าย

เหตุผลเชิงกลไกคือ **การเพิ่ม instance ไม่ได้ทำให้ query ที่เขียนไม่ดีเร็วขึ้น** หากปัญหาที่แท้จริงคือ N+1 query หรือ full table scan เพราะไม่มี index การเพิ่มเครื่องเป็นเพียงการซื้อ query ที่ไม่ดีให้ทำงานเร็วขึ้นเท่านั้น และหาก bottleneck อยู่ที่ database การเพิ่ม instance ของแอปพลิเคชันจะให้ผลตอบแทนแทบเป็นศูนย์ เพราะทุกเครื่องยังคงไปรออยู่ที่ database ตัวเดิม

ที่แย่กว่านั้นคือการ scale ผิดจุดมี**ผลข้างเคียงที่ทำให้สถานการณ์แย่ลง** เนื่องจากจำนวน connection รวมจะเพิ่มขึ้นตามจำนวน instance ทำให้ database ที่กำลังรับภาระหนักอยู่แล้วต้องแบกเพิ่ม จนอาจเกิด "too many connections" และล่มทั้งระบบ

นอกจากนี้ต้องตรวจสอบด้วยว่า CPU ที่เต็มนั้นมาจากสาเหตุใด หากมาจากงาน CPU-bound  *((งานที่กินซีพียูล้วน ไม่ได้นั่งรอ I/O))* เช่นการสร้าง PDF หรือประมวลผลรูปภาพที่ทำอยู่ใน process เดียวกับ API งานเหล่านั้นกำลังยึด event loop  *((คิวงานเส้นเดียวของ Node ถ้าโดนยึดคือช้าทั้งระบบ))* และทำให้ทุก request ช้าตามไปด้วย ทางแก้ที่ถูกต้องคือย้ายไปยัง worker แยกผ่าน queue ไม่ใช่การเพิ่ม instance ของ API

เมื่อถึงขั้นตอน scale จริง ควรทดสอบด้วยเครื่องมืออย่าง k6 แบบ ramp-up ไปจนถึง peak แล้ว ramp-down เพื่อให้ได้ baseline ที่เปรียบเทียบก่อนและหลังได้ และพึงระวังว่าการเพิ่มเป็น 3 instance มักได้ throughput ราว 2.8 เท่า ไม่ใช่ 3 เท่า เพราะมี overhead ของ load balancer และการแย่งทรัพยากรที่ database
</details>

<details>
<summary><b>จงอธิบายว่า Nginx รู้ได้อย่างไรว่า instance ไหนล่ม และมีข้อจำกัดอะไร</b></summary>

โครง: แก้ความเข้าใจผิด → passive check ทำงานยังไง → active check ต้องใช้อะไร → SPOF

ต้องแก้ความเข้าใจผิดที่พบบ่อยเสียก่อน คือ **Nginx ไม่สามารถอ่านสถานะ health ของ Docker ได้** ทั้งสองเป็นคนละระบบที่ไม่รู้จักกัน คำสั่ง `HEALTHCHECK` ใน Dockerfile เพียงเปลี่ยนสถานะที่แสดงใน `docker ps` เท่านั้น หากไม่มี orchestrator ก็ไม่มีผู้ใดนำผลนั้นไปใช้ต่อ

สิ่งที่ Nginx รุ่นฟรีทำได้คือ **passive health check** เท่านั้น กล่าวคือจะถอด upstream ออกจากกลุ่มก็ต่อเมื่อ *request จริงของผู้ใช้* ล้มเหลวครบตามจำนวน `max_fails` ภายในช่วงเวลา `fail_timeout` ข้อจำกัดที่ตามมาคือต้องมีผู้ใช้จำนวนหนึ่งพบ error เสียก่อน Nginx จึงจะทราบว่า instance นั้นมีปัญหา

**Active health check** ซึ่งคือการที่ load balancer ยิงไปตรวจสุขภาพ upstream เองเป็นระยะโดยไม่ต้องรอ request จริงนั้น มีเฉพาะใน **Nginx Plus** ที่เป็นรุ่นเสียค่าใช้จ่าย หากต้องการพฤติกรรมนี้โดยไม่เสียค่าใช้จ่าย ต้องใช้ orchestrator ที่รองรับ เช่น Kubernetes ผ่าน readinessProbe หรือ Docker Swarm

ประเด็นนี้สำคัญเพราะผู้ที่เข้าใจผิดจะเชื่อว่าตนเองมีระบบ failover อยู่แล้วทั้งที่ไม่มี และจะทราบก็ต่อเมื่อระบบล่มจริง

ข้อจำกัดอีกประการคือ **Nginx ตัวเดียวเป็น single point of failure** หากล่ม ระบบทั้งหมดจะเข้าไม่ถึงแม้ instance เบื้องหลังจะทำงานปกติดี จึงต้องรัน Nginx อย่างน้อยสองตัวคู่กับ virtual IP หรือ DNS failover หรือใช้ managed load balancer ของผู้ให้บริการ cloud นอกจากนี้ต้องตั้ง proxy timeout ให้ครบ มิฉะนั้น upstream ที่ค้างจะยึด worker connection ของ Nginx จนหมดและลุกลามเป็น outage และต้อง forward header `X-Real-IP` กับ `X-Forwarded-For` ไม่เช่นนั้นระบบ rate limiting และ audit log ทั้งหมดจะเห็นแต่ IP ของ load balancer
</details>

## 9. ✅ เช็คตัวเองก่อนปิดบท

- อธิบายได้ว่า "เพิ่มเครื่องแล้วพังหนักกว่าเดิม" เกิดจากอะไรบ้าง อย่างน้อย 4 อาการ
- ท่องสูตร `instances × (1 + replicas) × poolSize` ได้ และรู้ว่าตัวคูณ replica มาจากไหน
- ตอบได้ว่าทำไม liveness ห้ามเช็ค DB
- รู้ว่า Nginx ฟรี**ทำ active health check ไม่ได้** และสไลด์เขียนผิดตรงไหน
- อธิบาย read-your-writes กับ replication lag ได้
- บอกลำดับ "วัด → query → cache → queue → scale" ได้พร้อมเหตุผล
