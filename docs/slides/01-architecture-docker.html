Architecture & Containerization

บทนี้ตอบคำถามเดียว: ก่อนจะเขียนโค้ดสักบรรทัด เราต้องตัดสินใจอะไรบ้าง แล้วจะส่งโค้ดนั้นไปรันบนเครื่องอื่นยังไงให้มันไม่พัง

Monolith vs Microservices (แอปก้อนเดียว vs แยกเป็นหลายบริการเล็ก) DevOps / CI-CD (dev กับ ops ทีมเดียวกัน / ทดสอบ-ดีพลอยอัตโนมัติ) Infrastructure as Code (เขียนโครงสร้างพื้นฐานเป็นไฟล์ที่เก็บใน git ได้) Container vs VM (แชร์ kernel ของเครื่องแม่ vs ยกทั้ง OS มาใหม่) Image / Layer / Cache (แม่พิมพ์ / ชั้นของแต่ละคำสั่ง / จำผลไว้ไม่ build ซ้ำ) Multi-stage build (build ในสเตจหนึ่ง แล้วหยิบเฉพาะผลลัพธ์ไปอิมเมจจริง) Secrets (ค่าลับ เช่นรหัส DB หรือ API key)

0. เรื่องที่จะเดินยาวทั้ง 6 บท

ก่อนอื่นขอปูภาพรวมให้ก่อน เพราะปัญหาของนายไม่ใช่ "ไม่รู้จัก Redis" แต่คือ "ไม่รู้ว่า Redis ไปโผล่ตรงไหนของภาพ" วิธีแก้ที่ตรงจุดที่สุดคือใช้ระบบเดียวตลอดทั้ง 6 บท แล้วให้มันค่อย ๆ เจ็บทีละแบบ เราก็แก้ทีละบท พอเดินครบภาพมันจะต่อกันเอง

ระบบที่ว่าคือ Flash Sale — ขายของลดราคาแรง ๆ จำนวนจำกัด คนแห่เข้ามาพร้อมกันเป็นพัน (ตรงกับ mini-project ที่นายทำพอดี)

อ่านบทนี้จบแล้วต้องได้อะไร

ต้องตอบได้สองข้อโดยไม่ต้องท่อง: "ทำไมไม่แตก microservices ตั้งแต่วันแรก" (แตกระบบเป็นหลายบริการเล็ก ๆ ที่ deploy แยกกันได้) และ "ทำไม Dockerfile ต้องเรียงบรรทัดแบบนั้น"

1. ปูพื้นฐาน: ปัญหาจริงคืออะไร

1.1 "บนเครื่องผมมันรันได้นะ"

สมมติเขียน Flash Sale API เสร็จบนโน้ตบุ๊กตัวเอง ใช้ Node 20 กับ PostgreSQL 16 บน macOS พอส่งไฟล์ให้เพื่อนไปรัน มันพัง เพราะเพื่อนใช้ Node 18 บน Windows แถมยังไม่ได้ลง PostgreSQL

ปัญหานี้ไม่ได้อยู่ที่โค้ด แต่อยู่ที่สภาพแวดล้อม (environment) ที่โค้ดวางอยู่บนนั้น ซึ่งมีของอยู่หลายชั้น:

  • เวอร์ชันของ runtime (Node 18 กับ 20 พฤติกรรมต่างกันจริง)
  • library ระดับระบบปฏิบัติการ (พวก openssl, libc ที่ native module ต้องใช้)
  • ตัวแปร environment (DATABASE_URL, REDIS_URL)
  • บริการข้างเคียงที่ต้องมี (PostgreSQL, Redis)

สรุปคือโค้ดไม่ได้รันอยู่ในสุญญากาศ มันรันอยู่บนกองของพวกนี้

ความคิดตั้งต้นของทั้งบท

ถ้าส่งแค่ "โค้ด" มันไม่พอ ต้องส่ง "โค้ด + สภาพแวดล้อมทั้งกอง" ไปด้วยกันเป็นก้อนเดียว นี่แหละคือเหตุผลที่ container มีอยู่ เรื่องที่เหลือในบทนี้เป็นแค่รายละเอียดของความคิดข้อนี้

1.2 ทางเลือกยุคก่อน: Virtual Machine

วิธีเดิมคือใช้ VM — จำลองคอมพิวเตอร์ขึ้นมาทั้งเครื่อง มีระบบปฏิบัติการของตัวเองเต็มรูปแบบ (เรียกว่า Guest OS) แล้วเอาแอปเราไปวางข้างใน มันแก้ปัญหาได้จริง แต่แพงมาก: image ขนาดหลาย GB, boot ทีนึงเป็นนาที, แล้วเครื่องหนึ่งรันได้ไม่กี่ตัว

1.3 แล้ว container ต่างจาก VM ยังไง

Container ไม่ได้จำลองเครื่อง มันคือ process ธรรมดาที่รันบน kernel ของเครื่องแม่ (kernel = แกนกลางของ OS ที่คุมฮาร์ดแวร์ให้ทุกโปรแกรม) แต่ถูกกั้นไว้ด้วยฟีเจอร์ของ Linux สองตัว:

  • namespace — ทำให้ process มองเห็นโลกแคบลง เห็นแค่ process ของตัวเอง ไฟล์ของตัวเอง network ของตัวเอง เปรียบเหมือนการปิดตาไม่ให้เห็นของคนอื่น
  • cgroups — จำกัดว่าใช้ CPU กับ RAM ได้เท่าไร เปรียบเหมือนล่ามโซ่ไม่ให้กินเกินโควตา

สองตัวนี้รวมกันก็ให้ความรู้สึกเหมือนอยู่คนละเครื่อง ทั้งที่จริง ๆ ยังอยู่บน kernel เดียวกัน

จุดที่ข้อสอบชอบถาม

เพราะ container แชร์ kernel กัน ถ้ามีช่องโหว่ระดับ kernel ผู้โจมตีก็ทะลุจาก container ออกไปถึงเครื่องแม่ได้ (เรียกว่า container escape) ฉะนั้นถ้ามีใครบอกว่า "container ปลอดภัยเท่า VM" อันนั้นผิด

ถ้าต้องการกั้นระดับที่รันโค้ดของคนแปลกหน้าได้จริง (multi-tenant) ต้องใช้ gVisor / Kata / Firecracker (ตัวรัน container ที่กั้นแน่นกว่า เกือบเท่า VM) หรือแยกเครื่องกันไปเลย และนี่คือเหตุผลตรง ๆ ที่ต้องใส่ USER node ใน Dockerfile — เพื่อลดสิทธิ์ที่ผู้โจมตีจะได้ตั้งแต่ก้าวแรก ถ้าเจาะเข้ามาแล้วเจอว่าตัวเองเป็น root มันไปต่อได้ง่ายกว่ามาก

2. Image, Layer และ Cache — หัวใจของ Dockerfile

2.1 แยกให้ออกก่อน: image ≠ container

เทียบกับสิ่งที่นายคุ้นอยู่แล้ว: image คือ class ส่วน container คือ instance ที่ new ออกมา จาก image ก้อนเดียวจะสร้าง container กี่ตัวก็ได้ แต่ละตัวมีชีวิตแยกกัน — และนี่แหละคือสิ่งที่ทำให้เรา scale ออกได้ในบทที่ 6

คำศัพท์ที่จะเจอตลอดบท
  • Dockerfile — สูตรอาหาร บอกว่าจะประกอบ image ยังไง
  • build — เอาสูตรไปทำจริงจนได้ image
  • image — ก้อนที่ประกอบเสร็จแล้ว พร้อมเอาไปรัน
  • registry — ที่เก็บ image ส่วนกลาง (Docker Hub, GitHub Container Registry) เอาไว้ push ขึ้นแล้วให้เครื่อง production pull ลงไปรัน
  • container — image ที่กำลังรันอยู่จริง
  • tag — ป้ายชื่อเวอร์ชันของ image เช่น node:20-alpine

2.2 ทุกบรรทัดใน Dockerfile = 1 layer

Docker build ไล่ทีละบรรทัด แต่ละบรรทัดสร้าง "ชั้น" ของ filesystem ซ้อนทับกัน (นึกถึงแผ่นใสวางซ้อน) แล้วแต่ละชั้นถูก cache ไว้ เพื่อไม่ต้องทำซ้ำในการ build ครั้งหน้า

กฎของ cache มีข้อเดียว แต่เป็นข้อที่อธิบายทุกอย่างในหัวข้อนี้:

กฎ cache ข้อเดียวที่ต้องจำ

ถ้า layer ที่ N เปลี่ยน → layer ที่ N+1 เป็นต้นไปต้อง build ใหม่หมด ต่อให้เนื้อหาเหมือนเดิมเป๊ะก็ตาม

เหตุผลคือแต่ละชั้นวางทับกัน ถ้าชั้นล่างเปลี่ยน Docker ก็รับประกันไม่ได้ว่าชั้นบนจะออกมาเหมือนเดิม เลยต้องทำใหม่ให้หมด

เพราะฉะนั้นถ้าจำกฎข้อเดียวข้างบนได้ นายจะคิดคำตอบเรื่องการเรียง Dockerfile ออกมาเองได้ ไม่ต้องท่องว่า "ต้อง COPY package.json ก่อน"

2.3 Multi-stage build (แบ่ง Dockerfile เป็นหลายช่วง แล้วหยิบแค่ผลลัพธ์ไป image สุดท้าย)

ปัญหาคือ ตอน build เราต้องใช้ของเยอะ — TypeScript compiler, devDependencies (แพ็กเกจที่ใช้แค่ตอน build/test ไม่ต้องมีตอนรันจริง), source code ทั้งหมด แต่ตอนรันจริงเราอยากได้แค่ dist/ กับ dependency ที่จำเป็นตอนรันเท่านั้น

ถ้า build ใน image เดียว ของที่ใช้ตอน build จะติดไปอยู่ใน image สุดท้ายด้วย image เลยบวมไปประมาณ 1.2GB แถมมีของให้โจมตีเยอะโดยไม่จำเป็น

# ---- stage 1: builder ----
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci                    # ติดตั้งครบ รวม devDependencies เพราะต้องใช้ tsc
COPY . .
RUN npm run build             # ได้ dist/

# ---- stage 2: production ----
FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev         # เอาเฉพาะ dependency ที่ใช้ตอนรัน
COPY --from=builder /app/dist ./dist   # ← หยิบมาแค่ผลลัพธ์
USER node
EXPOSE 3000
CMD ["node", "dist/main.js"]

ผลที่ได้คือ ~1.2GB → ~150MB ซึ่งข้อดีไม่ได้มีแค่ "เล็กลง" อย่างเดียว มันแปลว่า pull เร็วขึ้น, cold start (เวลาตั้งแต่สตาร์ทตัวใหม่จนพร้อมรับงาน) เร็วขึ้น, ตอน scale ออกก็เร็วขึ้น, ค่า network ถูกลง และช่องโหว่น้อยลงเพราะมีแพ็กเกจติดมาน้อยลง

⚠ สไลด์เขียนผิด — ระวังตอนตอบข้อสอบ
  1. สไลด์ 20 ที่ตั้งชื่อว่า "optimized" ใช้ไม่ได้จริง: stage builder รัน npm ci --only=production แล้ว COPY . . แต่ไม่มี npm run build แถม stage สุดท้ายทำ COPY --from=builder /app . ซึ่งลากทั้ง source และ node_modules มาหมด สรุปคือ multi-stage ไม่ได้ประโยชน์อะไรเลย ให้ยึดแบบสไลด์ 21 (โครงเดียวกับโค้ดข้างบน)

  4. version: '3.8' ใน docker-compose (ไฟล์เดียวสั่งรันหลาย container พร้อมกัน) เลิกใช้แล้วใน Compose v2 ใส่ไปก็ถูกเมินเฉย ๆ

Secret เข้ามาตอน runtime เท่านั้น ห้ามอยู่ใน image — เพราะอะไรที่ถูก build เข้าไปใน layer แล้วมันจะอยู่ตรงนั้นถาวรและอ่านย้อนได้

ถ้าทำแบบนี้อันตรายยังไงให้ทำแทน

4. Monolith (ทั้งระบบเป็นก้อนเดียว deploy พร้อมกันทีเดียว) vs Microservices

4.1 สองคำนี้ต่างกันที่ "ขอบเขตของการ deploy"

ไม่ได้ต่างกันที่จำนวนไฟล์หรือความสวยของโค้ดนะ แต่ต่างกันที่ หน่วยที่เรา deploy ออกไปพร้อมกัน

4.2 กฎการตัดสินใจ

คำตอบมาตรฐานของวิชานี้

เริ่มที่ monolith เสมอ แต่แบ่งโมดูลตาม domain ตั้งแต่วันแรก (เรียกว่า modular monolith) แล้วค่อยแตกออกเมื่อมีเหตุผลที่วัดได้ เท่านั้น เช่น เจอ bottleneck เฉพาะจุดจากการวัดจริง หรือทีมโตเกิน 15–20 คนจนชนกันที่ codebase เดียว

เหตุผลลึก ๆ มีสองข้อ:

  1. วันแรกเรายังไม่รู้ domain boundary ที่แท้จริง (เส้นแบ่งว่าเรื่องไหนควรเป็นของ service ไหน ตามงานจริงของธุรกิจ) — และการแตก service ผิดที่ แพงกว่าการรวมกลับมาก เพราะเราแตก database ไปแล้ว จะรวมกลับต้อง migrate ข้อมูลใหม่หมด
  2. Microservices ไม่ได้แถม performance มาให้ฟรี — มันเอา in-process call (เรียกฟังก์ชันในโปรเซสเดียวกัน เร็วระดับนาโนวินาที ไม่มีทางพลาด) ไปแลกกับ network call (ยิงข้ามเครื่อง ช้ากว่าเป็นพันเท่า และล้มเหลวได้ตลอด) ซึ่งช้ากว่า เราจ่ายเงินก้อนนี้เพื่อซื้อ "ความเป็นอิสระของทีม" ไม่ใช่ซื้อความเร็ว ตรงนี้คนเข้าใจผิดกันเยอะ

4.3 "Microservices tax" — ค่าใช้จ่ายที่มองไม่เห็น

พอแตก service ปุ๊บ เราได้ปัญหาชุดใหม่มาฟรี ๆ ที่ต้องมีคนดูแล: service discovery (ทำยังไงให้ service หากันเจอ เวลามันย้ายเครื่องหรือเปลี่ยน IP), distributed tracing (ตามรอย 1 request ว่าวิ่งผ่าน service ไหนบ้าง ช้าตรงไหน), contract testing (เทสว่า service ที่คุยกันยังส่งของตามสัญญาเดิม ไม่มีใครแอบเปลี่ยนฟอร์แมต), API versioning (ออก API เวอร์ชันใหม่โดยไม่ทำของเก่าที่คนยังใช้อยู่พัง), partial failure (บาง service ล่ม บางตัวยังอยู่ ระบบครึ่ง ๆ กลาง ๆ ที่ต้องตามเก็บ), retry storm (ทุกตัวลองใหม่พร้อมกันจนถล่มตัวที่กำลังจะฟื้น), saga (แตก transaction ยาวเป็นสเต็ปย่อย พลาดกลางทางก็ย้อนคืนทีละสเต็ป)

ดูจากของจริง — Uber ใช้ microservices ตั้งแต่วันแรกจนมีประมาณ 2,200 service และต้องตั้ง platform team ทั้งทีมมาดูแลโครงสร้างพวกนี้โดยเฉพาะ ส่วน Instagram เริ่มด้วย Django monolith โตถึง 30 ล้านผู้ใช้แล้วค่อยแยก Feed / Stories / Messaging ออกมา

คำถามทดสอบก่อนตัดสินใจแตก

ถามตัวเองว่า "ธุรกิจรับ eventual consistency ได้ไหม" (ข้อมูลแต่ละที่ยังไม่ตรงกันชั่วคราว แต่เดี๋ยวก็ตรงกันเอง) เพราะพอเป็น database-per-service (แต่ละ service มี DB ของตัวเอง ห้ามยุ่ง DB ของคนอื่น) แล้ว ACID (คุณสมบัติ 4 ข้อที่การันตีว่า transaction จะไม่ทำข้อมูลเพี้ยน — transaction = กลุ่มคำสั่ง DB ที่ต้องสำเร็จทั้งหมดหรือไม่เกิดอะไรเลย) ข้าม service ทำไม่ได้ ถ้าคำตอบคือรับไม่ได้ (เช่น ตัดสต็อกกับตัดเงินต้องเกิดพร้อมกันเป๊ะ) → อย่าแตก จบ

5. DevOps, CI/CD และ IaC — สามคำนี้ต่างกันยังไง

สามคำนี้มักถูกพูดปนกันจนงง แยกแบบนี้:

คำคืออะไรมาแก้ปัญหาอะไร
DevOpsวัฒนธรรม/แนวปฏิบัติที่ลบกำแพงระหว่างคนเขียนโค้ดกับคนดูแลเครื่องเมื่อก่อน dev โยนโค้ดข้ามกำแพงให้ ops แล้วพอพังก็โทษกันไปมา
CI/CDpipeline อัตโนมัติ: Code → Build → Test → Deploy → Monitorทำมือแล้วช้า ลืมขั้นตอน และแต่ละครั้งทำไม่เหมือนกัน
IaCเขียนโครงสร้างพื้นฐานเป็นไฟล์ที่เก็บใน git ได้ เช่น docker-compose.ymlSSH เข้าไปตั้งค่ามือ = ไม่มีใครรู้ว่าเซิร์ฟเวอร์ตั้งค่าไว้ยังไง และสร้างใหม่ให้เหมือนเดิมไม่ได้

ทั้งสามอย่างเล็งไปที่เป้าเดียวกันคือ ทำให้ผลลัพธ์ทำซ้ำได้ (reproducible) ซึ่งเป็นเหตุผลเดียวกับที่ห้ามใช้ tag latest

เรื่อง latest ขยายหน่อย: มันไม่ใช่ "เวอร์ชันล่าสุดที่เสถียร" อย่างที่ชื่อชวนให้คิด มันเป็นแค่ป้ายธรรมดาที่ชี้ไป image ตัวไหนก็ได้และเปลี่ยนได้ตลอดโดยที่เราไม่รู้ ผลคือ build ไม่ reproducible (วันนี้ผ่าน พรุ่งนี้พัง ทั้งที่ไม่มีใครแก้อะไร) และ rollback ไม่ได้เพราะไม่รู้ว่าตัวที่เคยใช้ได้คือตัวไหน ทางที่ถูกคือ pin tag ให้ชัด แล้ว tag image ของเราด้วย commit SHA (รหัสประจำ commit ใช้ชี้ว่า image นี้มาจากโค้ดตัวไหน) เพิ่มด้วย เพื่อให้ย้อนได้ว่า image ที่รันอยู่ตรงกับโค้ด commit ไหน

6. เรื่อง runtime ที่มักถูกลืม

เรื่องถ้าไม่ทำจะเป็นยังไง
--memory --cpus --pids-limitnoisy neighbor — container ตัวเดียวที่ memory leak จะดูดทรัพยากรจนเพื่อนบ้านตายหมด
Node เก่ากว่า 18 + cgroupNode รุ่นเก่าอ่าน cgroup limit ไม่เห็น เลยตั้ง heap (หน่วยความจำที่ Node ขอไว้เก็บ object) ตาม RAM ของเครื่องแม่ แล้วโดน OOM-kill (ระบบฆ่าโปรเซสทิ้งเพราะใช้ RAM เกินโควตา) ต้องตั้ง NODE_OPTIONS=--max-old-space-size ให้ตรงกับ --memory
custom networkcontainer ที่อยู่ network เดียวกันคุยกันด้วยชื่อ container ได้เลย เช่น postgresql://db:5432 ไม่ต้องรู้ IP
depends_onรอแค่ container "start" ไม่ได้รอ "พร้อมใช้งาน" แอปเลยไปต่อ DB ที่ยังไม่พร้อมแล้ว crash แก้ด้วย condition: service_healthy หรือใส่ retry ในแอป
docker-compose down -v-v ลบ volume (พื้นที่เก็บข้อมูลนอกตัว container ที่ไม่หายตอนลบ container) = ลบข้อมูล DB ทั้งหมด อย่าติดนิสัยพิมพ์ทุกครั้ง
ไม่ validate env ตอน bootสะกด env var (ค่า config ที่ส่งเข้าแอปจากข้างนอก ไม่ต้องแก้โค้ด) ผิดแล้วแอปยังขึ้นได้ปกติ ไปพังตอนลูกค้าใช้งาน ควรให้มัน fail fast (พังตั้งแต่ตอนสตาร์ทไปเลย ดีกว่าปล่อยไปพังตอนลูกค้าใช้) ตั้งแต่ boot

8. 📝 คลังคำตอบอัตนัย

ข้อสอบแนวอธิบายเหตุผลต้องการโครงคำตอบแบบเดิมเสมอ: นิยาม → กลไก → ตัวอย่างรูปธรรม → trade-off ลองปิดคำตอบแล้วเขียนเองก่อนนะ อ่านเฉย ๆ มันจะรู้สึกว่าเข้าใจแล้วทั้งที่เขียนออกมาไม่ได้

ทำไมโปรเจกต์ใหม่ควรเริ่มด้วย monolith แทนที่จะเป็น microservices จงอธิบายพร้อมเหตุผล
โครง: หลักการ → เหตุผล 3 ข้อ (ไม่รู้ boundary / ต้นทุน ops / เสีย ACID) → ทางสายกลาง → เงื่อนไขที่ควรแตกจริง

เพราะในวันแรกเรายังไม่รู้ domain boundary ที่แท้จริง ของระบบ การแตก service ผิดที่มีต้นทุนสูงกว่าการรวมกลับมาก เนื่องจาก microservices มาพร้อม database-per-service ซึ่งย้อนกลับยาก

ข้อสอง microservices มี ต้นทุน operation ที่มองไม่เห็น ("microservices tax") ได้แก่ service discovery, distributed tracing, contract testing, API versioning และการจัดการ partial failure ทั้งหมดนี้ต้องมีคนดูแล — Uber ที่มีประมาณ 2,200 service ต้องมี platform team โดยเฉพาะ ทีมเล็กจึงจ่ายค่านี้ก่อนที่จะได้ประโยชน์อะไรเลย

ข้อสาม เมื่อแยก database แล้ว ACID transaction ข้าม service ทำไม่ได้ ต้องเปลี่ยนไปใช้ Saga หรือ compensating transaction (คำสั่งย้อนผลของสเต็ปที่ทำไปแล้ว เช่น คืนสต็อก คืนเงิน) และยอมรับ eventual consistency ซึ่งบางธุรกิจรับไม่ได้

ทางที่ควรทำคือ modular monolith คือ deploy ก้อนเดียวแต่แบ่งโมดูลตาม domain ให้ชัดตั้งแต่วันแรก เมื่อถึงวันที่ต้องแตกจริงก็ "ยกโมดูล" ออกไปได้โดยไม่ต้อง rewrite และควรแตกเมื่อมีเหตุผลที่วัดได้เท่านั้น เช่น bottleneck เฉพาะจุดที่วัดเจอ หรือทีมโตเกิน 15–20 คนจนชนกันที่ codebase เดียว เทียบได้กับกรณี Instagram ที่ใช้ Django monolith จนถึง 30 ล้านผู้ใช้ก่อนค่อยแยก

อธิบายกลไก layer caching ของ Docker และเหตุผลที่ต้อง COPY package*.json ก่อน COPY . .
โครง: layer คืออะไร → กฎ invalidate → ผลลัพธ์ที่ตามมา → ตัวเลขจริง

ทุกคำสั่งใน Dockerfile สร้าง filesystem layer หนึ่งชั้นที่ซ้อนทับกัน และ Docker จะ cache แต่ละ layer ไว้ กฎคือ เมื่อ layer ใดเปลี่ยน layer ที่อยู่ถัดลงมาทั้งหมดจะถูก invalidate และต้อง build ใหม่ แม้เนื้อหาจะเหมือนเดิมก็ตาม

ถ้าเขียน COPY . . ก่อน RUN npm ci การแก้โค้ดเพียงตัวอักษรเดียวจะทำให้ layer ของ COPY เปลี่ยน ส่งผลให้ npm ci ต้องรันใหม่และดาวน์โหลด dependency ทั้งหมดอีกครั้ง

แต่ถ้า COPY package*.json ./ แล้วตามด้วย RUN npm ci ก่อน จากนั้นค่อย COPY . . — layer ของ npm ci จะเปลี่ยนก็ต่อเมื่อ dependency เปลี่ยนจริงเท่านั้น การแก้โค้ดตามปกติจะยังได้ cache HIT ทำให้ build ลดจากประมาณ 5 นาทีเหลือประมาณ 30 วินาที

หลักการทั่วไปที่สรุปได้จากกฎนี้คือ เรียงคำสั่งจากสิ่งที่เปลี่ยนน้อยที่สุดไปหาสิ่งที่เปลี่ยนบ่อยที่สุดเสมอ

Multi-stage build คืออะไร แก้ปัญหาอะไร และให้ประโยชน์อะไรบ้าง
โครง: ปัญหา → กลไก → ประโยชน์ 3 ด้าน (ขนาด/ความปลอดภัย/ความเร็ว) → ตัวเลข

ปัญหาคือของที่จำเป็นตอน build ได้แก่ TypeScript compiler, devDependencies และ source code นั้นไม่จำเป็นตอน run ถ้า build ใน stage เดียวของเหล่านี้จะติดไปอยู่ใน image สุดท้าย

Multi-stage แก้ด้วยการแบ่ง Dockerfile เป็นหลาย stage โดย stage builder ติดตั้ง dependency ครบและรัน npm run build ส่วน stage สุดท้ายเริ่มจาก base ใหม่ ติดตั้งเฉพาะ production dependency ด้วย npm ci --omit=dev แล้วใช้ COPY --from=builder /app/dist ./dist เพื่อหยิบมาเฉพาะ artifact (ไฟล์ผลลัพธ์ที่ได้จากการ build เช่น dist/) ที่ต้องใช้จริง

ประโยชน์มีสามด้าน หนึ่งคือขนาด ลดจากประมาณ 1.2GB เหลือประมาณ 150MB เมื่อใช้ร่วมกับ alpine base สองคือความปลอดภัย เพราะ attack surface (ช่องทางทั้งหมดที่ผู้โจมตีเอื้อมถึงได้ ยิ่งมีของติดมาเยอะยิ่งเสี่ยง) เล็กลงจากการที่ไม่มี build tool และ source code ติดไปด้วย และสามคือความเร็วในการดำเนินงาน ทั้ง pull เร็วขึ้น cold start เร็วขึ้น rolling update และ auto-scale เร็วขึ้นตาม รวมถึงค่า network egress (ค่าข้อมูลขาออกจากคลาวด์ ที่คิดเงินตามปริมาณ) ถูกลง

ทำไมห้าม hardcode secret ลงใน Docker image และควรจัดการ secret อย่างไรใน production
โครง: กลไกที่ทำให้อันตราย → ทางที่ถูก → ทำไม secrets manager ไม่ใช่แค่ "ปลอดภัยกว่า"

เพราะ image ประกอบด้วย layer ที่อ่านย้อนได้และลบไม่ได้ ผู้ใดก็ตามที่ pull image ได้สามารถรัน docker history เพื่อดูค่าที่ถูก build เข้าไปทั้งหมด การลบ secret ออกใน layer ถัดมาไม่ช่วย เพราะ layer เดิมยังคงอยู่

สิ่งที่ถูกต้องคือ ส่ง secret เข้ามาตอน runtime ผ่าน environment variable ซึ่งทำให้ image เดียวกันรันได้ทุก environment หมายความว่า binary ที่ผ่านการทดสอบบน staging คือตัวเดียวกับที่ขึ้น production

ใน production ควรดึงจาก secrets manager เพราะได้สองอย่างที่ไฟล์ให้ไม่ได้ คือ audit log ว่าใครอ่าน secret ตอนไหน และความสามารถในการ rotate โดยไม่ต้อง redeploy ซึ่งจำเป็นมากเวลาเกิดเหตุ ส่วน --env-file ใช้ได้เฉพาะ dev เพราะค่ายังอ่านได้ผ่าน docker inspect

เพิ่มเติมคือต้องใส่ .env ทั้งใน .gitignore และ .dockerignore เสมอ และหากเผลอ commit ไปแล้ว การลบไฟล์ไม่เพียงพอ ต้อง rotate secret เพราะค่าเดิมยังคงอยู่ใน git history

Container กับ Virtual Machine ต่างกันอย่างไร และมีนัยอะไรต่อความปลอดภัย
โครง: กลไกที่ต่างกัน → ผลด้าน performance → ผลด้าน security (จุดที่คนตอบไม่ครบ)

VM จำลองเครื่องทั้งเครื่องและมี Guest OS พร้อม kernel ของตัวเอง ส่วน container คือ process ที่รันบน kernel ของ host โดยถูก isolate ด้วย namespace ซึ่งจำกัดสิ่งที่มองเห็น เช่น process, filesystem และ network และ cgroups ซึ่งจำกัดทรัพยากรที่ใช้ได้

ผลด้าน performance คือ container ไม่มี Guest OS จึงมีขนาดระดับ MB แทนที่จะเป็น GB, start ในระดับวินาทีแทนที่จะเป็นนาที และรันได้หนาแน่นกว่ามากต่อเครื่อง

ผลด้านความปลอดภัยเป็นจุดสำคัญ เนื่องจาก container แชร์ kernel เดียวกับ host ช่องโหว่ระดับ kernel จึงสามารถทะลุจาก container ไปถึง host ได้ ซึ่งเรียกว่า container escape ทำให้ระดับการแยกส่วนอ่อนกว่า VM อย่างมีนัยสำคัญ หากต้องการ isolation ระดับ multi-tenant จริง ๆ ต้องใช้ gVisor, Kata Containers หรือ Firecracker หรือแยก node (เครื่องเซิร์ฟเวอร์ 1 เครื่องในคลัสเตอร์ คนละความหมายกับ Node.js) กันไปเลย ด้วยเหตุผลเดียวกันนี้จึงต้องรัน container ด้วย USER node ไม่ใช่ root เพื่อลดสิทธิ์ที่ผู้โจมตีจะได้รับหากเจาะเข้ามาทางแอปพลิเคชันได้

เพื่อนบอกว่า "ใส่ depends_on: [db] แล้ว แอปจะรอ database พร้อมก่อนค่อยเริ่ม" จริงหรือไม่ เพราะอะไร
โครง: ปฏิเสธ → บอกว่ามันทำอะไรจริง ๆ → ผลที่เกิด → 2 ทางแก้

ไม่จริง depends_on รับประกันเพียงลำดับการ start ของ container เท่านั้น ไม่ได้รอให้ service ภายในพร้อมรับ connection ในทางปฏิบัติ PostgreSQL ใช้เวลาอีกหลายวินาทีหลัง container เริ่มทำงานกว่าจะยอมรับ connection ได้

ผลคือแอปพลิเคชันจะพยายามเชื่อมต่อ database ที่ยังไม่พร้อมแล้ว crash ตั้งแต่ตอน boot ซึ่งอาการนี้จะปรากฏเป็นครั้งคราวขึ้นกับจังหวะ ทำให้วินิจฉัยได้ยาก

แก้ได้สองทาง ทางแรกคือใช้ depends_on ร่วมกับ condition: service_healthy คู่กับการประกาศ healthcheck ของ service นั้น ทางที่สองคือใส่ retry logic ในแอปพลิเคชันเอง ซึ่งทนทานกว่าเพราะครอบคลุมกรณีที่ database ล่มระหว่างการทำงานด้วย ไม่ใช่เฉพาะตอน boot

ทำไมห้ามใช้ tag latest ใน production
โครง: latest คืออะไรจริง ๆ → ผล 2 ข้อ → ทางแก้

latest ไม่ใช่ "เวอร์ชันล่าสุดที่เสถียร" ตามที่ชื่อสื่อ แต่เป็นเพียง tag ธรรมดาที่ชี้ไปยัง image ตัวใดก็ได้ และเปลี่ยนได้ตลอดเวลาโดยที่เราไม่รู้

ผลที่ตามมามีสองข้อ ข้อแรกคือ build ไม่ reproducible — build วันนี้กับพรุ่งนี้อาจได้ผลต่างกันทั้งที่โค้ดเหมือนเดิม ทำให้เกิดกรณีที่ระบบพังโดยไม่มีใครแก้อะไร ซึ่งวินิจฉัยได้ยากมาก ข้อที่สองคือ rollback ไม่ได้ เพราะไม่ทราบว่าเวอร์ชันที่เคยทำงานได้คือ image ตัวใด

ทางที่ถูกต้องคือ pin tag ให้ชัดเจน เช่น node:20.11-alpine และ tag image ของเราเองด้วย commit SHA เพื่อให้ทราบว่า image ที่รันอยู่ตรงกับโค้ด commit ใด ซึ่งทำให้ rollback แม่นยำและตรวจสอบย้อนหลังได้ เรื่องนี้มีเป้าหมายเดียวกับหลัก Infrastructure as Code คือทำให้ทุกอย่าง reproducible

9. ✅ เช็คตัวเองก่อนปิดบท

  • พูด "กฎ cache ของ layer" ได้ในประโยคเดียว แล้วอธิบายเหตุผลของการเรียง Dockerfile ต่อจากกฎนั้นได้เอง
  • บอกได้ว่า multi-stage ให้ประโยชน์ 3 ด้าน ไม่ใช่แค่ "image เล็กลง"
  • ตอบได้ว่าทำไม .dockerignore เป็นเรื่อง security ไม่ใช่แค่ performance
  • บอกเงื่อนไขที่ ควร แตก microservices ได้ และเงื่อนไขที่ ห้าม แตก
  • อธิบายได้ว่า depends_on ไม่พอเพราะอะไร
  • รู้ว่าทำไม container ไม่ใช่ VM ในแง่ security
