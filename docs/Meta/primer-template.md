## 🎯 หัวใจของเอกสารประเภทนี้

เอกสารปูพื้นที่ดีทำ 2 อย่างพร้อมกัน และคนส่วนใหญ่ทำได้แค่อย่างเดียว:

| | ทำอะไร | ถ้าขาดจะเป็นยังไง |
| :--- | :--- | :--- |
| **ชั้นโครง** | เรียงว่า ทำไม → ใคร → เดินยังไง → พังยังไง → ทดสอบตัวเอง | อ่านแล้วรู้เรื่องเป็นจุดๆ แต่ไม่เห็นว่ามันต่อกันยังไง |
| **ชั้นปูพื้น** | สอนศัพท์และแนวคิดที่คนอ่านยังไม่มี **ณ จุดที่เขาต้องใช้มันพอดี** | โครงสวยแต่คนอ่านตกตั้งแต่หน้า 2 เพราะเจอศัพท์ที่ไม่รู้จัก |

เทมเพลตฉบับแรกมีแต่ชั้นโครง ฉบับนี้เพิ่มชั้นปูพื้นเข้ามา และมันคือส่วนที่ยาวที่สุดในไฟล์ — ตั้งใจให้เป็นแบบนั้น

## 📥 ตัวแปร 11 ตัว

| ตัวแปร | ความหมาย | ตัวอย่าง |
| :--- | :--- | :--- |
| `SUBJECT` | เรื่องที่จะปูพื้น | ระบบ Flash Sale ที่กัน oversell |
| `ARTIFACT` | "ของ" ที่ทุกอย่างหมุนรอบ — ใช้ใน §7 | order 1 ใบ |
| `AUDIENCE` | คนอ่านคือใคร **ให้เจาะจงกว่าที่คิด** | นักศึกษาปี 3 เขียน REST API ต่อ DB เป็น ไม่เคยแตะ Redis |
| `FLOOR` | เพดานล่าง — สิ่งที่ถือว่ารู้แล้ว ไม่ต้องสอน | HTTP method, SQL พื้นฐาน, JSON |
| `FROM_ZERO` | ศัพท์/แนวคิดที่ต้องสอนตั้งแต่ศูนย์ **ลิสต์ให้ครบ อย่ารวบ** | Redis, cache-aside, TTL, race condition, message queue, worker, replication, atomic |
| `SOURCE_OF_TRUTH` | ชื่อแหล่งที่ถือว่าถูก (ใช้เป็นชื่อเรียกในเอกสาร) | `architecture.md` |
| `SOURCE_MATERIAL` | **เนื้อหาเต็มของแหล่งนั้น** วางลงในบล็อกใน prompt | (แปะทั้งไฟล์) |
| `GOAL` | อ่านจบแล้วต้องทำอะไรได้ — เป็นกริยา ไม่ใช่ "เข้าใจ" | ตัดสินใจตอนเขียนโค้ดได้เองโดยไม่ต้องถามซ้ำ |
| `LANGUAGE` | ภาษาที่ output ต้องใช้ | ไทย (ศัพท์เทคนิคคงภาษาอังกฤษ) |
| `LENGTH` | **เพดาน** ความยาว ไม่ใช่เป้า | ไม่เกิน 1,000 บรรทัด |
| `DATE` | วันที่ที่เนื้อหาอ้างอิง (LLM ไม่รู้วันนี้) | 2026-08-26 |

`FLOOR` กับ `FROM_ZERO` เป็นคู่กัน — ตัวหนึ่งบอกว่าอย่าเสียเวลาสอนอะไร อีกตัวบอกว่าต้องสอนอะไร
ถ้าเว้น `FLOOR` ว่าง LLM จะเดาเอง แล้วมักเดาสูงเกินไป (สอนน้อยไป) หรือต่ำเกินไป (อธิบาย HTTP ให้โปรแกรมเมอร์ฟัง)

# 📚 เครื่องมือปูพื้นฐาน — ส่วนที่สำคัญที่สุดของไฟล์นี้

โครง 13 หัวข้อบอกว่า *จัดหน้ายังไง* ส่วนนี้บอกว่า *สอนยังไง* ถ้าใส่แต่โครงจะได้สารบัญที่สวยแต่คนอ่านตกกลางทาง

## 1. บันไดความรู้ — ทำก่อนเขียนบรรทัดแรก

ก่อนลงมือเขียน §0 ให้สร้าง "บันได" ขึ้นมาก่อน แล้ว**แสดงมันไว้ในเอกสารด้วย** (ท้าย §0):

1. แตก `FROM_ZERO` ออกเป็นศัพท์ย่อยให้หมด — คำที่ซ่อนอยู่ในคำ เช่น "cache-aside" ซ่อน "cache hit/miss", "TTL", "eviction" ไว้ข้างใน
2. เรียงตาม **ลำดับพึ่งพา** — ตัวไหนต้องรู้ก่อนถึงจะเข้าใจตัวถัดไป
3. ระบุว่าแต่ละตัวจะถูกสอนที่ § ไหน
4. **ไล่ตรวจย้อน**: ถ้ามีศัพท์ตัวไหนถูก*ใช้*ก่อน § ที่*สอน* ให้ย้ายจุดสอนขึ้นมา หรือใส่กล่อง 📖 ตรงจุดที่ใช้ครั้งแรก

ตารางบันไดหน้าตาแบบนี้:

| ลำดับ | ศัพท์ | ต้องรู้อะไรก่อน | สอนที่ | ใช้ครั้งแรกที่ |
| :--- | :--- | :--- | :--- | :--- |
| 1 | race condition | — | §1.1 | §1.1 ✅ |
| 2 | atomic | race condition | §1.3 | §1.3 ✅ |
| 3 | cache hit / miss | — | §2.5 | §2.5 ✅ |
| 4 | TTL | cache hit/miss | §2.5 | §3.2 ✅ |

ช่อง "ใช้ครั้งแรกที่" ต้องอยู่**หลังหรือเท่ากับ**ช่อง "สอนที่" เสมอ ถ้าไม่ใช่แปลว่าบันไดพัง

## 2. หนึ่งศัพท์ต้องสอนครบ 5 ช่อง

ห้ามสอนศัพท์ด้วยนิยามเปล่าๆ ทุกตัวต้องมีครบ:

| ช่อง | ทำอะไร | ตัวอย่างจากของจริง |
| :--- | :--- | :--- |
| **(ก) ปัญหาเดิม** | ก่อนมีของสิ่งนี้ คนแก้ปัญหานี้ยังไง แล้วมันแย่ตรงไหน | "ถ้าไม่มี cache ทุก request ต้องยิง DB — 1,000 คนอ่านพร้อมกัน DB ตาย" |
| **(ข) นิยามหนึ่งประโยค** | สั้น ตรง ไม่มีศัพท์ที่ยังไม่ได้สอน | "Cache คือที่เก็บของชั่วคราวที่อ่านเร็วกว่าแหล่งจริง" |
| **(ค) อุปมาที่ยึดกับ FLOOR** | เทียบกับของที่คนอ่าน**รู้อยู่แล้ว**จริงๆ | "เหมือนจดเบอร์ที่โทรบ่อยไว้หน้าแรก แทนที่จะเปิดสมุดทุกครั้ง" |
| **(ง) ในงานเราคือตัวไหน** | ชื่อจริง เลขจริง ไฟล์จริง — ช่องนี้คือตัวที่กันไม่ให้กลายเป็นตำรา | "`redis-cache` :6379 เก็บ key `catalog:page:1:limit:10`" |
| **(จ) กับดักของศัพท์นี้** | ความเข้าใจผิดที่คนเจอศัพท์นี้ครั้งแรกมักติด | "cache ไม่ใช่ 'ที่เก็บเร็ว' เฉยๆ — มันคือที่เก็บที่ **ยอมให้ข้อมูลเก่าได้**" |

ช่อง (ค) มีกฎเหล็ก: **อุปมาต้องยึดกับสิ่งที่อยู่ใน `FLOOR` เท่านั้น** ถ้าอธิบาย Redis ด้วยการเทียบกับ Memcached แล้วคนอ่านไม่รู้จัก Memcached เท่ากับไม่ได้อธิบาย
ช่อง (จ) สำคัญกว่าที่คิด — คนที่พอรู้ศัพท์แบบผิดๆ อันตรายกว่าคนที่ไม่รู้เลย

## 3. ศัพท์ถูกสอน 3 ที่ คนละหน้าที่กัน

| ที่ | รูปแบบ | หน้าที่ | ความยาว |
| :--- | :--- | :--- | :--- |
| **กล่อง 📖 แทรกกลางเนื้อ** | blockquote ขึ้นต้นด้วย 📖 วางตรงที่ศัพท์โผล่ครั้งแรก | สอนให้พอเดินต่อได้ ไม่ให้คนอ่านต้องเลื่อนไปหา glossary | 3–6 บรรทัด ครบ (ก)(ข)(ค) |
| **ช่อง "ศัพท์" ท้ายตัวละครใน §2** | บรรทัดสุดท้ายของตัวละครแต่ละตัว | สอนศัพท์ที่ *มากับ* ตัวละครนั้น พร้อม (ง) ในงานเราคือตัวไหน | 1 บรรทัดต่อศัพท์ |
| **§10 Glossary** | ตาราง 2 คอลัมน์ | **รวบของที่สอนไปแล้ว** ไว้เปิดหาตอนลืม | 1 บรรทัดต่อศัพท์ |

> ### ⚠️ Glossary ไม่ใช่ที่สอน
> ถ้าศัพท์ตัวไหนถูกอธิบาย**ครั้งแรก**ใน §10 แปลว่าเอกสารพลาดไปแล้ว
> เพราะคนอ่านเจอมันกลางเอกสาร ไม่เข้าใจ แล้วไม่มีอะไรบอกว่าให้ไปเปิดท้ายเล่ม
> §10 เรียงแบบ **จัดกลุ่มตามหัวข้อ** (ตามที่มันโผล่มา) ไม่ใช่เรียง ก–ฮ

## 4. กฎห้ามใช้ศัพท์ก่อนสอน

กฎข้อเดียวที่ตรวจได้เชิงกล และเป็นตัวชี้ขาดว่าเอกสารปูพื้นจริงหรือแค่อ้างว่าปูพื้น:

> **ศัพท์ทุกตัวใน `FROM_ZERO` ห้ามปรากฏในเอกสารก่อนจุดที่มันถูกสอน**
> ยกเว้นในตารางบันไดความรู้ (§0) ซึ่งเป็นสารบัญของการสอน ไม่ใช่การใช้งาน

ตรวจได้ด้วยการค้นหาศัพท์ทีละตัว แล้วดูว่าที่พบครั้งแรกคือจุดสอนหรือจุดใช้

## 5. เทียบระดับความลึกกับ AUDIENCE

`AUDIENCE` ไม่ได้เปลี่ยนแค่น้ำเสียง มันเปลี่ยน**จำนวนชั้นที่ต้องขุดลงไป**:

| ระดับคนอ่าน | สอนศัพท์ลึกแค่ไหน | ใช้อุปมาไหม | ลงกลไกข้างในไหม |
| :--- | :--- | :--- | :--- |
| ไม่เคยแตะสาขานี้ | ครบ 5 ช่อง + อุปมา 2 อัน | ทุกตัว | ไม่ — บอกแค่ว่ามันรับประกันอะไร |
| อยู่สาขานี้ แต่ไม่เคยแตะเรื่องนี้ | ครบ 5 ช่อง | เฉพาะตัวที่สวนสัญชาตญาณ | เฉพาะตัวที่ถ้าไม่รู้กลไกจะใช้ผิด |
| เคยแตะมาบ้าง | (ข)(ง)(จ) พอ | ไม่ต้อง | ใช่ — เพราะเขาจะเถียงถ้าไม่มีเหตุผล |

ถ้า `AUDIENCE` เขียนไว้กว้างเกิน (เช่น "นักศึกษา") ให้ **ถามกลับก่อนเขียน** อย่าเดา

## 🧩 ตารางแปลงข้ามศาสตร์

โครงข้างล่างเขียนด้วยคำกลาง ตารางนี้บอกว่าแต่ละส่วน "แปลว่าอะไร" ในวิชาของคุณ

| § | ชื่อกลาง | วิศวกรรมซอฟต์แวร์ | กฎหมาย | แพทยศาสตร์ | เศรษฐศาสตร์ | ประวัติศาสตร์ | คณิตศาสตร์ |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| 1 | **แก่นที่ยาก** | race condition | ช่องว่างของตัวบท | ทำไมโรคนี้วินิจฉัยยาก | ทำไมกลไกราคาถึงไม่พอ | ทำไมเหตุการณ์นี้ยังถกกันไม่จบ | ทำไมทฤษฎีบทนี้ไม่ trivial |
| 2 | **ตัวละคร** | service / datastore | สถาบันในกระบวนการ | อวัยวะ / เชื้อ / ยา | ผู้เล่นในตลาด | ผู้เล่นและปัจจัย | นิยาม / สัจพจน์ / เลมมา |
| 3 | **เส้นทาง** | read path / write path | ฟ้อง → สืบ → พิพากษา | กลไกก่อโรค → อาการ | กลไกส่งผ่านนโยบาย | ลำดับเหตุปัจจัย | เส้นการพิสูจน์ |
| 6 | **หลายชั้น** | เร็ว vs ถูก | 🚫 ข้าม | คัดกรอง vs ยืนยัน | 🚫 ข้าม | 🚫 ข้าม | 🚫 ข้าม |
| 7 | **วงจรชีวิต** | state machine ของ order | สถานะของคดี | ระยะของโรค | 🚫 ข้าม | 🚫 ข้าม | 🚫 ข้าม |
| 8 | **ตารางพัง** | เขียนผิด → oversell | ตีความผิด → แพ้คดี | วินิจฉัยพลาด → ผลต่อคนไข้ | สมมติผิด → นโยบายพัง | อ่านหลักฐานผิด → สรุปผิด | ขั้นพิสูจน์ที่คนพลาดบ่อย |

**ช่อง 🚫 คือช่องที่ต้องข้ามจริงๆ ไม่ใช่ให้พยายามหาอะไรมาใส่** เหตุผลอยู่ในกล่องข้างล่าง

> ### ⚠️ กฎที่สำคัญที่สุดของทั้งไฟล์
> **section ที่บังคับ ปล่อยว่างไม่ได้ และ LLM ไม่ปฏิเสธ — ดังนั้นทุก section ที่ไม่เข้ากับวิชา จะกลายเป็นจุดที่มันแต่งเรื่อง**
> ความแข็งของโครงแปลง "ไม่เข้ากัน" ให้กลายเป็น "เท็จอย่างมั่นใจ"
