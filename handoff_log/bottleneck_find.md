## 🔍 วิเคราะห์ Bottleneck โดยละเอียด (ทีละกลุ่ม)

### กลุ่ม 1 — JaJoJi/mobile-backend-group-1
`OrdersProcessor` ถูก register แบบ unconditional ใน `AppModule` ทำให้ queue processor รันจริงบน**ทั้ง 14 container** ไม่ใช่แค่ 6 worker-only ตามที่ตั้งใจ (env `ROLE=worker` คุมแค่การเปิด/ปิด HTTP listener เท่านั้น ไม่ได้ตัด module ออก) ผลคือมี concurrency รวมสูงถึง ~28 workers แย่งกันจับ row เดียวกันของสินค้า hot SKU ผ่าน `SELECT...FOR UPDATE` ที่ `lock_timeout` แค่ 2 วินาที และ `attempts=2` เท่านั้น จึงเสี่ยง job fail ถาวรเมื่อสินค้าขายดีจริง นอกจากนี้ DB pool ตามทฤษฎี (300×14×2 ≈ 8,400) เกินความจำเป็นมากเมื่อเทียบกับ `max_connections=1500` — บ่งชี้ว่ายังไม่ได้คำนวณ pool sizing ให้ตรงกับจำนวน instance จริง

### กลุ่ม 2 — fiat222/flash-sale-system
Redis มีเพียง instance เดียว (ไม่มี replica/sentinel) ต้องแบกรับพร้อมกัน 3 หน้าที่: distributed lock (`SADD`+`DECR` แบบ atomic ผ่าน Lua), cache-aside ของหน้า product list, และเป็น broker ให้ BullMQ — จึงเป็นทั้ง **Single Point of Failure (SPOF)** และจุดที่ CPU/network ของ Redis อาจอิ่มตัวก่อนใคร สำหรับสินค้า hot SKU ตัว pessimistic row lock ที่ worker บังคับให้ order ทุกใบต้อง serialize เรียงคิวทีละ transaction แม้ BullMQ จะตั้ง concurrency ไว้ถึง 30 ก็ตาม ที่น่าสนใจคือทีมมีบันทึกไว้เองว่าเมื่อถอด edge cache ของ Nginx ออก คอขวดจริงกลับไปอยู่ที่ **CPU ของ API layer** (6×0.55 vCPU) มากกว่า DB หรือ Redis

### กลุ่ม 3 — STANDALONE42069/Mobile-Backend-Architecture
แม้จะมี Nginx (`least_conn`) กระจายโหลดระหว่าง 3 backend instance ได้ปกติ แต่ทุก order ของสินค้า SKU เดียวกันไปจบที่การ `UPDATE` row เดียวกันผ่าน atomic CTE ซึ่ง Postgres serialize การเขียนทีละ transaction โดยอัตโนมัติ (implicit row lock) ทำให้ Worker concurrency ที่ตั้งสูงถึง 10-20 ไม่ได้ช่วยเพิ่ม throughput ของ hot SKU เลย นอกจากนี้ยังไม่มี connection pooler (PgBouncer) คั่นกลาง ขณะที่ pool รวม (API 3×20 + Worker 20 ≈ 60-83) ชิดกับ Postgres default `max_connections≈100` มาก — ถ้าเพิ่ม instance ในอนาคตอาจชนเพดานง่าย และ Redis ตัวเดียวก็ยังเป็น SPOF ของทั้ง lock และ cache

### กลุ่ม 4 — LomerAlloys/FlashSaleBackend
สินค้า hot SKU ทุกออเดอร์ต้องผ่าน pessimistic row lock (`SELECT...FOR UPDATE`) ทำให้ throughput สูงสุดถูกจำกัดด้วยความเร็ว commit ทีละแถว ไม่ใช่จำนวน worker slot ~20 ช่อง (4×concurrency 5) หรือ DB pool ที่เหลือเฟือ (100/200) เลย อีกจุดเสี่ยงคือ Redis instance เดียวรับทั้ง distributed lock, L2 cache และ BullMQ broker พร้อมกัน — ถ้าตัวนี้ล่ม ระบบทั้งหมดหยุดทำงานทันที (SPOF) และเอกสาร `CLAUDE.md` ของทีมเองยังระบุจำนวน instance ไม่ตรงกับที่ deploy จริง (3 vs 4) ซึ่งอาจสร้างความสับสนตอนรายงานผลทดสอบ

### กลุ่ม 5 — PattaraponKitcharoen/mob05-flash-sale-backend
DB connection pool ไม่ใช่ปัญหา เพราะตั้ง `max_connections=300` ไว้สูง ในขณะที่ระบบมีจริงเพียง ~4 container จุดเสี่ยงจริงคือ **Redis instance เดียว**ที่แบกภาระทั้ง distributed lock (กันกดซ้ำ), cache-aside และ BullMQ broker พร้อมกันโดยไม่มี replica สำรอง และเนื่องจากค่า concurrency ของ Worker กับ TTL cache ถูกกำหนดผ่าน environment variable ที่**ไม่ได้ commit ไว้ใน repo** ทำให้ตรวจสอบพฤติกรรมจริงได้ยากและอาจไม่ตรงกับที่ทีมตั้งใจ นอกจากนี้ทุกออเดอร์ของสินค้าตัวเดียวกันยังคง serialize ผ่าน `UPDATE...WHERE remaining_stock>0` (implicit row lock) เหมือนทีมอื่น ๆ

### กลุ่ม 6 — tophbeifong123/mini-project-backend-mobile *(กลุ่มเรา)*
คอขวดที่ชัดเจนที่สุดคือ **`orders-worker` ตั้ง `concurrency=1`** (hardcode ทับค่า default=5 ในโค้ด) และใช้เพียง 0.25 vCPU ทำให้ทุก order ต้องประมวลผลเรียงต่อกันทีละใบ ไม่ว่า API layer จะมี 6 instance รองรับ request พร้อมกันได้แค่ไหนก็ตาม ผลทดสอบจริงของทีมเองยืนยันชัดเจน: read p95 = 291ms แต่ **write p95 พุ่งถึง 1,141ms** บน VM เดียวกัน (ต่างกันเกือบ 4 เท่า) จุดเสี่ยงรองลงมาคือ `redis-data` (แยกไว้เก็บ stock/lock/queue) เป็น single node ไม่มี replica และเคยเจอปัญหา `HINCRBY` ทำ memory พุ่งจน OOM มาแล้วภายใต้โหลดหนัก แนะนำเพิ่ม `WORKER_CONCURRENCY` เป็นอย่างน้อย 5 (ตาม default ในโค้ด) และทบทวน eviction policy ของ `redis-data`

### กลุ่ม 7 — sanpipop/FlashSaleSystem
แม้ออกแบบเป็น micro-batch (BullMQ รวม job 16-32 รายการต่อการเรียก stored function ครั้งเดียว) เพื่อลดจำนวนรอบไปกลับกับ Postgres แต่ทุก batch ของสินค้าตัวเดียวกันยังต้องแย่ง row lock เดียวกัน (`FOR UPDATE OF product`) จึง serialize อยู่ดี และมี Worker container เพียงตัวเดียวไม่ scale แนวนอน ทำให้ concurrency=8 ช่วยได้จำกัด ที่น่าสนใจคือทีมมีข้อมูลทดสอบจริงใน `tuning-results.md` ว่าเพิ่ม API instance จาก 3 เป็น 4 ให้ RPS เพิ่ม 15.6% แต่ **p95 latency แย่ลง 16.7%** เพราะ CPU context-switch contention บนเครื่อง 4 vCPU จึงตัดสินใจ revert กลับ 3 instance — ตัวอย่างที่ดีว่า **CPU ก็เป็นคอขวดได้** ไม่ใช่แค่ database

## 📌 Pattern ที่พบซ้ำในเกือบทุกกลุ่ม

1. **Single-row lock contention** — เกือบทุกทีม (1,3,4,5,6,7,9) ใช้ pessimistic `FOR UPDATE`/implicit row lock บนสินค้า SKU เดียวกัน ทำให้ throughput ของสินค้า hot SKU ถูกจำกัดด้วย **transaction latency ต่อครั้ง** ไม่ใช่จำนวน worker/instance — เพิ่ม concurrency ไปเท่าไหร่ก็ไม่ช่วยถ้ายังชน row เดียว
2. **Redis single instance = SPOF** — ส่วนใหญ่ (2,3,4,5,6,8,9) ใช้ Redis เพียงตัวเดียวทำหน้าที่ทั้ง lock + cache + queue broker พร้อมกัน มีเพียงกลุ่ม 1, 6, 7, 9 ที่แยก Redis เป็นมากกว่า 1 instance ตามหน้าที่
3. **Worker ไม่ scale แนวนอน** — กลุ่ม 3, 5, 6, 7, 9 มี Worker container เพียงตัวเดียว (กลุ่ม 6 ยังตั้ง concurrency=1 ซ้ำเข้าไปอีก) ทำให้เป็นคอขวดที่ชัดที่สุดในกลุ่มเหล่านี้
4. **DB pool sizing ไม่สอดคล้องกับ instance count จริง** — กลุ่ม 1 (pool เกินจริงสิบเท่า) และกลุ่ม 3 (pool ชิดเพดาน default) เป็นตัวอย่างสองด้านของปัญหาเดียวกันคือคำนวณ pool ไม่ตรงกับสภาพจริง
5. **CPU ก็เป็นคอขวดได้** — กลุ่ม 2 และ 7 มีข้อมูลทดสอบจริงที่ชี้ว่า เมื่อแก้ database bottleneck ไปแล้ว คอขวดถัดไปย้ายไปที่ CPU ของ API/Nginx layer แทน
